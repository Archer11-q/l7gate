# ADR-13 · 故障注入以应用层注入为主，tc netem 仅作交叉验证

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 3.1、9.3、4.1 门禁第 2 项

## 我选择什么

故障注入做在**网关转发路径内部**：按配置对指定路由/上游注入额外延迟、随机丢包、指定错误码、连接层 RST、上游响应中途截断。`tc netem` 只在需要独立证据时做一次交叉验证，不作为主手段。

## 为什么应用层注入是主手段

1. **可控**。注入条件是「这条路由、这个上游、这批请求」，而不是「这块网卡上的所有流量」。后者会同时污染 Nginx 基线连接、Docker 内部网络、甚至我的 SSH 会话。
2. **可断言**。FAULT-INJECTION.md 的每一行「预期 vs 实测」需要明确的因果：注入 200ms 延迟 → p99 应当移动到某个区间、熔断应当在 N 秒内摘除。内核层注入时，我无法确定注入到的包是不是我关心的那一条，断言就退化成统计观察。
3. **不依赖内核**。这条在本机尤其重要：**WSL2 的定制内核（`6.18.40.1-microsoft-standard-WSL2`）不保证 `tc netem` / `sch_netem` 可用**，契约 9.3 已把这个风险写死。我的 perf 版本与内核也不匹配（见 ENVIRONMENT.md 第 4 节）——同一类风险，工具链不可用不是假设，是我这台机器上的现实。把核心验证手段压在内核特性上，等于给自己埋一个「做到一半发现做不了」的雷。
4. **可复现**。应用层注入的配置能进仓库、能被别人一键复跑；`tc` 命令依赖具体内核模块与网卡名，写进脚本也不可移植。

## 应用层注入的固有偏差，我必须承认

在转发路径里注入延迟，**测的是「网关认为上游慢」时的行为，不是真实的内核网络栈行为**。具体失真：

- 我注入的位置之后的真实排队、TCP 重传、缓冲区效应不会发生。
- 因此「超时与重试防放大」（S4）用应用层注入测是合适的，而「TCP 层丢包恢复时间」这类问题应用层注入**给不出有效结论**。

这就是为什么保留 `tc netem` 作为**交叉验证**：只在结论涉及内核网络语义时用它，且用它之前先确认本机内核支持。用不了就在 FAULT-INJECTION.md 如实写「该场景未验证，原因：WSL2 内核不支持 netem」，不假装测过。

## 与「数字造假是本项目最严重的错误」的关系

故障注入是本项目最容易自说自话的部分——注入开关是我自己写的，预期也是我自己定的。约束办法是：**先写预期再跑注入**。`FAULT-INJECTION.md` 的每一条记录格式固定为「注入条件 / 预期 / 实测 / 是否达标 / 归因」，未达标照记。如果实测与预期不符，改的是结论，不是预期。
