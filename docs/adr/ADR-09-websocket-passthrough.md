# ADR-09 · WebSocket 只做 Upgrade 后的纯透传，不解析帧

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 1.3、4.2、SLO #2

## 我选择什么

正确处理 `Upgrade: websocket` 握手（101 响应、连接语义切换），**握手之后一律按不透明字节流双向透传**。不解析 WebSocket 帧头，不做帧掩码解码，不实现 ping/pong 语义处理（ping/pong 只作为「链路还活着」的空闲超时依据），不复用帧做消息级治理。

## 为什么

1. **握手后的流量已经不是 HTTP 了。** 我的 filter 链、路由、限流判定全部建立在「解析得出请求行与头部」这个前提上。101 之后这个前提消失，硬套只会有两种结果：要么把二进制帧当文本解析（错误），要么在透传里塞帧感知（范围扩张）。
2. **帧解析会把重心从尾延迟治理拉走。** 消息级限速、消息级重试、按消息路由这些听起来漂亮，但契约第 2 节没有任何一个数字需要它们。
3. **透传才是这个场景的真实难点**（契约 4.2 明确点了这三条）：
   - 不切透传，连接会卡死——请求-响应模型等不到「响应结束」。
   - **短连接测 C100K 是假的**，连接在不断重建，量不出每连接常驻内存。只有长连接才真正考验 SLO #2 的「每连接 ≤ 20 KB」。
   - 优雅退出最难处理的就是长连接：存量连接不会自己结束，drain 必须有超时兜底。

## 与 SLO #2 的关系（这条不能含糊）

我要测的是 100k **空闲**长连接的稳态占用，透传模型完全够用：每连接成本 = fd + 上下游两个连接对象 + 两个 buffer 的实际分配。如果为了「看起来更完整」去持有帧缓冲、消息拼装，每连接内存会直接涨到不可达标——**这个不做项是 SLO #2 达标的前提之一，不是简化**。

## 代价

不做帧级治理意味着我不能对 WebSocket 流量做消息级限流或熔断，只能做连接级。这一点会写进 README 的限制段。

## 验证归属

S1-05 用单测断言「101 之后帧内容不被解析、不被改写」；`demo/ws-echo.html`（契约 4.2 第 2 层演示面）负责演示 Upgrade 后仍能正常双向收发，配合故障注入能看出熔断摘掉后端时长连接的实际情况。
