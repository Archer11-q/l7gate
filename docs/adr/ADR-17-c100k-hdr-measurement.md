# ADR-17 · 测量手段：自研 C100K 长连接客户端、多目标地址口径、HDR 风格分位

- 状态：**部分采纳**——客户端 / 多目标地址 / HDR 分位三条已采纳并实现；**第二跳（网关→上游）的多端点口径待项目所有人裁决**，见最后一条
- 日期：2026-10-28
- 相关：`docs/SLO.md` #1（p999 半边「无法判定」）与 #2（100k 长连接资源占用）、`docs/ROADMAP.md` 的 2026-10-26 裁决表第 4 行（「p999 由自研 C100K 客户端做 HDR 分位，落地时随 `c100k.sh` 补一条 ADR」）、卡点四（每连接内存分母＝**连接对**）、ADR-09（隧道只透传）、ADR-14/15（per-worker 拥有与池）、`docs/ENVIRONMENT.md` 第 7 节（临时端口 28,232 的取证）、契约 1.3「自研压测客户端」唯一许可场景

## 我选择什么

**SLO #2（100k 长连接）与 SLO #1 的 p999 半边，用我自研的长连接客户端取数；它跨多个目标地址建连，并把延迟记进对数分桶的 HDR 风格直方图。**

1. **工具**：`tools/c100k_main.cc` → `l7gate_c100k`。单线程 epoll ET（复用 `net/Epoll`、`net/socket`，与网关同一套自研网络层，不引第三方），非阻塞 connect + 发请求 + 收到响应即记一次延迟。**两种形态**，各自对上一个 SLO：
   - `--requests-per-conn 0`（默认）= **隧道空闲形态**：发 HTTP 升级请求、读到完整 `101` 头算握手完成，之后**不再消费任何字节**（只保留"对端把我关了"的可见性）。这正是 SLO #2 的口径：短连接测 C100K 是假的（契约 4.2 那句），只有长连接才真考验每连接内存。
   - `--requests-per-conn N > 0` = **闭环请求形态**：每条连接串行发 N 条 keep-alive GET，一次只在飞一条，逐条记「请求写完 → 响应收完」的**每请求**延迟，并给 QPS。**SLO #1 的 p999 只有这个形态才存在**——握手延迟量的是"建一条连接花多久"，和"每条请求网关引入多少"是两个物理量，拿前者填 #1 那一格就是换口径。加这个形态不是范围扩张：裁决（2026-10-26）把 p999 的取数手段交给这个客户端，一个只会量握手的工具交不出那一格。
2. **多目标地址口径**：客户端按 round-robin 把连接摊到**多个目标地址**上，脚本用 `--targets 127.0.0.1:P,127.0.0.2:P,…` 显式给，**目标地址数与每个地址的连接数一律写进报告**。理由不是"配得好"，是实测的天花板（见下面「为什么」那条），把它藏起来就是让报告里的 100k 看起来比实际容易。
3. **HDR 风格分位**：不存全部样本（100k×60s 的样本量会把工具自己的内存变成被测对象），改存直方图。桶设计是**两级**：`[0, 1 ms)` 每 **1 µs** 一个桶（1024 桶），`[1 ms, 64 s)` 每**倍频程 16 桶**（16 个倍频程 → 相对误差上界 4.3%）。输出**必须带桶宽/误差棒**（`p999=12.3ms±5.3%` 这种形状），不报单点。分位取数按累计计数插值，且**只有工具自己产出的 p999 才进 SLO #1 的 p999 那一格**（取自闭环请求形态那套直方图，不是握手那套）——wrk 4.1.0 / hey 0.1.4 的分位表只到 99%，那两条线（B-001、B-004）不作废也不回头改。
4. **fd 上限不是环境阻塞**：脚本侧 `ulimit -n` 自抬 + 进程侧 `setrlimit(RLIMIT_NOFILE)` 抬到"需要值 + 余量"（夹在 hard 以下）。2026-10-27 实测：soft=10240、**hard=1048576**、`ulimit -n 300000` 当场成功、`fs.file-max`=9.2e18——**不需要 root、不需要改机器配置**。这条把 S1 期间写在四处的"必须先解决 rlimit"当场作废（那处措辞已就地更正）。
5. **上游夹具加一个 `--upgrade` 模式**（`tools/bench_upstream_main.cc`）：收到带 `Upgrade` 的请求就回完整 101 头，之后只读不管（隧道字节不需要被理解，ADR-09 同一个立场）。**默认行为一字不改**——B-001…B-005 那几轮的固定体回显仍然成立，换了默认行为等于作废历史基线。

## 为什么

**因为要在单机回环上开 100k 条*已握手*的长连接，唯一挡住我的不是 fd、不是内存，是临时端口——而这个数是实测出来的。**

- **同一个 `(源 IP, 源端口, 目的 IP, 目的端口)` 元组的实测上限 = 28,232 条**。第 28,233 条 `connect()` 返回 `EADDRNOTAVAIL`（errno 99）。这正是 `ip_local_port_range = 32768–60999` 的宽度，但**我不拿算术当结论**：2026-10-28 用一次性探针在本机实测（服务端 accept 后全部持有，确保是真实在建连接而不是半开队列）。
- **换目的地址各自再拿满 28,232**：在第一个元组已经耗尽之后，`127.0.0.2:同端口` 仍然成功开出 **28,232** 条 → 4 个目的地址 = **112,928** ≥ 100k，余量 12.9%。**这就是"多目标地址"这条口径的全部依据**，也是为什么它必须写进报告：它不是风格，是这次测量的前提条件。
- 换源地址同理（实测 ③ 又开出 28,232），但那条路要走"网关回源时绑源地址"，等于为测量发明一个生产语义，我不选它（选它的话报告里那个 100k 是靠一个只有测试才会打开的开关撑起来的）。
- 客户端侧的多地址**不需要动网关代码**：实测 `l7gate --serve --listen 0.0.0.0:18095` 能被 `127.0.0.1/.2/.3/.4` 四个地址都打到（四条 `HTTP/1.1 200 OK`）；上游 `--listen 0.0.0.0:0` 同理。**缺的只有网关自己回源时只能用 `--upstream` 那一个地址**（见最后一条）。

## 我放弃什么

- **不引入 wrk2 / hdrhistogram / Vegeta / Go 版压测器**。它们都能少写我这一份代码，但契约 1.3 早就定了"HTTP 吞吐一律用第三方工具，只有长连接场景允许自研"，而 p999 取数手段的裁决（2026-10-26）明写"不引 wrk2/vegeta 之类第三方依赖"。引一个新依赖就是把 SLO #2 的可复现性挂在一个我没锁版本的东西上（契约 9.1 的版本锁定表里没有它们）。
- **不追求分位数的绝对精度**。HDR 的卖点本来就是"有界相对误差换常数内存"；我把它做成显式的两级桶并**强制在输出里带误差棒**。要精确到 µs 就得存全样本，那会让测量工具自己的内存随连接数与时长增长，反过来污染它要测的东西。
- **不在客户端里做任何"模拟业务"的帧收发**。SLO #2 的口径是握手后空闲；发帧会把背压、隧道泵、上游 read 全搅进来，那个 RSS 就不再是"每条长连接的持有成本"。业务帧的验证归 S1-05 的透传用例与 S2-05 的隧道硬关用例。
- **不用 4 个网关进程拼出 100k**（详见最后一条的候选 B）。SLO #2 的"每连接内存"定义是 `(VmRSS − 空进程基线) / 连接对数`，这个口径只对**一个进程**成立；四进程各 25k 得到的每连接数与一进程 100k 不是同一个物理量——分配器的 arena/per-thread 缓存摊薄方式都不一样，把四份求和写成"100k 实测"就是拿外推冒充实测。

## 后果与约束

- **测量工具的自报口径**：客户端进程自己的 RSS/fd/CPU 全部单独打印，绝不与网关的数混在一张表里；网关的空闲 CPU 一律取**该进程** `/proc/<pid>/stat` 的 utime+stime 增量（不是系统级 5%），否则客户端自己的 100k 握手会把网关的"空闲"读脏。这条在 `c100k.sh` 的输出里写死。
- **工具自己要有等式，不能只有读数**。它不进 ctest（`tools/` 的语义是被构建、不被断言），所以它的正确性由三条当场可算的等式兜住，实测在 FAULT-INJECTION 第 3 节：`requests_done` == 网关 `requests_parsed` == 网关 `responses_completed` == 上游 `requests`；`bytes_down_to_upstream` == 条数 × 请求字节数；`bytes_up_to_downstream` == 条数 × 响应字节数。**再加一条量纲口算**：`mean × 并发数 ≈ 窗口 ÷ 条数`——我第一版闭环量出 mean 4.2 µs 而窗口÷条数是 468 µs，就是这条口算把它抓住的（根因见 ARCHITECTURE §5 那张表的最后三行：观测输出进热路径、`EPOLLOUT` 没摘导致计时起点每轮重打）。限速同理：**"延迟只随总量变、不随速率变"就是 ramp 没生效的签名**，不是被测方的性质。
- **建连必须限速**：`somaxconn=4096`、监听 backlog 也在这个量级，100k 条 SYN 一次性砸下去测的是内核队列不是网关。`--ramp-ms` 给窗口，脚本报告**建连速率**（条/秒）与 `accept_errors`/`downstream_rejected_over_capacity`/`upstream_connect_failed` 三个失败计数——**任何一个非 0 就作废这一轮**（BENCHMARK 规矩：工具丢了负载那一轮直接作废，不许记个数继续算）。
- **每连接内存的分母仍是「连接对」**（卡点四裁决）：100k 对 = 200k 个 `Connection` 对象；ADR-15 的 per-worker 池在这条路径上摊销为空（隧道态上游不入池、不可复用），所以构成表里那一格要按**实测**写，不拿"池省了连接"来抵——那是 ADR-15 后果段已经禁止过的邀功。
- **p999 的可判定性到此改变，但 SLO 目标值一个字没动**（禁令二）：`SLO.md` #1 那一格从「无法判定」改成"有取数手段"，判定仍要等实测数字（S2-07）。
- **工具不进 ctest**（与 `tools/bench_upstream_main.cc` 同一条纪律）：`tools/` 是被构建的、不是被断言的，"哪段代码被断言过"这个性质不能被压测工具稀释。它的正确性由脚本的**等式断言**兜（发出的字节数 == 收到的字节数、握手成功率 100%、`refused==0`）。

## 未决（要项目所有人裁决）：第二跳的多端点口径

**问题**：SLO #2 要 100k 条**已握手的 WebSocket 长连接**，而 ADR-09/ADR-15 的形状是一条下游隧道 1:1 配一条上游连接（隧道态不可复用、不入池）。所以 100k 下游必然要 **100k 条网关→上游连接**，全部落在同一个目的元组上 → 实测天花板 **28,232**。**这一条今天已经不是推断了**：2026-10-28 的 100k 名义档实测 `downstream_accepted=100000`（下游侧四条元组全接进来了、`accept_errors=0`）而 `established` 精确停在 **28,231**、`upstream_connect_failed=75,708`（BENCHMARK B-006 结果二）。**不解决这一格，SLO #2 的 100k 判定就只能记未达标／测量条件不齐。**

候选与我怎么看：

| 候选 | 做法 | 代价 |
|---|---|---|
| **A（我推荐）** | 网关 `--upstream` 支持**多个端点**，按 **worker 固定映射**（worker i → 端点 `i mod E`，E=4 → 4×28,232=112,928）。**不做** per-request 选择、不做健康检查、不做故障转移——那些仍然留给 S3 的路由/负载均衡。 | 要在 `Reactor::Config` 与 `ReactorGroup::Config` 里加一个"端点列表"，并给 `ensure_upstream` 传目标；**它不是零改动，而且离 S3 的边界很近**，所以我先写 ADR 再动代码，也不在这条 ADR 里自己拍板 |
| B | 起 4 个网关进程，每个 25k 连接 | 不改产品代码，但**SLO #2 的口径就变了**（每连接内存的定义只对一个进程成立，见上面"我放弃什么"最后一条）。拿它冒充实测是我要避免的那种错 |
| C | 只测到 28,232 连接对，SLO #2 记「未达标／测量条件不齐」+ 归因就是这条端口天花板 | 最诚实但把 100k 这一格推给 S3/S4，S2 门禁第 1 条的 #2 半边只能按"有读数、判定推迟"记 |
| D | 抬 `ip_local_port_range`（sysctl，要 root） | 默认 28,232 → 约 64,512，**仍然 < 100k**，单靠它不够；而且它改了机器配置，历史数据的可比性要额外声明 |

**我按 A 的理由**：它是唯一既不歪口径、又不必把 100k 推后的路；"网关连一个上游集群而非单点"本来就是产品应有的形状，只是这次把它限制到"静态、per-worker、无策略"这个最小形，避免提前把 S3 的路由做完。**但这确实是在 S2 里加一项配置能力**，方向该你裁——你点头我就按 A 写进 TASKS（新增一条 S2-06a）再动手；你选 C 我就把 28,232 这一档的实测与构成表交齐、SLO #2 按未达标照记。
