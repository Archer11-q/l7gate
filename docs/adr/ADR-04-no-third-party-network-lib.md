# ADR-04 · 网络层在本仓库内自行实现，不引入第三方网络库

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 1.3、3.1

## 我选择什么

epoll 封装、事件循环、Buffer、HTTP/1.1 解析、连接对象生命周期全部在本仓库手写。不引入 asio、muduo、brpc、folly::fibers 等任何第三方网络库。

## 为什么

**因为「网络层怎么写的」就是本项目要交付的东西。** 一个用 asio 包出来的网关，评审者要问的仍然是 p99 多少、差在哪，而我对性能曲线的每个拐点都失去了第一手解释能力——那才是空壳。自研的代价是我必须自己承担 ET 语义下的读干净、buffer 高水位、fd 与连接对象生命周期对齐这些细节，而这些恰好是 S1 里「被逼出来的问题」的来源（S1-07）。

第三方库在这里也不是没有代价：asio 的错误码模型和完成处理器风格会把 Reactor 的显式状态机打散成回调图，我要验证 TSan 干净反而更难；muduo 是 LT 模型，与 ADR-02 的选择正面冲突。

## 边界（我不无限自研）

自研范围严格限定在**网络与协议层**。以下我都用现成的，不重造：

| 用现成 | 用途 | 为什么不自己写 |
|---|---|---|
| hiredis v1.2.0 | Redis 客户端 | RESP 不是本项目考点，见 ADR-05 |
| libmysqlclient 8.4.x | MySQL 客户端 | 同上，见 ADR-06 |
| GoogleTest v1.14.0 | 单测 | 测试框架与项目价值无关 |
| prometheus-cpp v1.1.0（或自实现 `/metrics`） | 指标暴露 | S5 才用到；契约 9.1 已预留「编译成本过高则自实现纯文本端点，但先写 ADR」的分支 |

判断标准是：**它是否承载本项目要证明的能力。** 承载就手写，不承载就用现成的，两类都写进本 ADR 以免日后被误读成「什么都自己造」。

## 代价

代码量、bug 面、以及「协议实现正确性只能靠我自己的测试保证」——这正是半包/粘包 12 类畸形输入用例（S1-03）必须存在的理由。我会用 ASan/UBSan/TSan 三件套作为兜底，而不是声称手写代码没有 bug。
