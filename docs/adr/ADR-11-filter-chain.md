# ADR-11 · filter 链架构，而非写死的转发流程

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 3.1、S1-08、S4

## 我选择什么

转发路径不是 `解析 → 限流 → 路由 → 转发 → 熔断` 这样一条写死的代码序列，而是一条**由配置决定顺序与组合的 filter 链**。每个 filter 有统一接口，作用于请求阶段与响应阶段；主路径代码只负责按序驱动链，不认识任何具体 filter。

## 为什么

**工业界一致做法。** Envoy 是 filter chain，Pipy 是 pipeline。两条独立演化出的 L7 项目收敛到同一个形状，说明这不是审美偏好，而是这类系统的耦合点天然长这样：治理能力的种类会不断增加，但「在请求生命周期的哪些时刻可以介入」是有限的。

三条具体理由：

1. **配置驱动组合是免费的。** 一旦有链，「这条路由限流但不熔断」「那个上游组先路由后限流」就是配置行数的差别，不是代码分支的差别。写死顺序的话，每一种组合都要在主路径里加 if。
2. **成本极低而架构约束力真实。** 我不靠文档承诺「主路径不随功能膨胀」，我靠一条可执行的断言：**S1-08 的验收标准是「新增 filter 不修改转发主路径的任何一行代码」**。做不做得出来，测试直接给答案。
3. **它是 S4 的前置。** 限流、熔断、重试防放大都是 filter。S4 往链上填充时，主路径应该一行不改——如果改了，说明 S1-08 的空壳骨架是假的。这正是我为什么在 S1 就搭空壳：骨架的价值要在还没有功能诱惑的时候定下来。

## 顺序为什么必须由配置决定而不是我定一个「正确顺序」

因为不存在无条件正确的顺序，而且这个分歧是可测的：限流放在路由之前，超配额直接 429、不消耗上游连接；放在路由之后，才能按上游做配额。两种都合理，取决于策略意图。**我把这个选择交给配置，而不是在代码里替所有人决定。**

## 我放弃什么

- 不做插件热加载（`.so` 动态装载）。链在配置里声明的仍是内置 filter，新增类型要重新编译。理由：动态装载引入 ABI 与生命周期问题，而没有任何一个 SLO 数字需要它。
- 不做 Lua/WASM 脚本层。那是「框架」能力，契约 1.2 明确本项目定位是产品不是框架。

## 与 ADR-10 的连带关系

配置热重载时要替换的是「链的组合与顺序」这份数据。链上 filter 实例若持有跨请求状态（限流窗口、熔断计数），就不能跟着配置重建——否则每次 reload 都清零熔断历史，安全阀失效。所以状态在共享结构里、链只引用它。这个区分是 S5 的一个真实难点，先在这里记账。
