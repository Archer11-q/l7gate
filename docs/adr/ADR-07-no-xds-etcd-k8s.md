# ADR-07 · 不引入 etcd / xDS / K8s / Service Mesh / 动态服务发现

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 1.3、3.1；ADR-06

## 我拒绝什么，以及为什么

| 拒绝项 | 一句话理由 |
|---|---|
| xDS 协议族 | xDS 是为**多实例服务网格**控制面与数据面通信设计的。单机网关引入它是纯成本：一套 LDS/RDS/CDS/EDS 的订阅与版本协商状态机，换来的能力我本地配置文件就有。 |
| etcd | 它的价值是分布式共识 + watch。我要的配置读取与周期 reload 不需要共识；审计与时间回溯是关系型查询，见 ADR-06。 |
| K8s / Ingress / Service Mesh 集成 | 运维栈不是 C++ 栈。一旦声明「支持 K8s」，评审者合理的问题是 Sidecar 注入、CRD 版本兼容、EndpointSlice watch——全都不是本项目要回答的问题。 |
| 动态服务发现 | 用「配置文件 + MySQL 节点表定期 reload」替代。 |

**判断标准始终是第 2 节那三个数字。** 上面每一项都通不过「它服务于哪个数字、或它防住哪种失效」这一问。

## 动态服务发现这条要说清代价

我不假装定期 reload 等价于服务发现。真实差距是**收敛延迟**：节点上下线到网关感知，最坏是一个 reload 周期。这在稳定部署（上游是我自己起的两个假上游 + Nginx 基线）下无关紧要，在弹性伸缩场景下不可接受。

我会把这个限制如实写进 README 的定位段：**本网关假设上游集合是运维管理的稳定集合，不是弹性集合。** 定位说清楚了，限制就不叫缺陷；说不清楚，它才叫。

## 如果日后要推翻

解锁条件是「多实例部署 + 需要秒级配置收敛」成为真实需求。届时不是加个 etcd 客户端就完事，要重写 ADR 并回答：多实例间如何达成一致、reload 与热重载（ADR-10）如何协调、旧配置的引用计数在跨实例语义下意味着什么。
