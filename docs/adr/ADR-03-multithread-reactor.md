# ADR-03 · 多线程 Reactor，而非多进程 SO_REUSEPORT

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 3.1、1.3

## 我选择什么

一个监听 fd，主线程 accept 后把连接对象派发给 N 个 Reactor 线程（每线程一个 epoll 事件循环），线程间共享状态用显式同步原语。不采用「每进程一个 SO_REUSEPORT 监听 fd、内核分担 accept」的多进程模型。

## 为什么

**决定性理由是本项目要治理的东西全是共享状态**：熔断的三态机与节点健康度、限流的令牌桶与滑动窗口、上游连接池、单位时间统计。

- 多进程模型下，这些状态要么每个进程各有一份（那么「最多摘除 10%」就变成了「每个进程各自摘除 10%」，在全局视角是错的；限流阈值 N 也会被放大成 N × 进程数——这正是契约 3.4 里「单机限流在多副本下不准」的同一个失效模式，我何必自己在单机内复刻它），要么就得跨进程同步（共享内存 + futex / 无锁环形队列），复杂度直接超过本项目要解决的问题本身。
- 一个进程内，线程共享地址空间，熔断状态与限流计数天然是一份事实。代价是并发正确性，而这个代价我有**自动化验证手段**：TSan。契约 4.1 把「TSan 干净」定为 S2 门禁，就是这笔代价的显式对账。

## 我放弃什么

- 多进程的两个真实好处：单进程崩溃不影响其他进程；SO_REUSEPORT 由内核分流、accept 无锁竞争。
- 我不用多进程扛 crash，是因为网关崩了就等于流量全断，进程级隔离对本项目只是把故障域切小，不改变 SLO。真要谈可用性，那是多实例部署的事（而我已按 ADR-07 排除 Service Mesh 栈）。

## 后果与约束

连接对象跨线程传递与**异步销毁**是 S2 的核心难点，也是这个项目里最容易写出 use-after-free 的地方。所以顺序是硬性的：S2 必须同时交付 TSan 干净的证据，否则不进 S3。

accept 单点可能成为瓶颈，我把它列为延迟观察项：只有在压测显示主线程 accept 排队时才考虑改造，届时先写 ADR。
