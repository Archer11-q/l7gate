# ADR-01 · 协议只实现 HTTP/1.1

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 3.1、1.3；ADR-02、ADR-13

## 我选择什么

只做 HTTP/1.1：文本协议、keep-alive、`Content-Length` 与 chunked 两种 body。不做 HTTP/2、gRPC、HTTP/3(QUIC)，也不自定义二进制协议。

## 为什么

**这个决定的唯一标准是第 2 节那三个数字能不能被可信地量出来。**

1. **可对比性 > 先进性。** HTTP/1.1 是 Nginx 的主场，我能拿它当公开基线做同环境对比。契约第 2 节的吞吐目标本身就以 Nginx 实测值的 60% 定义——协议一旦换掉，分母就没了。
2. **第三方压测工具只认 HTTP/1.1。** wrk / hey / ab 都能直接打。HTTP/2 需要一个我完全无法独立验证的自研客户端（契约 1.3 禁止自研压测工具，除 C100K 长连接外），量出的数字可信度天然打折。
3. **实现量不是同一量级。** h2 的 HPACK 动态表、流控窗口、多路复用状态机、h3 再加 QUIC 的拥塞控制与连接迁移，任何一项的实现量都是 HTTP/1.1 一个数量级以上。做完这些我的重心会从「做网关」滑向「实现协议」，而项目要证明的是流量治理与尾延迟，不是协议栈。
4. **可观测性。** 文本协议在 tcpdump 里肉眼可读，故障注入返回的 429/503 能直接抓包断言。这不是便利性偏好，它决定了 FAULT-INJECTION.md 里的每一条「预期 vs 实测」能不能被第三方复现。

## 我放弃什么

- 多路复用带来的连接数下降——但契约 SLO #2 关心的恰恰是**长连接资源占用**，h2 反而会让这个指标失去意义。
- gRPC/流式这些「简历上更好看」的能力。我不做业务 API（契约 1.2），它们没有服务对象。

## 代价与边界

HTTP/1.1 的队头阻塞是真实存在的，我在 keep-alive 上仍是一请求一响应。这在报告里必须如实写：**我的 p99 是 HTTP/1.1 语义下的 p99，不能外推为「我的网关比 h2 网关快」**。协议选型是范围限定，不是性能结论。
