# ADR-18 · 路由作为 filter 链上的一环：`RequestInfo` 的目标上游字段 + per-worker 池按目标分桶

- 状态：已采纳（S3-01 落地本 ADR 的三件事；负载均衡三策略与节点表文件归 S3-02，健康检查归 S3-03）
- 日期：2026-10-29
- 相关：ADR-11（链的形状与可插入点）、ADR-14（连接单线程拥有——**本 ADR 不许扩大它的跨线程接触面**）、ADR-15（池的归属；**它的按目标分桶写成下面的追加节，正文一字不改**）、ADR-16（配对模型——目标切换的时机由它决定）、ADR-09（隧道不经过链）、`docs/ARCHITECTURE.md` 1.16/1.17/1.18/1.21、`TASKS.md` 的「## S3」已裁三条

## 这一节在问什么

S2 之后网关会分摊并发，但它只会把请求交给"配置里那一个地址"。要按请求决定交给谁，必须同时回答三个问题，而这三问是同一个不可逆决策的三个面：

1. **决定放在哪里**——放在转发主路径里的一段 if，还是放在链上的一环？
2. **决定怎么交出去**——主路径拿得到"目的地"吗？今天拿不到：`RequestInfo` 里没有这一格，`ensure_upstream` 只读 `Reactor::Config` 的地址与端口（`src/net/reactor.cc:649`）。这就是 1.16 末尾欠的那笔返工。
3. **决定一变,池怎么办**——一个 worker 从此可能碰多个目的元组,ADR-15 那个不带目标键的 `vector` 就装不下了。

## 我选择什么

**一、路由是 filter 链上的第一个业务 filter,它的决策通过 `RequestInfo` 的两个新字段交回主路径。**

```cpp
struct RequestInfo {
  // …既有四个字段（method / target / headers / request_bytes / downstream_fd）一字不动…
  std::uint16_t upstream_target = kNoUpstreamTarget;  // 0xffff = "我没决定,用默认目标"
  std::uint16_t reject_status = 0;                    // 0 = 不表态;非 0 = 请回这个状态码
};
```

- `FilterChain::run()` 与 `RequestFilter::on_request()` 的参数从 `const RequestInfo&` 变成 `RequestInfo&`。**这是链接口的第一次返工,理由与 S1-08 定下的规矩同源:写通道必须显式存在,而不是让 filter 去改一份借来的读视图。** 可读的那四个字段仍然是借用的 view、仍然不许存进成员、仍然在 `finish_request` 一消费就作废——我把 const 去掉是为了这两个数字,不是为了让 filter 能碰 view。
- **`Decision` 不加第三个值,`ForwardOutcome` 不加第四个值**。kStop 之后分两种走法:`reject_status != 0` → 走 S1-06 已有的 `fail_pair_with_reply()`（回完就按既有口径收尾）;`reject_status == 0` → 保持 S1-08 的行为(字节留在原地、连接不关、一条响应都不发)。这不是钻空子:ADR-11 当年拒绝 `kRejected(code)` 的理由是"拒掉之后回什么字节是那个 filter 的责任,今天给它一个状态码字段就是给一条没人走的分支发空头证明"。**S3-01 正是那条分支的第一个走路人**,所以字段现在才进来——同一条纪律的两半,不是自相矛盾。

**二、无匹配的回 404,走 `reply_status_for_parse_error` 那张表的同一形状。**

路由表里没有任何规则命中 = 客户端要的东西我没有路由,这是**请求侧的确定性结果**,不是网关故障(503/502 都会让运维去查一条根本没坏的 upstream)。`gateway_error_reply()` 加 `case 404` 一格,body 与 `Content-Length` 照既有每条的写法一一对死。这条表和 S1-06 那张表的共同纪律是:**刻意不写 default,新增分类忘了归类时 `-Wswitch` 会点名**。

**三、匹配本身是纯函数,放在 `src/route/router.{h,cc}`,不碰 fd、不发 syscall。**

```
RouteRule { kind ∈ {prefix, regex}, pattern, target }   →  RouteTable（规则数组，顺序 = 配置顺序）
match(table, target_view) → optional<target>            →  可重复喂入，同输入同输出
```

这条分工继承 S1-03 给解析器立的规矩:判定逻辑一旦和 socket 状态混在一起,我就只能用真连接去测它,测出来的失败分不清"路由错了"还是"时序没对上"。纯函数意味着 22 条以上的规则语义用例能在一个不建 socket 的文件里跑完。

三个语义定死:

- **前缀 = 最长匹配优先**,不是第一条命中、更不是字典序第一条命中。用例集故意放 `/api` 与 `/api/v2` 两个长度:`/api/v2/users` 必须落 `/api/v2` 的目标;谁把规则按字典序排了或者按"第一条命中"返回,这条用例当场红。
- **正则 = 全串锚定**(整条 target 必须匹配完整个模式)。定死这条是为了让 `regex_search` 那种"模式出现在任何位置都算"的实现红掉:`/ap` 不该命中 `/api/x`。
- **匹配对象是解析器给的原始 origin-form `target`,含 query、不解码、不做路径规范化。** 这是安全选择而不是省事:`%2F`、`..`、大小写折叠任何一项归一化都可能让"我路由掉的东西"和"上游自己解析到的东西"不是同一个路径,那是请求走私的家族。归一化如果要做,得连"上游侧会看到什么"一起重新裁决,不是这一条 ADR 的单方动作。

**四、per-worker 池按目标分桶,但仍然 per-worker、仍然不 shared**(已裁第 1 条的落地形状,详见下面 ADR-15 追加节):

```cpp
// Reactor 成员，每 worker 各一份，只被该 worker 的循环线程碰——无锁面与 S2-02 完全相同
std::vector<std::vector<std::shared_ptr<Connection>>> upstream_pool_;  // 下标 = target
std::vector<Target> targets_;                                          // 下标 = target，配置期定长
```

`Reactor::Config` 从"一个地址 + 一个端口"换成**目标表 + 默认目标下标**,单一真相源在表里(保留两个字段就等于"同一个限制有两个抄本",那条教训见 `http/request_parser.h` 里 `max_header_count` 那段)。**没有路由 filter 时,每个 worker 的默认目标就是 S2-06a 指派给它的那一个**(`reactor_group.cc` 的 `i mod E` 原样保留,只是它现在写的是"默认目标下标"而不是"一个端点")——所以 S2 交出的容量公式 `min(N,E) × 28,232`、B-007 的 100k 读数、八份 canonic 档全部不作废,`--serve` 的两条横幅(`upstream=` / `upstream_endpoints=`)一个字不改(它们是 `s1-p99.sh:126-132` 判路径的签名)。

**五、目标可以换,但只能在干净边界上换;换不动就压住这条请求,并且欠它一次重驱动。**

ADR-15 定的配对是"下游存活期独占一条上游"。路由按请求选目标,于是出现新形态:一条 keep-alive 下游的第 N 条请求要去的后端不是它当前配对的那条。我的规则写死成一句可断言的话:

| 配对上游现在 | 目标变了怎么办 |
|---|---|
| `in_flight == 0` 且 `outbound_pending == 0` 且 `upstream_reusable()` 为真 | **换**:把它按自己那条目标归还进对应桶,再从 `target` 桶借/新建——这正是 ADR-15 已有的"干净可复用"边界,我不新造第二个复用判据 |
| `in_flight > 0`(上一条请求的响应还没回完) | **不换**:这条请求压在下游缓冲里(`kBlocked`),等配对上游在飞归零那一刻换 |
| 不可复用(隧道、`close_after_response`、出向还有货) | **不换**:同上压住;它变干净的时机由既有的 `retry_peer_after_room()` → `forward_pending_requests()` 接手 |

第二行买到的性质是 **ADR-16 的响应 FIFO 不会被路由打乱**。如果允许"响应还在 A 路上的时候把下一条请求发给 B",下游收到的响应序列就不再由请求顺序决定——那不是负载均衡的代价,是我自己造的错位。

代价必须写明白:**`pump_response` 的 `kComplete` 分支今天要新增一次重驱动**(`in_flight` 减到 0 且配对下游手上确实还压着完整请求时,再走一遍 `forward_pending_requests`)。没有它,被第二行压住的那条请求永远等不到重试——客户端在等响应、网关在等在飞归零、而"在飞归零"这件事发生时没人叫醒下游侧的转发循环,**这是一条会挂死的环,不是理论**:我在写代码前顺着 `note_response_completed()`(`reactor.cc:1293`)往下找重驱动点,找到的是空,所以这一格必须补。它只在"目标要换且手上还有在飞"时才真的干活,判据是 `downstream->request() != nullptr`,空链那一臂永远不满足。

## 为什么

**因为这三件事里,只有"路由进链"是可选项,另外两件是它的必然代价。**

- **为什么不写进主路径的一段 if**:那样 ADR-11 那条"S1-08 的验收=新增 filter 不改主路径任何一行"就从性质退化成了口号,而 S4 的限流/熔断就是靠这条性质插进来的。代价我也照记:本 ADR **确实**改了主路径(`forward_request` 多一个参数、`ensure_upstream` 多一个参数、链调用点读回两个字段)。这不是自我否定——改的是**路由这一环落地那一次的管路**,从此以后第二个、第三个业务 filter 加进来仍然一行不改。这两件事必须分开说,不然下次有人拿"ADR-18 也改了主路径"给我开新的口子。
- **为什么字段进 `RequestInfo` 而不是新开一个返回结构体**:交接段和 1.16 都把它写成"`RequestInfo` 的'目标上游'字段"。新开一个 `RequestDecision` 出参同样能满足"和第一个读者同批进来",但它让链有两个通信通道(返回值 + 出参),而这两个通道在 S4 会开始互相说不同的话(`kStop` 了却带着一个 target)。一个栈上临时对象、两个字段、一条 `run()` 调用,是我能找到的最少真相的形状。这个对象本来就是每次调用现造的(`reactor.cc:1024`),不存在生命周期风险。
- **为什么分桶而不是"每 worker 一个 shared_ptr map<target, vector>"**:桶的下标空间在配置期就定死了(目标表长度),`vector<vector<…>>` 不需要哈希、不分配第二份索引、`pool_idle_count()` 求和是连续内存。map 的灵活性在这里买不到任何东西:目标 id 是一个 `uint16_t`,而目标表不会在运行期变长(变长是 S5 热重载的话题,那时按 ADR-10 换成"整张表换一根指针")。
- **为什么不预先给 `Connection` 加"目标"字符串**:池要按目标分桶,回收时必须能从上游连接本身认出它属于哪一桶(`close_connection` 的级联只给我一条 `Connection`)。存的是一个 `uint16_t` 下标,不是地址+端口两份字符串。

## 我放弃什么

- **不做 shared 池、不做跨 worker 借热连接**。已裁第 1 条,ADR-15 的原由(保住 ADR-14 + 与 nginx 同形)一条没变。代价照记:负载不均时不能跨 worker 复用,而路由让不均更容易出现(某条前缀的路由可能天然集中)。这条要在 S3-03/S3-06 的读数里露出来,不许读成"池没问题"。
- **本 ADR 不做负载均衡策略、不做节点表配置格式、不做健康检查**。路由 filter 在这里只做"这条请求属于哪条路由",一条路由对应一个目标;一条路由对应多个后端、按请求在三策略里选,是 S3-02 的 ADR-19。**边界的形式证据是代码里没有这些类型**,不是我说我没做。
- **路由表在 S3-01 只在进程内构造(测试与 reactor 装配),配置文件格式与 S3-02 的节点表同批。** 理由不是拖延:节点表和路由表是同一份文件的两个 section,拆成两个任务各写一半解析器,就有了两份会分叉的配置真相。已裁第 2 条说的是"01～03 不依赖 MySQL",不是"01 就得有文件格式"。这条边界我在 S3-01 的收尾文档里明写,不藏在代码注释里。
- **不给路由单独新增产品侧统计计数**。"落到哪个后端"这件事的可见性由**上游夹具自报**(`tests/test_upstream.h` 加 `connections_accepted()`;真进程侧沿用 B-007 那套 `accepted_by_addr=`),网关自报的 `upstream_opened` 保持单一口径。等 S3-03 的摘除/误摘率真需要"每目标请求数"时再按 ADR 引入,不为"日志看起来更丰富"预先造一个没人核对的分母(那条教训的原型是 S2-06 的 `measurable=0` 两格)。
- **不在这一环做 `Host` 维度路由**。契约 S3 写的是前缀/正则,而 `Host` 匹配要引入"同一前缀不同虚拟主机"的优先级语义——那是第二套排序键,和链不排 `priority` 同一个理由,现在不开。

## 后果与约束

- **ADR-14 的接触面仍然只有裸 fd**。桶是 worker 私有的 `vector`,目标表是配置期定长的,`upstream_target_` 只在 owner 线程读写。可证伪形式:`tsan` preset 全套零 data race(S3 门禁硬条件),而它**必须能红**——S2 的纪律是"摘掉锁才叫验证过",这一条的对应做法是把某个桶的借用改成跨 worker 借用,TSan 应当报 race(具体反证形式在 S3-01 的收尾记录里)。
- **`sizeof(Connection)` 不许因为这一环变大**。目标下标 `uint16_t` 落在 `armed_events_` + `read_stopped_at_line_` 之后那三字节对齐空位里(`net/connection.h:320-323` 的注释当年就为多一个布尔值留过这个位置)。**这条不是审美**:B-011 的构成表把 `Connection`×2 = 1,056 B 逐条钉进了 17,861 B/对,涨 8 字节就是每 100k 对多 1.6 MiB,SLO #2 的账要重写。收尾时用例里那条 sizeof 断言要跟着核对。
- **`pool_idle_count()` 的口径变了,并要就地标注**(已裁第 1 条点名):从"本 worker 空闲热上游数"变成"**按目标分桶后本 worker 各桶之和**"。数字的含义在单目标配置下与过去完全一致(只有一个桶在用),所以历史读数不作废;但任何"池有多满"的比较必须写清是哪几个桶。SLO/BENCHMARK 里引用它的地方加一句标注,不改历史数字。
- **`upstream_reusable()` 现在是目标切换的守卫,而不只是回收的守卫**。同一个判据两处用是故意的:如果"能换目标"和"能进池"是两个条件,迟早出现"进了池却换不了目标"那种没人能解释的状态。
- **压住请求这件事需要一次真实时序验证,单测必须能红**。用例形状:两条路由(两个 `TestUpstream`,靠响应体长度区分,沿用 S2_06a 那三条的做法)→ 一条下游先发 `/a` 再在**同一次可读里** pipeline 一条 `/b` → 断言 `/a` 的响应先回来、`/b` 的响应后回来、两个夹具各收到一条请求、`upstream_opened == 2`(不是 1、也不是 4)。摘掉 `kComplete` 那次重驱动 → 第三条 `/b` 的响应等不到、用例红。**这条用例是本 ADR 那条代价的收据**,没有它我不声称压住是安全的。
- **成本这一格照规矩四办,不口头保证"没有退化"**。空链 vs 路由链,同一份 binary、同负载 100 并发闭环(B-009 实测这一档观察者占单核 0.39,仪器不饱和),每请求 p50/p99/p999 与每请求 `epoll_ctl` 逐项对照,**≥2 轮、报极差**;判据是增量落在本档 128 条用例的散布带里,并对着 B-008 的每请求 ≈8.7 µs 净赤字报。抬高就在极差外照记——**照记不是失败,把它读成"路由本来就该免费"才是**。
- **隧道仍然不经过链**(ADR-09/1.16),所以路由天然管不到已经 101 的流量;一条下游进了隧道,它的目标就定在握手那一条请求上。这条边界与 S4 限流管不到隧道是同一族,原样登记在 1.16 的边界段旁边。
- **回源耗尽时网关仍然不自产错误响应**。本 ADR 加了 404 这一格,它是"没有路由"的表态,不是"上游连不上"的表态——S4 那一格没被顺手填,别把两者读成一回事(B-006 结果二那句仍然成立)。
