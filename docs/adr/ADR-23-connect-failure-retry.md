# ADR-23 · connect 失败的重试：只换成员、只一次、只在那一刻确定没到上游（S4-06）

- 状态：已采纳（S4-06 落地）
- 日期：2026-11-02
- 相关：ADR-22（**本 ADR 的挂接点就是它的 connect 失败分支**——第四节那条"不做重试"欠的就是这一节）、ADR-12 追加二（半开门与安全阀：重试不许绕过它，第二节第 2 条"放行的那条必须真的落到它"是我这里"落点要钉死"的同族论证）、ADR-19（追加第二条＝判据要配对；追加第三条＝"允许被选中"与"接得到流量"是两件事）、ADR-16（请求/响应配对与 FIFO：搬运为什么不破坏它）、ADR-17（候选 A：`--upstream` 列表 + `i mod E` 是**容量**手段不是候选集，所以那条路径不重试）、ADR-18（链的写回通道；`RequestInfo` 多一个可写字段）、ADR-15（池按目标分桶：重放借来的那条为什么出向一定空）、S1-06（表态资格）、契约 3.1 / TASKS「## S4」S4-06 行 + 已裁第二条

## 这一节在裁什么

已裁第二条把边界钉死了：**只对 connect 失败、在另一个候选成员上、重试一次；5xx 与超时不重试**。
这一节把那句话摊成可实现的语义，要回答的是起草时躲不掉的五个问题：

1. "确定没到上游"在代码里到底是哪一刻（两个揭晓点，一个能当场重试、一个不能）；
2. 异步那一支的字节在哪儿、搬运会不会破坏 ADR-16 的配对模型；
3. "另一个候选成员"由谁在什么时候算——重选要读候选集，而候选集住在 filter 里；
4. 重试与摘除/半开怎么互动（资格、失败判据、安全阀）；
5. 判据形状。第 4 问的答案不能只有上界：**"放大倍数 ≤ 2"这条上界，一个从不重试的实现同样满足**
   （ADR-12 追加二第八节、ADR-19 追加第二条教过的同一件事），所以每条上界旁边必须有一条点名落点的下界。

编号说明：这一节原定编号 22，ADR-22 起草时把它顺延给重试（编号按起草顺序排，不预支），本节就是那个 23。

## 一、定义域：只有"握手没成"这一个失败可以重试

判据不是"哪种错误码好看"，是**这一次尝试有没有可能已经把请求交付给上游应用**：

| 失败形态 | 请求字节到过上游应用吗 | 重试 |
|---|---|---|
| connect 同步失败（`start_connect` 当场 `kFailed`） | **不可能**——socket 从没连上 | ✓ |
| connect 异步失败（`kConnecting` 期间 `SO_ERROR != 0`） | **不可能**——EPOLLOUT 只是握手结果的通知，握手没成时一个字节都写不出去 | ✓ |
| 响应头之前 EOF / 头坏 / 截断 | **可能**——握手成了，字节早就发出去了，后端可能已执行 | ✗ |
| 上游回 5xx | **一定**——重发就是一次重复执行，写操作直接放大 | ✗（已裁第二条原文） |
| 三类超时（含**连接超时**） | 不确定，而且客户端已经等满一条限期 | ✗ |

**connect 超时为什么也不重试**（这一格最容易读成"它也是 connect 失败"，所以单独写）：它在安全意义上
确实和 `SO_ERROR` 同族（握手没成 = 没交付），我仍然排除它，两个理由都在账上——
① 撞这条线意味着到那一台的**网络路径在退化**（SYN 黑洞、中间设备丢包），立刻换一台再走一遍同一条
退化路径是在给已经慢的网络加负载，这与 ADR-12 那句"不自我放大"是同一条立场；
② 客户端此刻已经付完一整条 `--upstream-connect-timeout-ms`（缺省 3000 ms），SLO #1 那条 p99 尾延迟
的账不能再挂一次握手。代价照记：黑洞型故障（连而不回、SYN 被丢）下这一格不恢复服务，客户端拿 504——
那是"宁可快速失败也不要拖长尾"的取舍，不是我漏了一格。

**上游半开（连上不回字节，S3-05 §12 类 3 那一格）不在定义域内**：它握手成功，属于表里第三行，
管它的是 ADR-21 的响应头限期（→ 504），不是重试。ADR-12 追加二第七节那条命名边界在这里同样成立，
别把「上游半开」读成「熔断半开态的重试」。

**只有"回源失败"这一族里的 connect 分支参与重试**：本地容量分支（`max_connections` 命中、
`epoll_ctl` 注册失败）**不重试**——那是我自己的资源问题，换一台后端不会多出一个 fd，
重试只会把同一格记两次。它照旧走 ADR-22 的 503 + `gateway_replies_over_capacity`。

## 二、预算 = 1 是结构性事实，不是计数器

我不实现"重试次数"这个状态。做法是：**备选只在发起握手那一刻登记一次，而重放那一次不再登记备选**——
新那条上游的备选字段是 `kNoUpstreamTarget`，所以它失败时无处可去，直接走 ADR-22 的自产表态。
"每条请求最多两次尝试"因此是**代码里只有一条赋值**的结果，而不是一处需要有人记得去夹的逻辑。

理由不是省事，是 ADR-19 追加第二条那一类失效：预算若写成 `if (retries < kBudget)`，
"忘了 ++"和"忘了判"都能让实现仍然满足 `retries ≤ N`，而上界照样绿。
阳性验证里我会把"重放时不清空备选"这一条退回（=级联重试）——它必须让**上界**用例红。

**预算挂在请求上，不是挂在连接上**：一条 `kConnecting` 的上游可能排着 pipeline 里 N 条请求（ADR-16），
握手失败时这 N 条**一起**重放，计 `upstream_retries += N`。所以放大上界是**每条客户端请求 ≤ 2 次尝试**，
不是"每条配对连接 ≤ 2 次"。这一格如果数错，方向是少报，所以下面第八节的等式把它钉成可断言。

## 三、挂接点：ADR-22 第二节的两个揭晓点，先重试、仍失败才表态

| 揭晓点 | 现在做什么 | 重试插在哪儿 |
|---|---|---|
| `ensure_upstream` 的 `start_connect` 同步 `kFailed` | `upstream_connect_failed` +1 → 读 `is_ejected` 归类 → `note_health_failure` → 返回 `UpstreamPick{nullptr, 502/503, cause}` | **在返回之前**：`forward_request` 拿到 `cause == kConnectFailed` 且带有效备选 → 用备选目标再调一次 `ensure_upstream`。请求字节此刻**还在下游入向缓冲里**（`finish_request` 没跑），所以第二次调用就是首趟那条路径，`close_after`/upgrade 意图的落点一字不动 |
| `on_upstream_event` 的 `kConnecting` + `SO_ERROR != 0` | `upstream_connect_failed` +1 → 读归类 → `note_health_failure` → 找到配对下游就 `fail_pair_with_reply(502/503)` | **在表态之前**：把这条连接里**从未发出**的字节整体搬给备选成员（第四节）。搬不成（无备选/不合格/新上游拿不到）才回到原来那句表态 |

顺序纪律（与 ADR-22 同一条，不改）：**归属读在 `note_health_failure` 之前**——重试用掉的那次失败
自己也可能把目标推进摘除，反过来读会把普通 connect 失败误归成 `all_ejected`（口径⑫）。

## 四、异步那一支：搬运的是"一个字节都没出去过的出向缓冲"

**为什么安全**：`flush_outbound` 只在握手揭晓成功之后才可能写这条 fd（`desired_events` 在
`kConnecting` 期挂 EPOLLOUT 是**等结果**，不是发数据；见 `on_upstream_event` 那段 SO_ERROR 先行的注释）。
所以握手失败那一刻，这条上游的出向缓冲里的字节 = 网关收下但**从未交付给任何后端**的字节。
搬运它们不是"重发一个可能被执行过的请求"，是"第一次真的把它发出去"。

**为什么 ADR-16 的配对模型不坏**：搬的是**整块**出向缓冲，字节顺序原样（`queue_bytes` 一次整块追加），
不拆不重排。响应仍然按 FIFO 回来，因为发出去的顺序就是客户端写进来的顺序。

**落地形状（顺序是有理由的，逐条不能换）**：

1. **交出字节**：把 A 的出向缓冲整体摘出来（`Connection::take_outbound()`，一个"我即将废弃、这些字节
   从未发出"的转移接口）。不是拷贝到临时缓冲：那块 Buffer 本来就在堆上，换的是**所有权**，不多一次分配。
2. **解链**：两侧 `peer_fd` 置无效 + `note_upstream_unpaired`。必须先解链，因为
   `ensure_upstream` 的"在干净边界才换目标"那条判据（ADR-18 第五节）会因为在飞 > 0 而把旧目标那条
   原样还给我——那是给"路由改主意"设计的保护，用在重试上是错的（重试不是换目标，是换**配对**）。
3. **六步关闭 A**（`kDiscardOutbound`；出向已经空了，所以这一步不会丢任何字节）。
   关掉再取新上游，是为了不让一条正在废弃的连接虚占一格 `max_connections`，
   把重试读成 `over_capacity`——那是把后端的毛病记成我的毛病。
4. **取新上游**：`ensure_upstream(downstream, 备选)`（备选字段此时不再往下传，见第二节）。
   借来的或新建的都行。
5. **排字节 + 过账**：`queue_bytes` 那批字节 → 逐条 `note_request_forwarded()`（**在飞计数必须跟着字节走**：
   少这一步，响应完结时的 `note_response_completed` 会把零夹住，而"在飞归零才关"的判据
   ——包括 `Connection: close` 的兑现时机和排水——全部失真）；A 若带 `close_after_response` 意图，
   转给 B（不转的话一次性配对会被归还进池，`Connection: close` 的后端变成 keep-alive 复用——
   这是语义变更不是性能优化）；`close_headers_honored` 已经计过，不重复计。
   101/upgrade 那半不需要动：意图存在**下游**侧（`mark_upgrade_request`），搬运不碰下游。
6. **限期换格**：B 是新建的 `kConnecting` → `ensure_upstream` 自己登记连接超时；B 是借来的热连接
   （`kOpen`）→ 登记响应头超时。这条与 `forward_request` 里那句是同一件事，**抽成一个公共函数**，
   不留两份迟早漂移的抄本。
7. **计数**：`upstream_retries += 搬走的请求条数`。

**装不下怎么办（照记，不假装它不存在）**：`Connection::queue_bytes` 的整块判据是
`readable_bytes() + len > high_water_mark`（缺省 256 KiB），**不是** `max_capacity`——所以装得下装不下
看的是水位线。A 的出向本来就受同一条线夹着（`forward_request` 那次 `queue_bytes` 用的就是同一句判据），
而 B 无论是借来的（`upstream_reusable` 要求出向为空）还是新建的，那一刻出向都是空的、两侧共用同一份
`Buffer::Config` → **一定装得下**。剩下 `queue_bytes` 返回 false 那一格是端到端不可控注入的边角，
与 ADR-22 第五节那条"`epoll_ctl` 注册失败没有可控注入手段"同形：**不许丢字节**——退回 ADR-22 的表态路径
（503 + `over_capacity`：那时确实是本地内存装不下，归因诚实），客户端拿到一条完整 503 而不是挂死。
代价上限就是那条水位线：一次重放最多搬 256 KiB（B 的缓冲随之长到那个尺度），不是无界的。

**同一批字节共用一个备选**：备选是在**发起握手那一刻**定下的（配对级），而 pipeline 里后续请求
可能是在候选集变了之后排进来的。后果是重放落到"当初那个备选"而不是"每条请求自己那一刻的下一个"。
我接受这个：重试验合格读的是**搬运那一刻**的资格（第五节），而它要证明的命题是"换一台再试一次"，
不是"每台都按各自的候选序列"。写得这么直白是因为反过来说成后者就是撒谎。

## 五、落点：下一个候选成员，由均衡那一环在选中时算好

**为什么不在失败那一刻重选**：重选要读候选集，候选集在 `LoadBalanceFilter` 手里（它读 `HealthTable::admit`、
它知道组、它有本 worker 的游标）。两个选择：
① 把候选集那套东西搬进 `Reactor`（一份会漂移的抄本 + 让 net 层开始懂路由）；
② **选中时顺手记下"下一个是谁"**，失败那一刻只读一个数。我选 ②，理由是 S3-01 已经认过一次的那句话：
**存一个下标不等于做一次决策**（`Connection::upstream_target_` 的注释就是这条，见 1.23/1.25）。

**怎么算**：`LoadBalanceFilter` 在 `picked` 定下之后，取**候选集里被选者之后的那一位**
（`candidates[(idx + 1) % n]`，n ≥ 2；n == 1 → `kNoUpstreamTarget`）。三条性质是刻意的：

- **不调 `advance_rr`**：备选不是第二次选择，游标一步都不该动。动了就是每条请求推进两次游标，
  轮询分布与 B-013 那张成本对照全部变形——而这件事**看起来完全在正常工作**（口径⑦那一族的形状）。
- **一致哈希也用表顺序，不引入"环上第二个点"**：那需要第二种选择算法（环上继续顺时针走还要处理
  同一个点的多个 vnode）。重试要的是"任何另一台活着的人"，不是"哈希意义上的第二优选"。
  代价：这一条请求打破了 `key → 成员` 的亲和（落到另一台可能是冷缓存）。这是故障转移的固有代价，
  写清楚，不在实现里偷偷保留亲和。
- **半开被钉的那一条没有备选**：`kProbeSlot` 时候选集只有一个成员 → n == 1 → 不重试。
  这是对的而不是漏洞：那条请求是**探测本身**，换一台再试等于用别人的答案替它结案，
  ADR-12 追加二第二节第 3 条那套证据链就断了。

**搬运需要存一个字段**：`Connection` 多一个 `retry_target_`（`uint16_t`，`kNoUpstreamTarget` = 不重试）。
它**必须落在既有的对齐空位里**（`in_flight_requests_` 之后那两个 bool 后面还有 6 字节 padding），
由 `static_assert(sizeof(Connection) == 528)` 和一条命名用例盯着（S3-01 加 `upstream_target_` 时
就是同一道门，见 `SizesDoNotGrowForTheTargetLabel`）。**为什么这条不是洁癖**：B-011 的构成表把
`Connection`×2 = 1,056 B 逐条钉进 17,861 B/对，涨 8 字节就是 100k 对多 1.6 MiB，那一格账要整张重写。
装不下的话退路是 `Reactor` 侧的 fd→下标表（先例 `upstream_deadlines_`，ADR-21 第一节规则 2），
代价多一次哈希插入 + 一条生命周期的配对纪律——**这个取舍由断言裁决，不由我口头保证**。

**资格：只落到 `kAllow` 的成员**。搬运那一刻纯读一次健康状态（`HealthTable::retry_eligible(target, now)`，
const、**不消费半开名额、不做读侧迁移 CAS**——它是判卷不是判据）：

| 那一刻的备选 | 合格吗 | 为什么 |
|---|---|---|
| 健康（`state_ms == 0`） | ✓ | — |
| 摘除中 | ✗ | 重试绕过摘除 = ADR-12 的摘除与误摘率口径被打通，"候选集是摘除与均衡唯一交点"（1.25 第三节）不再成立 |
| 半开（有名额或没名额） | ✗ | 名额是恢复机的东西（`half_open_admitted/denied` 那两格账只由 `admit` 一处决定）；重放一条业务请求去占名额，等于让"恢复"多一个没人数的入口 |
| 摘除已到期、还没被 `admit`/`sweep` 推进 | 装配熔断时 ✗；未装配时 ✓ | 熔断下那一台已经归半开门管（第五节那条"读侧顺手迁移"的规矩在 `admit` 那儿兑现，不在我这儿抄一遍）；未装配熔断时到期**就是**健康（1.25 的读侧口径原样） |
| `health` 段不存在 | 全员 ✓ | 与 `candidates_for` 的 `health_ == nullptr → 全员候选` 同形：没有摘除概念，就没有可绕过的东西 |

不合格 → **不重试**，直接回到 ADR-22 的表态。这不浪费那个备选：同一台下一拍被 `admit` 推进之后
自然重新可 Retry，而我不会为了"多救一条请求"去碰那台机器的状态。

**全员被摘的回退那一格逐字节不变**：`candidates_for` 回退全员时，所有成员都不合格 → 不重试 →
`gateway_replies_all_ejected` 的 503 原样。ADR-22 第二节"入口不拒绝、回退保留"的立场不需要为本任务改一个字。

**没有候选集的路径不重试**（已裁，2026-11-02）：不装 `--config`、只有 `--upstream` 列表 +
worker i → 第 `i mod E` 个端点那条（ADR-17 候选 A）**不参与重试**。理由：那条映射是**容量**手段
（把 ephemeral 端口预算摊开），不是"一组可互换的后端"；在它上面换一台等于回头翻案 ADR-17 的
"不做故障转移"，并把 B-007 的 100k 容量口径与 §13 那 71,769 条 502 的重跑全部作废。
**收益是这些档一条不作废**，代价是最原始的部署形态没有故障转移——那本来就是候选 A 的边界①。

## 六、与摘除/熔断的互动：重试失败计入失败判据

- **首试那次失败照旧记账**（`upstream_connect_failed` + `note_health_failure(A)`）——重试不抹掉任何证据，
  摘除耗时与误摘率的读数口径不因本任务改变（B-014 的 202 ms、§12 的 273/89 ms 不作废）。
- **重放那次失败也记账**（`note_health_failure(B)`，走同一句代码，不是新采集点）。
  已裁那条"重试失败计入失败判据"就落在这里。
- **后果读得见，写出来**：两台都不通时，**一条客户端请求注入 2 个失败样本**而不是 1 个
  → 连续失败判据到 `max_fails` 更快、错误率窗口的分母也翻倍。上界就是预算本身：
  **失败样本 ≤ 请求数 × (1 + 预算)**。我不为这一格加"重试失败不计摘除"的例外——那会让重试
  变成一个不付账的第二次尝试，而 ADR-12 的整套立场是"付账"。
- **一次表态仍然只有一条响应**：重试用掉之后，无论第二台成不成功，客户端最多拿到一条自产响应
  （`gateway_replies_sent` 每条请求一次，三格互斥可断言这条一字不动）。
- **安全阀不参与重试决策**：`retry_eligible` 问的是这台成员自己的状态，不问"还能不能再摘一台"。
  阀挡的是摘除，不是发送。
- **半开的阀位账（`health_ejected_now` = 摘除 + 半开）一字不动**，因为重试根本不去碰半开。
  已裁那条"恢复出口两条并存"**本任务不改**（ADR-12 追加二第七节 → S4-07）。

## 七、配置面：不加开关、不加字段、预算不配置化

**零配置项。**三条理由，形状都与 ADR-12 追加二第一节那条"分桶数不做配置项"同族：

1. **预算 = 1 是已裁第二条的原文**，做成配置项等于把一条已裁的裁定改成一个可以投票的东西；
2. 多一个旋钮只是多一类配置错误，而这一格的错误形态不是"启动失败"而是"放大倍数变了"——
   它只有在压测里才看得见，那正是本项目最忌讳的"安静的答案"；
3. 重试没有"关掉它"的真实需求：它只在候选集 ≥ 2 且**首试已经失败**时才动，
   那本来就是一个已经坏掉的路径。

**`circuit`/`health`/`rate_limit` 段都不参与**（资格判据读的是已有状态，不新增开关）。
**`--config` 路径的既有语义变化**：装了一条 ≥2 成员的组，connect 失败就不再直接表态。
这是本任务的功能，不是附带清洁；不装 `--config` 的路径逐字节不变（第五节）。
`RequestInfo` 多一个可写字段 `retry_target` → `filter/chain.h` 那句"只许写 `upstream_target`/`reject_status`
那两个数字"要跟着扩成三个，这是文档层的契约面，不改代码注释就等于留一份说谎的注释。

## 八、观测口径与判据形状（成对写满）

新格两把，**退出账一行一个键**（口径⑭(b)）：

| 键 | 是什么 |
|---|---|
| `upstream_retries` | 因首试 connect 失败而被重放到**另一个成员**的请求条数（按请求计，不是按连接计） |
| `gateway_replies_after_retry` | 自产 502/503 里"此前已经换成员试过"的那部分（`重试也没救活` 的证据） |

**放大倍数的可测形式**（验收句"客户端请求数 : 上游请求数 ≤ 预算上界"摊成三条能断的式子）：

| 判据 | 上界那一半 | "确实发生过"那一半 |
|---|---|---|
| **预算** | `upstream_retries ≤ 客户端请求数` → 网关尝试数 = 请求数 + retries ≤ 2 × 请求数 | `upstream_retries ≥ 1`（否则"从不重试"的实现两条都过——ADR-12 第八节同一形状） |
| **不复制**（防放大真正的那格） | **后端实收请求总数 ≤ 客户端请求数**（`Σ 各成员自报 served ≤ N`）。一次 connect 失败不产生后端可见请求，所以重试**本不该**让这个数增长 | 重试那条**被另一台服务了**：那台的自报数随重放增长，且客户端拿到 200 而不是 502 |
| **仍失败才表态** | `gateway_replies_after_retry ≤ gateway_replies_connect_failed + gateway_replies_all_ejected`（重试用掉才表态，一次表态仍只有一条） | 两台全死那一臂 `gateway_replies_after_retry ≥ 1` |

**为什么"不复制"那一半要用后端的自报数**：网关侧的 `upstream_retries` 只说"我自己以为重试了几次"，
而放大这件事的主语是**后端执行了几次**。S4-05 那条等式（`后端自报 6 == 摘除前 4 + 门放行 2`，
仪器与被测方互背书）在这里复用：只有两边都数一遍，"从不重试"和"重复执行"才都跑不掉。

**探活不参与重试**（仪器不叠仪器）：探活连接机（`start_probe`）一个字节都不走这条路。

**`bytes_down_to_upstream` 的口径要说清**：它是"排进上游出向缓冲的字节累计"，重放会把同一批字节
**第二次**计入。我已 grep 核对过现有按它做相等断言的用例——全部在单目标/无候选集的形状里，
不受本任务影响；但任何后来拿它当"载荷字节数"对账的断言都必须先读这一句。

## 九、我放弃什么

- **退避（backoff）**：立即重试。两条理由：① 退避要把请求挂在网关里等一个定时器，而 ADR-21 的立场是
  "拿不到就表态，等 = 把失败拖成超时"；② connect 失败是**确定性**答案（RST 已到手），
  对确定性答案退避只是把延迟摊给客户端。代价照记：全组 connect refused 时每请求两次 SYN，
  一台重启中的后端会看到 2 倍连接尝试——这是摘除判据付账的地方（第六节）。
- **重试排队 / 多次换成员 / 跨请求共享预算**：预算 1 就是 1，不排队不重试第二次。
- **把超时纳入重试**：第一节那条，含 connect 超时。
- **改写或伪造响应**：重试用掉之后仍然只回一条自产 502/503，S1-06 的表态资格规则一字不动。
- **给重试加"这一条请求重试过了"的下游可见标记**（比如 `x-gateway-retried` 头）：那需要改写响应，
  而 ADR-09/ADR-22 的立场是不碰语义之外的字节。观测归计数器。
- **恢复出口唯一化**（ADR-12 追加二第七节）：**本任务不许顺手改**，归 S4-07 按摘除/恢复耗时重量再裁。

## 十、代价与边界（照记）

1. **一台死成员在"另一台活着"的配置下不再产生 502**——客户端看到的是成功 + 一次握手的时间。
   所以 S4-02 §13 那种"71,769 条 502"的结账形状只在 E=1（无候选集）那一臂仍然逐字成立；
   多成员配置里同一格的读数会变成 502 更少 + `upstream_retries` 非零。这是功能生效，不是回归。
2. **重放多花一次握手与一条上游连接**：`upstream_opened` 增长，新那条按 ADR-15 归进它自己那个桶。
   fd 预算的瞬时占用靠第四节第 3 步（先关再取）不收窄，但一次批量 connect 失败仍会同时多开若干条——
   上界是"在飞请求数"，不是"客户端数 × 2"（同一台配对连接的 N 条 pipeline 共用一次握手）。
3. **打破一次 key→成员亲和**（一致哈希组）：第五节写明了，不在实现里偷偷保留。
4. **失败样本翻倍注入**（第六节）：判据更凶，方向是 fail-closed，我接受。
5. **备选是配对级、不是请求级**：第四节末尾那条。
6. **`queue_bytes` 装不下那一格端到端不可断言**：第四节末尾，与 ADR-22 那条 `epoll_ctl` 同形。
7. **`retry_eligible` 是纯读，所以它可能读到"刚到期还没被推进"的备选并放弃一次重试机会**。
   方向是少救一条请求，不是多打一台后端。
8. **本任务不改 `deploy/gateway.json`**（它被 ctest 读、且刻意不带 health/circuit，S4-05 那条理由仍然成立），
   `deploy/gateway-circuit.json` 也不改——它有两台成员，重试在其中一台下线时会生效，
   这是冒烟阶段可以读到的正常行为，示例配置不需要为此加注解字段（没有配置项可注）。

## 十一、验收的可执行形状

**ctest**（进程内真 socket，两台 `TestUpstream` + 一条 ≥2 成员的组）：

- connect 失败被另一台救回：`upstream_retries == 1`、那台自报 +1、客户端拿 200、`gateway_replies_sent == 0`
  （同步支与异步支**各一条用例**，并像 S4-02 那样带环境预探针说明这一支为什么是这一支；
  两支都跑不到的那一格写 Skipped＝不判，不写成通过）。
- 两台都不通：`retries == 请求数`、`after_retry == 请求数`、表态条数 == 请求数（一次表态仍只有一条）。
- pipeline 3 条一起重放：`retries == 3`（预算按请求不是按连接那格的收据）。
- 5xx 不重试、超时不重试（含 connect 超时）：`retries == 0` 且 `gateway_replies_*`/`upstream_*_timeout`
  归因不变——**这两条是"不复制"的上界，必须能在退化实现下变红**。
- 全员被摘：`retries == 0`、503 与 `AllEjectedLastLineReplies503` 的形状一字不动。
- 半开被钉的那条不被重试（候选集 1 个成员），且重放**不消费**半开名额
  （`half_open_admitted` 不因重试增长）。
- 备选落在摘除中的成员时不重试（资格判据那条，纯读、不改状态）。
- 一次连接不重试第二次（级联）：`retries ≤ 请求数` 那条结构保证的显式用例。
- 无 `--config` / 单成员组：`retries == 0`（第五节"不重试"那两条路径）。
- `sizeof(Connection) == 528`（第五节那条取舍由断言裁决）。

**冒烟** `scripts/smoke-s4-06.sh`（真进程，**不需要 Docker**，形状照 `smoke-s4-05.sh`）：
一臂一台死一台活（放大上界 + 落点下界 + 后端实收 ≤ 客户端请求数三条同臂对上）、
一臂两台全死（`after_retry` 与"一次表态仍只有一条"）、一臂全活（`retries == 0`，零误重）。
毫秒按 `date +%s%N | cut -c1-13` 取，退出账一行一个键（口径⑮那条本机事实仍然生效）。

**阳性验证**（每条都必须真打红，"看起来在测、其实测的是别的东西"不算）：
① 从不重试 → 下界红；② 重试用掉之后还留着备选（级联）→ 上界红；③ 5xx 也重试 →
**后端实收 > 客户端请求数**那条上界红（唯一能抓"复制"的尺）；④ 备选算成"同一台" →
落点下界红；⑤ 不做资格检查 → 摘除/半开那两格账红；⑥ 重放不搬在飞计数 → 配对关不掉/
`Connection: close` 变 keep-alive 红；⑦ 重试推进 `advance_rr` → 轮询分布红。

**S3-05 §12 那一格的重测（含对交接指令的一处更正，照记不藏）**：交接段点名"重试落地后要重测
『在途请求挂在死成员上被 5s 排空』那一格"。那一格的实测成分是 §12 类 3/4a（**连上不回字节**与**慢**），
它们都不是 connect 失败、不在本任务定义域内（第一节表里第三行）；而且"被 5s 排空"这个形状自 S4-01
起已由响应头限期管住（→ 504），不归重试。真正被本任务改变的是 **类 1（connect refused）**：
今天它当场 502，落地后它换一台并被服务。所以我按这个范围重测并报告——
**类 1 的"客户端不再见到该成员"的时刻**（重试是否延长它）与**类 3/4a 的读数不变**（证明我没有顺手改超时那一族）。
如果重测发现类 3/4a 也动了，那说明实现越界，我回来改实现而不是改文档。
