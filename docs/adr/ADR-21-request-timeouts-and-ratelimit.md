# ADR-21 · 请求级超时与限流（S4-01 / S4-03）

- 状态：已采纳（超时半边随 S4-01 落地；限流半边随 S4-03 落地）
- 日期：2026-10-30
- 相关：ADR-05（Redis 分布式计数——S4-04 用本 ADR 定的键与令牌语义）、ADR-12（安全阀——S4-05 的错误率判据走 S3-03 摘除机构，本 ADR 的超时是其输入之一）、ADR-18（链写回通道）、ADR-19（策略/进程形态分家）、ADR-11（链顺序 = 配置顺序）、S1-06（表态资格规则）、S2-05（排水与超时的对齐约定）、契约 3.1 / TASKS「## S4」待裁三条

## 一、请求级超时的三格（S4-01）

**三格都是"进程形态"，进命令行不进配置文件**（ADR-19 的切分原样适用）。已裁：不设 body 总时长——idle 管住"死了的流"，总时长管不住"活着的流"。

| 格 | 参数 | 缺省 | 触发条件 | 表态 |
|---|---|---|---|---|
| 连接超时 | `--upstream-connect-timeout-ms` | 3000 | 上游处于 `kConnecting` 超过限期 | 配对下游收**自产 504**（头前，自产资格在）；该上游按六步关闭 |
| 响应头超时 | `--upstream-head-timeout-ms` | 10000 | 请求字节排进上游后，限期未见**最终响应头**（1xx 不重置计时——它不是表态） | 同上：自产 504 + 六步关闭 |
| body 空闲超时 | `--upstream-body-idle-timeout-ms` | 30000 | 响应中途（头已排给下游）入向**无字节流动**超过限期 | **无自产资格**（头已出去，S1-06 的表态资格规则沿用）：只能以连接终止表态——六步关闭 + 计数 `upstream_body_idle_timeout`，客户端看到断流自己判截断 |

三条语义规则写死：

1. **超时是健康判据的输入**：三类撞线全部走 S3-03 的 `note_health_failure`（被动记账点从四个变七个）——"慢"超过容忍线就是摘除判据意义上的失败，与已裁的"慢过 probe_timeout 判摘"同一条逻辑线。
2. **定时器在 owner worker 的循环 tick 里扫**（200ms 粒度，与排水扫描同一家）：deadline 记在 **Reactor 侧的 `unordered_map<int fd, int64>`**，不进 `Connection`——`sizeof(Connection)` 的 `static_assert`（528）是 B-011 构成表的地基，为计时器加字段要过 ADR。map 的生命周期跟配对：请求发出时登记、响应头到达 / 配对解除时移除。**零业务流量时 map 为空，扫描是 O(1)**——"超时器不产生任何副作用"的验收由这条结构保证。
3. **排水对齐在启动时校验**：`--drain-timeout-ms ≥ --upstream-head-timeout-ms`，违反 = 退出码 2——头都等不到的排水窗口没有意义（S2-05 埋的约定在此兑现；body idle 不参与校验：它是对活流的耐心，不是对排水的预算）。

## 二、限流的四条语义（S4-03）

1. **令牌桶参数与键**：配置文件 `rate_limit` 段——`{ "rate": 每秒令牌数, "burst": 桶容量, "key": "path" | "ip" | "header:<Name>" }`（缺省 key = `path`；按用户/IP 的维限不做，键口径可配是唯一让步）。`rate_limit` 段不存在 = 整个限流不装配（与 `health` 段同一条形状）。
2. **状态是共享原子，不是 per-worker**：与均衡状态（per-worker，ADR-19）**刻意相反**——限流的语义是"这个网关每秒最多放行 N 条"，per-worker 桶会把限额放大 N 倍，那不是限流是装饰。令牌数与上次补货时刻各一个原子（CAS 补货），先例 HealthTable/NodesPublisher；拒绝路径本来就是热点，CAS 竞争的成本只在被限的流量上。TSan 面不变（全原子）。
3. **链位置：限流在前、路由在中、均衡在后**（链顺序 = 配置顺序，ADR-11）。限流表态 = `kStop + reject_status=429`，走 `gateway_error_reply` 新加的 429 格——**写回通道零扩展**（ADR-18 的通道本来就为此留的）。被限的请求不回源（`upstream_opened` 不动，与 404 同一条性质）。
4. **限流计数不进业务计数**：`requests_parsed` 仍数"解析成功的请求"，429 是 parsed 之后、转发之前的表态（`gateway_replies_sent` 照记）——SLO 分母不被仪器污染的立场与探活同一条。

**Redis 分布式计数（S4-04）在本 ADR 之上**：分布式是**聚合形态不是第二种语义**——单实例下分布式计数与本地计数的放行数字必须一致；键口径沿用第 2 条；降级三段（挂 → 本地兜底 → 回 → 恢复）的语义归 ADR-05 追加节。hiredis 的引入决策与版本取证在 S4-04 落地时写（禁令三）。

## 三、放弃什么

- **令牌桶的预扣与回滚**：请求被后续环拒绝（如 404）时 token 不退——退token 等于把限流做成"按到达计费"还是"按成功计费"的选择题，而 429 的语义是"到达就被限"。代价：路由 404 大的配置会消耗令牌，写明即可。
- **突发外的排队**：桶空即拒，不排队等待（等待 = 把限流做成整形器，延迟预算进来了，S4 只表态不等待）。
- **per-key 全局精确性**：多 worker 下 CAS 是**全局**准确的（单进程内无漂移）；跨进程的精确性归 Redis（S4-04），本机不假装。

## 四、落地追加（S4-03，2026-10-31：实现边界，不回头改上面的语义）

1. **键集收敛为 `path`（缺省）与 `header:<Name>`，`"ip"` 显式不接受**。理由不是省事：`RequestInfo` 里没有对端地址，要它就得给 `Connection` 加字段、动 `sizeof(Connection)` 的 528（B-011 构成表的地基），而 TASKS「明确不在 S4 做」写着按用户/IP 的维限不做。配置文件里写 `"key": "ip"` 会被**具名拒绝**（话里指向这一节），不把它当未知字段糊掉，也不安静地退回 path。`header:` 键取第一个命中的头值；头缺失或为空时退回整条 target（与 `hash_key` 的既有口径同一条）。
2. **每个桶是一个打包原子，不是两个**。正文写"令牌数与上次补货时刻各一个原子"——落成**一个 64 位原子**：高 32 位 = 单调毫秒的低 32 位，低 32 位 = 毫 token（1 token = 1000 单位）。两个原子做 CAS 补货有一个已知的过补窗口：赢家在写回令牌之后、写回时刻之前被输家读到，输家会按旧时刻多补一截（量级是微秒，但每次竞争都漏一点）。打包成一个字之后 CAS 是单点，没有这个窗口。
3. **键 → 桶的容器用 `std::mutex` 保护的哈希表**。正文的"全原子"约束的是**桶状态**（这是错的读法会变成 per-worker 桶的入口）；键→桶的查表是结构不是状态。临界区只有一次字符串哈希查找，桶的准入（CAS）在锁外做。TSan 面仍零 race，由 S4-03 的门禁证明。
4. **键数硬上界 = 16384**，满了之后新键**共用一只溢出桶**（限流仍生效，但粒度退化为"所有溢出键共享一份额度"），计 `rate_limit_overflow_keys`。不回收旧桶、不做 LRU：键维度默认 path，正常配置的键域是路由表级别；`header:` 键的基数由客户端控制，没有上界就是内存 DoS，所以硬上界必须有。代价照记——曾经热过、后来冷掉的键会一直占位到进程重启。
5. **参数域**：`rate` 与 `burst` 必填、正整数（配置解析器只认整数，`1.0`/`1e3` 在 JSON 层就被拒）；rate ∈ 1..1,000,000/s，burst ∈ 1..1,000,000（打包格式的低 32 位装得下 burst×1000）。`rate_limit` 段不存在 = 不装限流（与 `health` 同一条形状）；段存在而缺 `rate`/`burst` = **整体拒绝**——给限流一个缺省值等于替流量改行为，不给这个"安静的答案"。
6. **链位置与表态**：限流 filter 在链首（路由之前），拒绝 = `kStop + reject_status=429`，走 S3-01 的写回通道与 `fail_pair_with_reply`（cause=kNone）→ `gateway_replies_sent`；被限的请求 `upstream_opened` 不动。`requests_parsed` 仍数这条请求本身（它是解析成功的请求），限流器自己的 `allowed`/`rejected` 另成两格，**不**往 `requests_parsed` 里加任何东西。
7. **多 worker 共用一份桶表**：桶表由装配方建一次、以 `shared_ptr` 进 `ReactorGroup::Config`，每个 worker 的 filter 拿同一份——per-worker 桶把限额放大 N 倍，正是正文第二条拒绝的形态。4 worker × burst=20 的用例断"总放行恰好 20，不是 80"。
8. **成本**：限流默认不装配，B-008/B-016 的基线不受影响；开启后的每请求成本（mutex 查表 + 一次 CAS）在 S4-08 对 B-008 的 8.7 µs 报。
9. **落地实测（2026-10-31）**：三 preset 各 **280/280**、非 gtest 警告 0、tsan 0 race、六条冒烟全绿；进程侧真 curl 同 path 打 6 条（burst=3、rate=1/s）→ **`200 200 200 429 429 429`**，退出账 `allowed=3 rejected=3 overflow_keys=0 keys=1`。阳性验证两处真红：每个 worker 一只桶 → 4 worker 用例放行 80（应为 20）；补货速率写成 1000 倍 → 桶数学与单 Reactor 429 两条同时红。
