# ADR-26 · 演示页的握手对端与取数仪器：帧的终结在上游，页面与网关同源，DOM 断言走无头浏览器

- 状态：已采纳（2026-11-04，项目所有人「可以的，按你建议来」）
- 相关：S5-04、ADR-09（只透传不解析帧）、契约 4.2 第 2 层、ADR-24/25（仪器不进被测方）、禁令三（新依赖先 ADR）

## 这一节在裁什么

S5-04 要在 `demo/ws-echo.html` 上把两条验收句落成可断言的事实：句① 「页面连上网关 → 101 建立 →
逐条回显**与上游自报序列一致**」、句② 「触发限流后页面出现 `429 rate limited` 文案」。
拆解那一句「约 30 行、零依赖」说的是**页面**的体量；它没有覆盖两件我先测出来才看得见的前提：

1. **仓库里没有任何一台上游能完成浏览器的 WebSocket 握手**——不是"网关不配合"，是对端回的那张 101 浏览器不认。
2. **浏览器不给读握手失败的 HTTP 状态码**——限流那格文案的来源必须另找，而"另找"在同源规则下会撞墙。

这两条都不是推断。下面先记实测，再记裁处。

## 一、实测（2026-11-04 本会话，浏览器 = Windows 侧 Chrome 156.0.8078.80，被测 = 本机网关 debug）

- **A/B 出在 accept 上**。`tests/test_upstream.h:428-437` 的 101 带一个**固定的假**
  `Sec-WebSocket-Accept: dGhpcyBpcyBub3QgcmVhbCBjcnlwdG9ncmFwaHk=`。经网关连它：浏览器侧
  `closed code=1006`，而**同一时刻网关侧 `upgrades_101` +1** ——握手一路走通到浏览器，是浏览器把这张
  101 判死了。把 accept 换成按 `Sec-WebSocket-Key` 算出的值（RFC 6455 样例键 `dGhlIHNhbXBsZSBub25jZQ==`
  → `s3pPLMBiTxaQ9kYGzzhZRbK+xOo=`，网关透出的与盘上算的逐字相同）→ `open` 且回显往返成立。
  结论：**Chrome 校这一格**。`tools/bench_upstream_main.cc:170` 用的是样例那一串固定值，
  它只在样例键下成立，浏览器每次发随机键，必然不匹配。
- **纯字节原样回显，浏览器收不了**。另起一台"accept 算对、之后把收到的字节原样吐回"的对端
  （这正是 `test_upstream` 隧道态与网关透传形态的做法）：实测 `open` → 立刻 `error` →
  `closed code=1006 clean=false`，`onmessage` **一次都没触发**。机理是客户端帧带掩码，
  服务端回帧必须未掩码；原样吐回等于给浏览器一个畸形帧。
  所以"回显"这件事要求对端**解掩码取载荷、重新组未掩码帧**——帧的终结必须发生在**上游**那一侧。
- **浏览器读不到握手的状态码**。12 条并发握手打同一条路径（`rate_limit rate=5 burst=5 key=path`）：
  页面侧 5 条 `open`、7 条 `1006` 且**不带任何状态码信息**；网关侧 `upgrades_101 2→7`、
  `rate_limit_rejected 0→7`（客户端那 7 条失败与网关那 7 次拒载逐数相等）。
  句② 的文案不可能从 WebSocket 事件里读出来。
- **跨源那一半是真墙**。页面在 `:18991`、对 `:18994` 发 `fetch` 取状态码：控制台原文
  `Access to fetch ... has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present`。
  网关不做静态文件服务（也不该为演示页加一条路由，那是动 `src/`），所以页面必须由**上游经网关**提供，
  页面的 HTTP 探针才与它同源。
- **无头浏览器能把 DOM 断言变成脚本，但它单次不可靠**（这条决定了句⑤ 的落地形态）。从 WSL 里直接执行
  Windows 侧 `chrome.exe`（interop 可用）配 `--headless=new --dump-dom --virtual-time-budget=N`：
  `N=8000` 抓到的 DOM 停在 `sent headless-roundtrip`，`N=15000` 抓到
  `recv text len=18 val=headless-roundtrip`——异步往返的**结果**能进落盘的 DOM 快照。
  但同一命令、同一预算连跑三轮，第三轮只抓到 `connect ws://…` 一行：
  **预算够了也不保证快照里那一格已经填上**。所以仪器必须是"有限重试 + 完成哨兵"，不是"跑一次看运气"。
  另一条同轮的仪器坑：`--dump-dom` 的输出里含页面自己的 `<script>` 源码，
  而源码里就写着 `recv text len=` 这串——整篇 grep 实测命中 **2** 次、限定到哨兵元素后命中 **1** 次。
  **拿整篇文档当证据会造出一条假绿**：那一轮（第三轮）整篇 grep 照样"过"。
  耗时那一格也与我先前的印象相反：单轮 ≈**1.11 s**（三轮逐轮 1.11/1.11/1.11 s，含 Chrome 冷启动），
  所以重试不贵。

## 二、我选择什么（三件）

1. **给 `l7gate_test_upstream` 加 `--ws-echo`**：带 `Upgrade:` 的请求按 `Sec-WebSocket-Key` 算 accept
   （自带 SHA-1 + base64，不引 OpenSSL——它不在契约 9.1 的锁定表里，动它就是禁令三）；进隧道态后
   **解掩码取载荷、回未掩码帧**，载荷逐字节原样（不改内容、不加前缀）。另加 `--html <path>`：
   非升级的普通 GET 回这个文件，用来把演示页放进上游。两档都是**测试/演示对端**的性质，
   默认不开、不加参数时行为与今天逐字节相同（既有冒烟与单测不受影响）。
2. **页面经网关同源提供**：演示拓扑是「一台 `--ws-echo --html demo/ws-echo.html` 的上游 + 一台
   路由到它的网关」，页面从网关端口载入，于是它的 WS、它的状态码探针、它自己都是同一个 host:port。
   429 的文案来源 = 页面对同一路径发一条普通 HTTP 请求读 `response.status`。
   连带账写在第四节第 3 条（限流键是 path，页面路径与探针路径必须分开）。
3. **句⑤ 的取数仪器 = 无头 Chrome + 有限重试 + 完成哨兵 + 落盘判定**。页面在跑完它该跑的那一串之后
   才写一个**哨兵元素**（`<output id="s504-verdict">`，内容形如 `DONE steps=open,send,recv,close`），
   `scripts/smoke-s5-04.sh` 用固定预算（`--virtual-time-budget=20000`）反复取快照直到哨兵出现，
   上限 8 次——**每一次的 DOM 都单独落盘**，重试次数与未成交的那几轮形状一起进判定，
   这样"重试把它跑绿了"这件事本身是可审计的，不是我一句"后来好了"。
   断言**只读哨兵元素的文本**，不读整篇文档（第一节的实测：整篇 grep 会被 `<script>` 源码骗过）。
   判定照 S5-03 的处置写进 `build/smoke-s5-04/verdict.txt`
   （本轮那条未归因的"脚本打 FAIL 而 rc 读 0"，§22.2 第 5 条，不再只信退出码）。
   `browser-use` 那套 MCP 工具作为**交互式复核**用（我这轮就是靠它先确认可达性），不进可复跑脚本。

## 三、边界（这一节是本 ADR 最需要被读到的地方）

- **ADR-09 一个字不动**：网关仍然只做握手 relay + 之后不透明双向透传。帧的终结在上游，
  这正是真实拓扑的样子——生产里 WebSocket 的端点永远是应用，不是代理。
  页面的职责仍是显示**网关给它的东西**，不是替网关解释帧。
- **`src/` 一字不动**。本任务全部落在 `tests/`、`demo/`、`scripts/`、文档。
  验收句① 的"与上游自报序列一致"由上游自报计数 + 网关隧道字节计数 + 页面 DOM 三处同轴对账，
  不需要网关新增任何键。
- **仪器不进被测方**：无头 Chrome 是取数仪器，不产生被测负载以外的东西，也不进网关任何计数
  （它发的每一条请求都是真业务请求，该进账就进账——这与句② 的逐数对账是同一条事实的两面）。
- **不拿它测任何 SLO 数字**：这条仪器只服务演示面验收。任何 p99/QPS 读数不得与它同批混比
  （同机抢 CPU 那条规矩照 ADR-25 第五节）。

## 四、代价（明码，不是"应该不贵"）

1. **测试对端不再完全 dumb**。`test_upstream` 的头注释写着"上游一旦开始聪明，网关的失败就分不清
   是我坏还是它坏"——`--ws-echo` 确实让它学会了 SHA-1 和帧重组。边界是：这条聪明**只在 `--ws-echo`
   开启时存在**，且只用于"让真浏览器能连"；S1-05/S2-05 那批透传断言仍打在默认档（裸回显）上，
   那里"对端越笨越好"原样成立。两处不能互换，这条我写进用例名与注释。
2. **新增一份工具依赖，按禁令三在此登记**：冒烟脚本现在依赖 Windows 侧 `chrome.exe`（实测
   156.0.8078.80）经 WSL interop 可执行。它不是契约 9.1 表内的锁定项、版本随 Windows 侧自动更新漂移，
   所以① ENVIRONMENT 记的是**实测版本 + 通路事实**，不是新的锁定行；② 依赖不在时脚本必须在阶段 0
   **自己拒跑**（照 `smoke-s3-04`/`smoke-s4-04` 对 Docker 的先例），不许换个浏览器顶上去，
   也不许把 DOM 那一半静默降级成"没做"。
3. **跨 9P 边界的进程**（`/mnt/c` 上的 exe）。契约 9.4 禁的是在 Windows 盘上**构建与压测**；
   这里只借它执行一次取 DOM 的动作，被测方与仓库都还在 ext4。耗时实测单轮 ≈**1.11 s**
   （含 Chrome 冷启动，三轮各 1.11 s），重试到 8 次的上限也就十几秒，所以它不进任何读数口径、
   也不构成"冒烟变慢"这条代价——真正的代价是**多了一条会时抓不到格子的仪器**（第四节第 5 条）。
4. **限流键是 path 的连带账**：页面自己就是一条路径、要吃一只桶，探针是另一条。
   所以演示配置必须让**探针路径**与**页面路径**分开，且突发必须打在探针那一条上
   （S5-03 已经为这条红过一轮：各用 unique path 时 `rate_limit_rejected` 恒 0）。
5. **虚拟时间预算是个真旋钮**：给小了它少抓一格（实测 8000 停在 `sent`），所以断言必须同时带
   "上界"和"确实发生过"那一半——`recv` 那一行不存在就是 ✗，不是"再等等看"。

## 五、S5-04 验收句 → 断言落点

| 句 | 落点 |
|---|---|
| ① 101 建立 + 逐条回显与上游自报序列一致 | 无头 DOM 快照里必须出现 `open` 与逐条 `recv ... val=<发出去的那一串>`；同一时刻网关 `upgrades_101`、`bytes_tunnel_up/down` 与上游自报数三条同轴（页面侧条数 == 网关侧条数，不是"看起来通了"） |
| ② 页面出现 `429 rate limited` 且不是把帧当文本误显示 | 页面对探针路径的普通请求读 `status` → DOM 文案含 `429 rate limited`；等式两边：DOM 数到的条数 == 网关 `rate_limit_rejected` 增量（逐数）；"没误显示"由另一侧钉——回显值与发送值**逐字相等**，畸形帧的表现是 `1006`（实测形状），不是文本 |
| ③ 断开时两侧都收 | 页面 `close()` 后 DOM 出 `closed code=1005`（实测：页面主动 `close()` 且服务端跟着关的那一侧读数是 **1005 而不是 1000**；`wasClean` 那一格本轮没实测，冒烟里按实际取值写死、不预设立场）；网关侧 `live_connections` 回基线、`connections_constructed == connections_destructed` |
| ④ 只有长连接才算数 | 页面保持连接（不做 send 完就关），冒烟在同一条连接上打第二条消息并断它仍是**同一条**连接（`live_connections` 不变、`connections_constructed` 不变）；README 点名契约 4.2 那句"短连接测 C100K 是假的" |
| ⑤ 取数证据用 DOM 断言 | 全部判定读 `--dump-dom` 的落盘快照 + `verdict.txt`；不接受人眼，也不接受截图 |

## 六、阳性验证清单（能红才叫绿）

- **W1 回显不改写**：让 `--ws-echo` 在回帧载荷前加一个字节 → 句① 的逐字相等那条必须红。
- **W2 accept 不算只抄**：把 accept 改回固定串（样例那一串）→ 浏览器根本连不上，句① 的 `open` 必须红
  （这条同时是"仪器坏了"与"被测方坏了"的区分器：网关侧 `upgrades_101` 仍会 +1）。
- **W3 两侧同轴**：把 429 那格的等式一边换成页面自己的计数（不看 `rate_limit_rejected`）→ 必须红。
- **W4 长连接那条**：让页面在收第一条回显后就 `close()` → 句④ 的"仍是同一条连接"必须红。
- **W5 哨兵提前写**：把哨兵的写入条件从"这一串步骤全跑完"改成"页面载入即写" → 句① 的断言必须红。
  这条守的正是第一节实测到的那个形状（第三轮只有 `connect` 那一行）：如果断言只看"页面活着"，
  仪器就会把没跑完的一轮读成通过。
每条第一版不红就先弄清为什么，不改用例凑红（§15.3/§16.3/§20.2/§21.1/§22.1 五次都是这条）。

## 七、这一节没做什么

不改网关一行代码、不改 ADR-09 的透传语义、不新增任何网关侧指标键、不给浏览器暴露状态码这件事
找绕过（那是协议边界不是缺陷）、不做 TLS/`wss://`（契约 1.3）、不做帧级治理或消息级限流（ADR-09 的代价段）、
不引 OpenSSL/python3 当演示对端、不在本任务里量 SHA-1 那台的资源占用（它是仪器）。
