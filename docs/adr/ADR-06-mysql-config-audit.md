# ADR-06 · MySQL 承担配置持久化与访问审计

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 3.1、3.4

## 我选择什么

路由配置、上游节点元数据、访问审计记录存 MySQL。网关启动时从 MySQL 读，运行期按周期定期 reload（契约 3.1：动态服务发现不做，用配置文件 + 节点表定期 reload 替代）。

## 为什么是 MySQL 而不是 Redis / 文件

关键不是「要持久化」——文件也能持久化。我要的是**可审计、可按时间范围回溯**：

- 「上周三 15:00–16:00 这条路由是谁、从什么值改成什么值」
- 「故障时间窗内哪些请求被打到了哪条上游，返回什么状态码」

这是带时间维度的查询语义。Redis 没有这个查询能力；文件配置改了就被覆盖，改动人、改动历史、改动顺序全丢；JSONL 审计日志能查但要自己写扫描逻辑，等于重造一个弱 SQLite。**「没有它会怎样」的标准答案**：配置改了无法追溯，故障复盘找不到时间点。

## 我放弃什么

- 不用 PostgreSQL：项目已锁 MySQL 系，两套并存只会增加运维面。
- 不用 ORM：网关只需在启动与定期 reload 时读配置，手写 SQL + 结果集映射的依赖面更小，也不引入与本项目考点无关的抽象。
- 不做配置写入 UI（契约 1.3 禁止 Web 管理后台）：配置由 SQL 直接改，网关侧只读 + reload。

## 版本偏离（本 ADR 与 ENVIRONMENT.md 的对账点）

契约原锁 `libmysqlclient 8.0.x`，但 Ubuntu 26.04 只有 **8.4.11**，这是本项目**唯一无法字面命中的锁定项**。我按现实把锁定值改为 8.4.x（理由与边界记在 ENVIRONMENT.md 第 3 节），同时保留服务端镜像 `mysql:8.0.36` 不动，理由是中途换镜像 tag 会让历史数据断代。

**客户端 8.4 → 服务端 8.0.36 的兼容性目前只是推断，不是实测事实。** 要到 S3 首次真正建连时取证，未取证前这条不能对外宣称成立。是否连服务端一并对齐 8.4，留到 S3 触到 MySQL 时决策。

## 依赖

libmysqlclient 8.4.x（apt `libmysqlclient-dev` 8.4.11）。MySQL 走 Docker（契约 9.3），但本机 Docker WSL Integration 尚未开启，属 S3 之前的阻塞项。
