# ADR-15 · 上游连接池：per-worker 归属，跨下游生命周期回收

- 状态：已采纳
- 日期：2026-10-27
- 相关：ADR-03（多线程 Reactor）、ADR-14（连接所有权：单线程拥有、跨线程只传 fd）、ADR-16（请求-响应配对模型，S2-04，尚未写）、契约 4（S2 = 多 Reactor + 上游连接池 + 跨线程销毁）、`docs/ARCHITECTURE.md` 1.7/1.14/1.17、`docs/BENCHMARK.md` B-005（nginx upstream keepalive 按 worker 计）

## 我选择什么

**每个 worker 各持一份上游连接池，池不跨线程共享。** 池是一组到「配置里那一个上游」（S2 无路由，多上游归 S3）的空闲（热）连接，由 owner worker 的循环线程独占管理，因此**不需要锁**（ADR-14 的单线程拥有原样成立）。借还语义按**下游连接的生命周期**，不按单个请求：

1. **借（borrow）**：一条下游第一次要回源、当前没有配对上游时，先从本 worker 的池里取一条空闲热上游；池空才新建（受 fd 预算约束）。借出即建立配对（`downstream.peer_fd ↔ upstream.peer_fd`），**这条下游在它整个存活期独占这条上游**（S1 的 keep-alive 复用原样保留：同一条下游的多条请求、包括 pipelined 请求，都走这条配对上游，响应按 FIFO 回来）。
2. **还（return）**：当这条**下游关闭**、而它配对的上游处于「干净可复用」状态时，解除配对、把上游放回池，供本 worker 的下一条下游借——**而不是像 S1 那样级联关掉它**。
3. **「干净可复用」的判据**（全部满足才归还，否则按 S1 级联关闭）：上游 `state()==kOpen`、非隧道态（`tunneling()==false`）、非一次性配对（`close_after_response()==false`）、出向缓冲空（没有在飞请求字节）、响应跟踪停在干净边界（`response_tracking().phase==kHead`，即上一条响应已完整完结并复位）、且本次关闭不是 `kDiscardOutbound`（写已坏的上游不值得留）。
4. **不入池、直接淘汰关闭的上游**：隧道态（101 之后是专用双向字节流，无法共享）；`close_after_response`；任何 EOF / 截断 / 坏框架 / 写失败 / connect 失败的上游。
5. **池有上限** `pool_max_idle`：归还时若池已满，直接关闭而不是放回（给每连接内存一个硬上界，SLO #2 要它）。
6. **空闲上游仍注册在本 worker 的 epoll 上（EPOLLIN）监控 EOF**：上游主动关掉一条空闲 keep-alive 连接时，owner worker 读到 EOF 就把它从池里淘汰关闭——**且这是一次正常的空闲连接回收，不计入 `upstream_truncated_*`、不级联任何下游**（它本来就没有配对下游）。
7. **空闲超时回收不在 S2-02**（归 S4）。空闲上游一直活着，直到被借走、被对端 EOF、池满被淘汰、或 worker 停止时随池排空。

## 为什么

**per-worker 而不是 shared，是项目所有人 2026-10-27 的裁决，我的分析三条：**

- **它保住 ADR-14 的不变量。** 整个 S2 的支点是「一条连接只被一个 worker 碰 → TSan 结构性干净」。per-worker 池让上游连接始终归它的 owner worker 独占，这条不变量原样成立；shared 池是唯一会打破它的东西——上游连接被非 owner 线程借出/归还/淘汰，S2-03 那批「更难的跨线程异步销毁」竞态会立刻全部涌现，而 TSan 干净正是 S2 的门禁本身。选 per-worker，S2-03 基本只剩 stop 时的收尾竞态。
- **nginx 自己就是 per-worker 池。** B-005 里实测并记过：nginx 的 `upstream keepalive` 池按 worker 计（单 worker 档要把池抬到 1024 才撑住 1000 并发）。选 per-worker 让 S5 与 nginx 的对比是同一种池模型，比较更公平；shared 反而是 nginx 没有的额外复杂度。
- **SLO #2 的内存代价被高估了。** 池的开销上界是「每 worker `pool_max_idle` × N」，是一个配置量、不是每条下游摊一份；而 100k 空闲长连接是隧道态、本来就 1:1 专用不入池。所以池对 #2 那 100k 的每连接内存几乎没有影响。

**借还按下游生命周期、而不是按单个请求-响应边界**，是被现有转发核逼出来的、不是我图省事：S1 的 `forward_pending_requests_body` 会在一次可读事件里把**多条 pipelined 请求**灌进同一条配对上游（`PipelinedRequestsInOneSegmentAreAllForwarded` 锁的就是这条），响应按 FIFO 从这一条上游回来。若改成「每条请求借一条上游、响应完结就还」，一条下游的多条在飞请求会被迫借多条上游，而多条上游的响应到达顺序不保证与请求顺序一致 → **响应乱序**，违反 HTTP/1.1 pipelining 的 FIFO。要正确支持「按请求借还 + 不乱序」就得先定义请求-响应配对模型（哪条响应配哪条请求、能不能重排），那正是 **S2-04（ADR-16）** 的内容。所以 S2-02 取保守口径：**下游存活期 1:1 独占（S1 语义全保留），只在下游关闭这个干净边界上回收上游**，把「按请求解耦」留给 S2-04 和它的配对模型一起放宽。

## 我放弃什么

- **稳态 keep-alive 负载下池基本惰性。** 一条长命下游全程独占它的上游，只有它关闭那一刻上游才归还。所以在 wrk 闭环基准（1000 条常驻下游）里，池**不减少上游连接数**（有多少条常驻下游就有多少条上游）。池的真实价值在**连接churn**：短命下游（发一条就关、或 `Connection: close`）轮流复用同一批热上游——那种负载下 1000 条短命下游可以只用个位数的上游连接，省掉的是每条下游一次 TCP 握手 + 上游侧的连接创建/销毁。
- **负载不均时不能跨 worker 借热连接**，池利用率比 shared 低。但 S2 只有单上游、派发又是 round-robin 均衡的，不均本来就小；等 S3 加了多上游 + 最少连接负载均衡再评估是否值得换 shared（届时新写 ADR，且要有 S2-07 压测证据，按契约 3.2 的延迟决策纪律）。
- **pipelining 与「按请求借还」的组合**，归 S2-04。

## 后果与约束

- **一条诚实的性能边界，写在这里免得日后拿它邀功**：如「我放弃什么」第一条，池在闭环 keep-alive 基准里不减少上游连接数，S2-07 的压测**不会**显示池带来上游连接数下降或 p99 改善，我不声称它有。池是结构性交付物（契约 S2 要求 + 与 nginx 同形 + churn 负载省握手），不是这个基准的提速项。能证明它真的在复用的，是 churn 用例：N 条短命下游跑完 `upstream_opened`（=新建数）远小于 N、`pool_borrows` ≈ N−新建数。
- **它推翻 S1 的一条隐含契约：「下游关 → 上游级联关 → `constructed==destructed`」。** 池化后上游活得比它的下游久（下游关闭时上游归还进池，不随之销毁）。所以 S1 里若干断言「单条下游关闭后所有连接对象都析构」的生命周期用例会**合理地**变红，必须改写成「下游关后上游进池仍存活；worker 停止、池排空后才 `constructed==destructed`」。这是池本来就该有的行为，不是为了让测试变绿而钳——按纪律，改的是测试对「新合法行为」的期望值，并在每条改动旁写明为什么。
- **新增观测面**（`ReactorStats`，全原子，累加到共享 stats）：`pool_borrows`（从池借出次数）/ `pool_returns`（归还进池次数）/ `pool_creates`（池空时新建，与既有 `upstream_opened` 同源）/ `pool_evictions_eof`（空闲被对端关）/ `pool_evictions_full`（池满未归还直接关）/ `pool_idle`（当前空闲数，非原子、循环停下后读）。验收「N 条短命下游只开 M 条上游、M ≪ N」靠 `upstream_opened` 与 `downstream_accepted` 的差额 + `pool_borrows` 断言。
- **淘汰与截断表态不变**：上游 EOF / 截断 / 坏框架走 S1-06 的两条口径（头之前 502、头之后 EOF 表态），那条上游被**淘汰**（关闭）而不是归还，配对的下游按 S1-06 处理。池只接「干净完结、随下游关闭而释放」的上游。**新增一条必须分清的边界**：空闲（未配对）池内上游被对端 EOF 是正常回收，绝不许误计成 `upstream_truncated_before_head`（它没有配对下游、也没有在飞请求）——这条我会用专门用例钉住。
- **隧道与背压路径不动**：隧道态上游不入池（专用），S1-05/07 的隧道泵与停读线逻辑原样保留；池只作用在普通 HTTP 请求-响应转发的上游侧。
- **每 worker 的 fd 预算**现在要同时容纳「在飞配对的上游 + 池里空闲的上游 + 下游」，`pool_max_idle` 与 `max_connections` 的关系写进配置注释，避免池把 fd 预算吃光导致下游被拒。
