# ADR-12 · 熔断必须带「最多摘除比例」安全阀

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 3.1、4（S3）、11.3

## 我选择什么

熔断判死之外，强制加一道上限：**任一时刻被摘除的上游节点比例不得超过 `max_ejection_percent`，默认 10%。** 达到上限后，即使判据仍然「应当摘除」，也不再摘除更多节点。参考 Envoy outlier detection 的同名参数。

## 为什么这是必需项，不是可选加固

熔断的输入是错误率与连续失败次数，而这些判据在两类情况下会**同时失准**：上游发布导致短暂 5xx、网络抖动、压测自己把上游打爆。

没有安全阀时的失效链条非常短：

1. 上游整体抖动，错误率同时飙升；
2. 判据成立，节点一个接一个被摘；
3. 剩余节点承接全部流量，过载更严重，错误率更高；
4. 更多节点被摘 → **熔断本身变成了雪崩放大器**。

最坏情况从「一个节点故障」演变成「我亲手把整个集群判死」。有 10% 上限时，最坏只损失 10% 容量——这是**故意保留一段错误来换取不自我放大**。这个取舍我在 README 与 INTERVIEW.md 里都要讲明，因为「熔断为什么要有个不熔断的阈值」是反直觉的，也正是契约 11.3 这道题的得分点。

## 半开与摘除比例的关系

半开探测恢复也要受同一道阀约束：恢复期不能一次性把节点全放回来，否则故障未消退时立刻二次雪崩。具体节奏（每次放多少、探测成功几次转正）在 S3 实现时定，且必须给出**可断言的验收标准**——契约 8.1 的反例「支持健康检查」不接受，要写成「kill 上游后 3s 内摘除，摘除期间错误率 < 1%」这种形式，已记在 TASKS.md 的 S3 门禁。

## 与 Nginx 的对照（可写进 README 的能力主张）

Nginx 开源版只有被动的 `max_fails` / `fail_timeout`，主动健康检查是 Nginx Plus 的功能，**内置熔断器没有**。所以在「流量治理」这个维度上，本项目的功能不比 Nginx 少——而契约第 2 节仍以 Nginx 为吞吐基线，这两件事不矛盾：我比它多的不是速度，是治理策略。这条必须表述精确，不能被读成「我比 Nginx 快」。

## 验证归属

S3 门禁要求「摘除耗时实测 + 误摘率实测 + 故障注入结果」，其中必须包含一条专门打安全阀的用例：全量节点同时注入故障，断言被摘除比例恰好停在配置上限、不越过。

## 追加（2026-10-30，S3-03 落地时的两条判据读法）

**一、误摘率的判据必须成对：上界（≤ X）+ 下界（摘除确实发生过）。**

这是 ADR-19 追加第二条用一次实测教过的形状：`≤ 1/(N+1)` 是期望不是上界，把环查找退化成"取第一个点"反而以 0.00% "满足"上界。误摘率「健康后端被摘次数 ÷（探活轮数 × 健康后端数）」是同一个上界形状——**一个从不摘除的实现，误摘率恒等于 0，比任何真实现都好看**。所以断言写成一对：

- 上界：误摘率 ≤ 配置阈值（读数进 BENCHMARK，带分母，≥1000 轮）；
- 下界：**注入故障的后端至少被摘除一次**（摘除计数 ≥ 1，按目标下标可查）——这条证伪"从不摘除"。

**二、安全阀"容量"的分母，今天 = 目标表去重后的成员数，且只对今天负责。**

加权已裁不做（ADR-19「我放弃什么」第二条），所以 `max_ejection_percent` 的分母今天就是**目标表去重后的成员数**（单组配置下就是组内成员数；两个组共用一台后端时它只算一次——那台机器的容量物理上只有一份，按组各算一次会把安全阀读虚）。这条不是永远成立：加权一旦进来，"摘掉一个加权后端损失多少容量"的分母就得重写，而 ADR-19 里「摘掉加权后端时权重是重归一还是保留」那个问题没有答案之前，任何新分母都是含糊的。所以这里只钉今天的口径，**不默认它以后不变**；那份答案要等加权进 ADR-19 时一并给。可摘除上限取 `floor(成员数 × max_ejection_percent / 100)`——"被摘除容量 ≤ 10%"的字面读法，N<10 的小组按这个式子就是"一个都不能摘"，配置的人想要摘除能力就把比例调大，我不替配小集群的人偷偷放宽成 ceil。
