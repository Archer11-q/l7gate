# ADR-12 · 熔断必须带「最多摘除比例」安全阀

- 状态：已采纳
- 日期：2026-10-26
- 相关：契约 3.1、4（S3）、11.3

## 我选择什么

熔断判死之外，强制加一道上限：**任一时刻被摘除的上游节点比例不得超过 `max_ejection_percent`，默认 10%。** 达到上限后，即使判据仍然「应当摘除」，也不再摘除更多节点。参考 Envoy outlier detection 的同名参数。

## 为什么这是必需项，不是可选加固

熔断的输入是错误率与连续失败次数，而这些判据在两类情况下会**同时失准**：上游发布导致短暂 5xx、网络抖动、压测自己把上游打爆。

没有安全阀时的失效链条非常短：

1. 上游整体抖动，错误率同时飙升；
2. 判据成立，节点一个接一个被摘；
3. 剩余节点承接全部流量，过载更严重，错误率更高；
4. 更多节点被摘 → **熔断本身变成了雪崩放大器**。

最坏情况从「一个节点故障」演变成「我亲手把整个集群判死」。有 10% 上限时，最坏只损失 10% 容量——这是**故意保留一段错误来换取不自我放大**。这个取舍我在 README 与 INTERVIEW.md 里都要讲明，因为「熔断为什么要有个不熔断的阈值」是反直觉的，也正是契约 11.3 这道题的得分点。

## 半开与摘除比例的关系

半开探测恢复也要受同一道阀约束：恢复期不能一次性把节点全放回来，否则故障未消退时立刻二次雪崩。具体节奏（每次放多少、探测成功几次转正）在 S3 实现时定，且必须给出**可断言的验收标准**——契约 8.1 的反例「支持健康检查」不接受，要写成「kill 上游后 3s 内摘除，摘除期间错误率 < 1%」这种形式，已记在 TASKS.md 的 S3 门禁。

## 与 Nginx 的对照（可写进 README 的能力主张）

Nginx 开源版只有被动的 `max_fails` / `fail_timeout`，主动健康检查是 Nginx Plus 的功能，**内置熔断器没有**。所以在「流量治理」这个维度上，本项目的功能不比 Nginx 少——而契约第 2 节仍以 Nginx 为吞吐基线，这两件事不矛盾：我比它多的不是速度，是治理策略。这条必须表述精确，不能被读成「我比 Nginx 快」。

## 验证归属

S3 门禁要求「摘除耗时实测 + 误摘率实测 + 故障注入结果」，其中必须包含一条专门打安全阀的用例：全量节点同时注入故障，断言被摘除比例恰好停在配置上限、不越过。

## 追加（2026-10-30，S3-03 落地时的两条判据读法）

**一、误摘率的判据必须成对：上界（≤ X）+ 下界（摘除确实发生过）。**

这是 ADR-19 追加第二条用一次实测教过的形状：`≤ 1/(N+1)` 是期望不是上界，把环查找退化成"取第一个点"反而以 0.00% "满足"上界。误摘率「健康后端被摘次数 ÷（探活轮数 × 健康后端数）」是同一个上界形状——**一个从不摘除的实现，误摘率恒等于 0，比任何真实现都好看**。所以断言写成一对：

- 上界：误摘率 ≤ 配置阈值（读数进 BENCHMARK，带分母，≥1000 轮）；
- 下界：**注入故障的后端至少被摘除一次**（摘除计数 ≥ 1，按目标下标可查）——这条证伪"从不摘除"。

**二、安全阀"容量"的分母，今天 = 目标表去重后的成员数，且只对今天负责。**

加权已裁不做（ADR-19「我放弃什么」第二条），所以 `max_ejection_percent` 的分母今天就是**目标表去重后的成员数**（单组配置下就是组内成员数；两个组共用一台后端时它只算一次——那台机器的容量物理上只有一份，按组各算一次会把安全阀读虚）。这条不是永远成立：加权一旦进来，"摘掉一个加权后端损失多少容量"的分母就得重写，而 ADR-19 里「摘掉加权后端时权重是重归一还是保留」那个问题没有答案之前，任何新分母都是含糊的。所以这里只钉今天的口径，**不默认它以后不变**；那份答案要等加权进 ADR-19 时一并给。可摘除上限取 `floor(成员数 × max_ejection_percent / 100)`——"被摘除容量 ≤ 10%"的字面读法，N<10 的小组按这个式子就是"一个都不能摘"，配置的人想要摘除能力就把比例调大，我不替配小集群的人偷偷放宽成 ceil。

## 追加二（2026-11-02，S4-05 落地）：第二个输入是错误率窗口，唯一的解除出口改成半开限流

编号说明：本节仍记在 ADR-12 里，不新开一条。S4-05 改的是**熔断判据与恢复节奏**，执行机构一条没新立（已裁第一条），
而 ADR-23 那个编号已经在 TASKS 里许给了 S4-06 的重试边界——把它挪来装熔断，就会有两份文档指同一个编号。

### 这一节在裁什么

S3-03 交的是执行机构：一条连续失败计数、一个 CAS 状态位、一只安全阀、一台主动探活机。它只有**一个输入**。
S4-05 按已裁第一条只加两个输入进来——滑动窗口错误率（第二个判死理由）与半开限流恢复（解除摘除时的放行节奏）——
**不另起一套判死**。下面第一、二节就是这两个输入的整份语义，第三条禁令（先 ADR 后代码）要求它们在这里写完，
而不是在 `src/` 里边写边定。

### 一、第二个判据：窗口内错误率

**它防的是哪一种失效**：连续失败计数只看"连着几次"，所以一台 **40% 请求回 5xx** 的后端可以永远不被摘——
每一次成功都把计数清零。这就是 S4 拆解里那句"判据太钝时坏节点拖着流量"的字面形状：坏的是比率，
而比率在"连续"这把尺上看不见。

**取值（缺省值即本 ADR 的裁定，配置文件里每个字段都可覆盖）**：

| 字段 | 缺省 | 取值域 | 是什么 |
|---|---|---|---|
| `window_ms` | 10000 | 100..3600000 | 滑动窗口总时长 |
| `minimum_requests` | 20 | 1..1000000 | 样本下界：窗口内不足这么多条请求，错误率不判 |
| `error_rate_percent` | 50 | 1..100 | 失败占比阈值（整数比较：`失败数 × 100 ≥ 总数 × 阈值`） |

- **窗口是 8 个桶**（`kWindowBuckets = 8` 是内部常量，不做配置项：多一个旋钮只是多一类配置错误）。
  `bucket_ms = max(1, ⌊window_ms / 8⌋)`，槽位 `= (now_ms / bucket_ms) & 7`。所以**有效窗口 = 8 × bucket_ms**，
  比配置值短不到 7 ms——方向是更保守（旧样本提前出账），不是更宽。窗口分辨率 = 一个桶，
  这条边界在断言里当容差用，不假装它是零。
- **样本来源**：失败 = 最终头 ≥500、头之前 EOF、响应头坏、三类超时、connect 失败；成功 = `<500` 的完整最终头。
  这与 S3-03 的被动记账点是同一批采集点，我没新增采集点。
- **主动探活的样本不进窗口。**两个理由，都不是风格：①口径第 3 条（仪器不进被测方）——窗口是"业务请求的真实体验"，
  掺进网关自己发的固定 `GET health_path` 之后，"这台后端的业务错误率是多少"就没有答案了；②已裁第三条④
  定的是"探活失败与业务失败汇入**同一个连续计数**"，汇合点在**摘除这个出口**，不在统计里。
  所以窗口与连续计数是两把独立的尺，它们共享的是一只阀、一条 CAS 摘除路径。
- **摘除那一刻窗口清零**，且**半开期内不判错误率**。不这么做的话，刚被放回来的成员会被自己上一周期的旧账
  立刻再摘——那是"横跳"，也正是 S3-03 已知边界④（恢复后再摘要重新攒满 `max_fails`）替我挡过一次的同一类事。
- 连续失败判据（`max_fails`）一个字没动。**"错误率判据会不会取代连续失败判据"**：不会，也不该——
  样本下界那一条就决定了它俩覆盖的是不同形状：一台后端刚上线就 100% 拒绝连接时，窗口还没攒够 20 条样本，
  先摘它的是连续计数。

### 二、解除摘除：到期先进半开，不再全量放行

**被替换掉的旧语义（写清楚，不然读代码的人以为两条并存）**：S3-03 的摘除解除有**两条全量出口**——
`fail_timeout_ms` 到期（`sweep_expired` 扫到就打回健康）与主动探活判活（`revive` 立即恢复）。
本节把**到期那一条**升级为"半开限流恢复"。第七节写明探活那一条为什么今天仍留作全量出口，那是已知弱点，不是漏了。

半开态的规则（六条，每条都有对应的用例）：

1. **放行预算 `half_open_requests`（缺省 3，1..1000）**：一个半开周期内最多放 B 条业务请求进这一台成员。
2. **被放行的那一条必须真的落到它**：候选集读到"有成员处于半开且门给了名额"时，返回**只含该成员**的候选集，
   本轮策略选择被跳过。理由不是我偏好确定性，是 ADR-19 追加三那条实测——把成员放回候选集不等于它接得到流量
   （B-013 里 98.3% 的流量吸附在成员 0）。半开若只做到"允许被选中"，它就是摆设。
   代价照记：被钉住的这一条请求不参与最少连接与一致性哈希的选择，探测优先于均衡。
3. **攒够 `half_open_successes`（缺省 2，1..1000，且必须 ≤ B）条业务成功 → 全量恢复**；
   其间出现**一次**业务失败 → 立即回摘（不等 `max_fails`），`fail_timeout_ms` 重新计时。
   "试一条就死"不需要再攒三次失败才承认它死。配 K > B 是配置错误（永远出不来半开），启动整体拒绝并在话里点名两个字段。
   **两条证据来源不对称，这一条是实现时才逼出来的、起草那一步没写全**：出半开只认**业务请求**的成功——
   探活判活不算证据，否则"只肯答 `GET /health`、业务全回 500"的后端会被自己的仪器推回全量流量；
   而半开期内**探活判死仍然立即回摘**（成员资格上它一票否决，S3-05 那句"探活是成员资格的唯一真源"）。
   方向是 fail-closed，所以这个不对称我留着不抹平。用例：`ProbeEvidenceAloneNeverClosesTheHalfOpen`
   与 `ProbeFailureDuringHalfOpenReOpens`；反面那条"探活样本不进窗口"由
   `ProbeFailuresFeedStrikesButNeverTheWindow` / `ProbeSuccessesNeverDiluteTheWindow` 两条钉住。
4. **`half_open_timeout_ms`（缺省 3000，100..3600000）**：周期内没攒够（探测请求挂在那里、或者根本没流量）→ 回摘。
   半开不是终点站，四条出路都得有到期兜着；这条与第 3 条一起保证"半开"不会变成一种永久的低效率状态。
5. **安全阀照常约束，而且半开占着阀位**。`health_ejected_now` 这一格在装配熔断时口径 = **摘除 + 半开**的成员数。
   把半开从账本里摘出去的话，10 台、`max_ejection_percent=10` 的那个组可以让 10 台各自进半开、
   全组有效容量≈0，而计数器上写着"只损失 0 台"——ADR-12 量的是容量，不是状态名。
   账本只在两种迁移上动：`健康 → 摘除/半开` 加一、`→ 全量恢复` 减一，CAS 赢家动账（S3-03 的纪律一字不变）。
6. **全员半开且预算耗尽 → 候选集空 → 回退全员**（沿用 S3-03 那条最后防线，另计一格
   `health_all_denied_fallback`）。**不新开一条 503**，三个理由：①"没地方去就拒绝"与 ADR-22 第二节
   "入口不拒绝"是同一条立场，我要改它得先在 ADR-22 里改，不是在两节里各说一套；②回退之后这些成员的失败
   **一次即回摘**（第 3 条），所以暴露的是一批请求、不是一个周期；③真连不上的时候 S4-02 的 502/503 就在下一跳等它，
   客户端不会挂在缓冲里。代价照记：那一批是全量，二次雪崩的门没有完全关死，上界由"一次即回摘"兜着。

### 三、配置面：新增顶层 `circuit` 段

```json
{
  "health": { "max_fails": 3, "fail_timeout_ms": 10000 },
  "circuit": { "window_ms": 10000, "minimum_requests": 20, "error_rate_percent": 50,
               "half_open_requests": 3, "half_open_successes": 2, "half_open_timeout_ms": 3000 }
}
```

- **`circuit` 段存在的前提是 `health` 段也在**：熔断没有自己的执行机构，它用的就是健康表那一条摘除路径与那一只阀
  （已裁第一条）。`circuit` 在而 `health` 不在 → 启动拒绝（退出码 2），话里**同时点名两个段名**（S4-04 那条口径）。
- 六个字段全部可选、缺省即上表；未知字段、类型不对、取值越界一律整体拒绝并点名是哪一项（ADR-19 第一节的严格性原样适用）。
- **不新增命令行开关**：判据与恢复节奏是策略，策略在文件（ADR-19 第一节那条切分）。这与 S4-04 把
  `--redis-settle-ms` 放命令行不构成矛盾——要不要跨进程聚合是部署事实，不是策略。
- **段不存在 = 今天的语义逐字节不变**：既有断言、七条既有冒烟与 B-016 的基线不被本轮扰动（与 `health`
  段、`rate_limit` 段同一立场；本轮之后是八条冒烟，新加的那条就是熔断自己的）。
- 新增一份**会被真跑的**示例：`deploy/gateway-circuit.json`（生产形状：`max_fails=3`、探活 1s、
  `max_ejection_percent=10`）。注意它配 2 个成员时 `floor(2×10/100)=0`——**这台组今天一只阀位都批不出来**，
  冒烟阶段 5 就拿这一格断"判据成立但被阀挡下、且挡下有账"（`blocked_by_valve=1`）。这不是示例写错，
  是 ADR-12 那条 floor 读法的必然结果；两台小集群想要摘除能力就得把比例调大，我不在实现里偷偷放宽成 ceil。
  `deploy/gateway.json`（被 ctest 读的那一份）**不加** health/circuit：`smoke-s3-02.sh` 的
  "后端自报 2/1/2"是靠上游的响应条数对的，装上探活就会往同一条分支上多打几条，那三格的含义就变了。

### 四、观测口径

退出账**一行一个键**（S4-04 那条教训：一行多键配行首锚 = 其余几格静默读成空串，而空串在判定里长得像 `0`）。

| 键 | 是什么 |
|---|---|
| `health_t<i>_<addr>_<port>_trips_rate` | 这台成员被**错误率判据**摘掉的次数（与 `_ejections` 并排读，才能把"谁摘的"分开） |
| `health_t<i>_<addr>_<port>_half_open_admitted` | 被钉进半开周期的请求条数（半开放行的**下界**证据） |
| `health_t<i>_<addr>_<port>_half_open_denied` | 预算已耗尽、后续请求在半开门口被挡的次数（**上界**证据的另一半） |
| `health_t<i>_<addr>_<port>_half_open_recovered` | 攒够证据、由半开转全量恢复的次数 |
| `health_t<i>_<addr>_<port>_half_open_reopened` | 半开期内失败或到期未决而回摘的次数 |
| `circuit_half_open_now` | 此刻处于半开的成员数（与 `health_ejected_now` 同口径：后者已含半开） |
| `health_all_denied_fallback` | 候选集全空 → 回退全员发生了多少次（不是"我没摘除"那一格的替身） |

启动横幅补一行 `circuit=on window_ms=… minimum_requests=… error_rate_percent=… half_open_requests=…/…`。
每请求成本（成功侧 1 次原子加、失败侧 1 次加 + 8 次桶读 + 判据比较、半开门只在半开成员存在时参与）归 **S4-08**
对 B-008 的 8.7 µs 与 B-016 的 p99 两把尺一起报，不在这里预先说"可忽略"。

### 五、状态还是一元

`HealthTable` 的 `ejected_until_ms` 改成语义更宽的 `state_ms`：**0 = 健康；非 0 = `(到期单调毫秒 << 1) | 状态位`**，
状态位 `0 = 摘除`、`1 = 半开`。三个状态仍由**一次 CAS** 迁移——"这个成员现在处于哪个状态"不允许有两个答案，
这条是 S3-03 立的，本轮只是把词表从两个词扩到三个词。时间戳两个口径也不变：决策用单调毫秒，
`last_ejection_epoch_ms` 收墙钟毫秒（摘除耗时与恢复时间线的"网关自报那一端"必须与脚本的墙钟轴同一根，B-014 的口径）。

到期还没被扫到的摘除，在读侧按"该进半开"处理，由读到它的那个人做那次 CAS 迁移。
**这不是新立的规矩**：`note_failure` 今天就在做"到期未扫顺手恢复掉，再按健康路径走"，读侧顺手做迁移、
CAS 输家不做账，形状一模一样。区别只在于迁移的目标状态从"健康"换成了"半开"。

### 六、我放弃什么

- **请求级立刻 503 的第三种"熔断拒绝"**（不试上游、在入口就拒）：那是 ADR-22 立场的反面，且今天没有实测逼我。
- **窗口分桶数做成配置项**：见第一节，固定 8。
- **滑动百分位、慢调用率**：超时已经是独立判据（S4-01），不为一台"慢但诚实"的后端再造一把尺；
  S3-05 矩阵里"慢在超时线内不摘"那条裁决在窗口判据下同样成立，本轮不改它。
- **per-worker 的错误率窗口**：窗口是"这台后端怎么样"的事实，共享原子表就是它的家（先例：健康表、`ReactorStats`）；
  per-worker 会给出 N 份答案，而熔断只需要一个。
- **把恢复出口唯一化**（探活判活也只推进半开）：见下一节，这是一条**明知而留着**的弱点。

### 七、与 S3 矩阵的边界（S4-05 验收点名的那句，两半都在这里）

**（一）"半开"这个词在本仓库有两个不相干的意思，文档必须分开称。**
S3-05 五类故障里的"半开"是**上游的**行为：`connect 成功但不回字节`（ADR-13 那一格注入形态，实测摘除 5280 ms）。
本节的"半开"是**熔断器自己的状态**：摘除期满后只放 B 条探测请求。两者不是同一件事，
命名上我叫它们「上游半开（连上不回字节）」与「熔断半开态」；INTERVIEW 里被问到这两个词的区别，
答案就是这一节。混称的代价不是不好看，是 S3-05 那张矩阵的读数会被读成"熔断器在半开期放了 5280 ms"。

**（二）节点级摘除与请求级熔断判据是同一台机构的两个输入。**判据（连续失败 / 错误率窗口）在 `route/HealthTable` 里，
采集点在 `net/Reactor` 里（S3 那一节说的"状态与决策 vs 探测"的分界没动），执行（CAS 摘除 + 安全阀）与 S3-03 一字未改，
恢复的门也长在同一个状态位上。S4-05 没有新增第二种"死"。

**（三）两条恢复出口今天仍并存，这是一条已知弱点，照记不藏**：
- 摘除到期 → 半开 → 攒证据 → 全量（本节升级了的那条）；
- 主动探活判活 → **立即全量恢复**（S3 已裁第三条③的判据原文，本轮**没动**）。

没动它的理由要说清：`probe_interval_ms` 这个值本身在已裁第四条里定义为"探活间隔"，而 S3 时代对它的实测
（B-014 摘除 202 ms、§12 恢复 89–129 ms）全都是按"探活成功即恢复"跑出来的。把探活接进半开门，
等于把那两份已归档读数的语义换掉，而我不回头改已记的数。
**后果我读得见**：只要 `probe_interval_ms` 配得比 `fail_timeout_ms` 短，到期那条路通常还没走到就被探活全量放行了，
半开在**这种配置下是弱路径**。所以本轮的取证必须按半开真正生效的配置去做：`probe_interval_ms = 0`（纯被动，
S3-03 本来就把探活做成可关的）与"探活失败但业务能通"两类形状——S4-05 的端到端用例与冒烟脚本就在前者下面跑，
显式断言"摘除期满后的周期里被钉进 1..B 条、而不是全量"，这是实测出来的下界，不是推断。
要不要把两条出口并成一条（探活判活也只推进半开），留给 S4-07 矩阵第二轮按"摘除耗时 / 恢复耗时"重新量一次再裁。
**2026-11-02 项目所有人裁定：照此执行**——S4-05 不动探活语义，**S4-06（重试）也不许顺手改**；
它是 S4-07 的实测对象，不是某一轮的附带清洁。

> **S4-07 就地标注（2026-11-02）**：上面这段（三）里"主动探活判活 → 立即全量恢复、本轮没动"这一句
> **与 shipped 二进制不符**——装了 `circuit` 时探活把成员叫醒到**半开**，不直接放回全量
> （`src/route/health.cc:160-163`、`tests/health_test.cc` 的 `ProbeSuccessWakesIntoHalfOpenNotFullTraffic`、
> 矩阵实测 9a 臂：摘除 15 次、半开放行 16 次、`recoveries=1` 逐数等于 `half_open_recovered=1`）。
> "两条出口并存"没有作废，但它的**真实适用面是没装 `circuit` 那一档**。原文一字不改（那是 S4-05
> 起草那一刻的意图，而 S4-05 的 TASKS 行里已经写了"探活判活改提前进半开"——两份说法分叉了，
> 本轮按实测合并）。裁定、代价与由此量出的新边界都在**追加三**，取数在 FAULT-INJECTION §18.4。

### 八、判据形状：四条判据每条都配对

ADR-12 追加一与 ADR-19 追加二用一次实测教过的形状是：**只看上界的断言挡不住退化实现**
（"从不摘除"的实现误摘率恒等于 0，"取环上第一个点"的实现迁移率读到 0.00%）。本节四条判据全部按成对写：

| 判据 | 上界那一半 | "确实发生过"那一半 |
|---|---|---|
| 错误率窗口 | 样本不足、或错误率低于阈值时**不许摘** | 窗口内达标的那台成员**被摘 ≥1 次**（`_trips_rate ≥ 1`） |
| 半开放行 | 一个半开周期内钉进该成员的请求**≤ B** 条 | **≥1** 条（否则"半开从不放行、把恢复锁死"的退化实现也能过） |
| 半开成功 | 攒不满 K 条**不许**全量恢复 | 攒满 K 后**确实**回到全量（`_half_open_recovered ≥ 1`，且恢复后它接到的请求数 > B） |
| 半开回摘 | 半开期内一次失败即回摘（不再攒 `max_fails`） | `_half_open_reopened ≥ 1`（回摘真的发生了） |

四处阳性验证与这四行一一对应：摘掉错误率判据分支 → 用例红；半开门不夹预算 → 红；到期不迁移半开
（= 退回旧语义）→ 红。逐条读数在 FAULT-INJECTION §15。

## 追加三（2026-11-02，S4-07 矩阵第二轮）：第二条出口的真实适用面、一条新边界、以及"要不要并成一条"的裁定

### 这一节在裁什么

第七节把"两条恢复出口要不要并成一条"交给 S4-07，条件是**按重新量出来的摘除/恢复耗时再裁**。
本轮量完了，裁定是**不并**。但本节的主要产出不是这句裁定，而是两处更正：
裁定所依据的那句现状描述（"探活判活 → 立即全量，本轮没动"）**与 shipped 二进制不符**；
而顺着这条不符往下量，逼出一条我在追加二里没写过的边界（本节第三节）。

取数全部来自 FAULT-INJECTION §18.4：同一个注入形状（坏台**业务恒 503、探活路径 200**）、
同一份流量（40 条 / 60 ms 涓流，另有一组 40 条突发），**只差装配**。

### 一、实测到的现状（不是意图，是读数）

| 装配 | 摘除 | 半开放行 | 全量恢复 | 暴露面（坏台自己数的 503） | 恢复耗时 |
|---|---|---|---|---|---|
| `health`(probe 100) + `circuit` | 15 | **16** | `recoveries=1` **逐数等于** `half_open_recovered=1` | 20/40 | 94 ms |
| `health`(probe **0**) + `circuit` | 3 | 4 | 1 | 8/40 | 95 ms（上一轮同一臂 252 ms） |
| **只装 `health`**(probe 100)、`max_fails=2` | 涓流 **0** ／ 突发 6 | 0 | 突发档 `recoveries=6` == 摘除 6 次 | 涓流 **20/40 且永不停** ／ 突发 12/40 | 95 / 15 ms |

三句话读它：① 装了 `circuit`，**每一次解除摘除都经过半开那道门**，探活那 40 次判活一次都没把
成员直接放回全量——所以"两条出口并存"在这一档**已经不成立了**；② 只有不装 `circuit` 时，
探活才把成员**从摘除直接放回全量**（`recoveries == ejections` 就是这条口的收据）；
③ 合并这条口的代价在有流量的时候**读不出来**（94 ms vs 95 ms 同带）。

### 二、我裁定：不并，且没有新任务要立

1. **装了 `circuit` 的配置里两条出口已经并了。** 这条裁定不是在对一个意图投票，是在对一个
   已经落地、并且被 `ProbeSuccessWakesIntoHalfOpenNotFullTraffic` 钉住的实现事实签字。
   再"并一次"只会制造第二份真相。
2. **没装 `circuit` 的那一档里没有"半开"这个状态可去。** 半开位、门与预算都由 `circuit` 段的
   装配决定（追加二第五节、ARCHITECTURE 1.31 第二节）。要把探活改成"到半开"，等于要求所有
   `health` 配置都必须装 `circuit`——那是把 S3 已裁第三条③的判据原文换成另一个功能开关，
   并且会作废 §12 那五类与 B-014（摘除 202 ms、误摘 0/3480）这两份按"探活即全量"跑出来的
   归档读数。**我不回头改已记的数**这条立场，在这一档仍然成立。
3. **没有实测逼这件事。** 代价读不出来（94 vs 95 ms），收益（门管着每一次解除）已经在位。

**代价照记**：不并就意味着"只装 `health`"那一档继续保持追加二第七节没有覆盖到的那个形状——
见下一节。这条代价不由"并口"解决。

### 三、新边界（本轮量出来的，S4-05 那份追加二里没有这一条）

**只装 `health` 且开着探活时，一台"探活会答、业务恒 503"的成员，在业务失败比探活稀疏的流量下
永远摘不掉。** 实测（9c）：`ejections=0`、`probe_ok=40`、这台自报接了 **20/40 条 503 且永不停**；
把它换成突发流量（9e）就摘得动（6 次）——**所以这条边界的准确表述是节奏，不是"能不能"**：
落到这台的业务失败约每 120 ms 一条，而探活每 100 ms 把连续失败计数**清零**一次，
`max_fails=2` 永远够不着。

机理是两条已裁规则撞在一起，不是哪一条写错：

- 已裁第三条④说"探活失败与业务失败汇入**同一个连续计数**"（汇合点在摘除出口）——这条对；
- `note_probe_result(alive=true)` 会把这个计数清零（`health.cc:145`）——这条也是 S3-03 立的，
  而且 §12 类 5 正是靠它把"探活死、业务活"的成员摘掉的。

**与类 5 合起来才是完整的一对**：探活只能证明"这台机器会答 `/probe`"，不能证明"它能服务业务"。
S3 的连续判据把前者当成了后者，于是类 5 那一格摘得掉、反过来的这一格摘不掉。
唯一不被探活清零、且**探活样本根本不进**的判据是错误率窗口（追加二第一节、ARCHITECTURE 1.31），
而窗口长在 `circuit` 段上——所以"只装 `health` 就够"这句从 S4 之后要补一个限定条件：
**它不覆盖"探活活、业务死"这一形状的稳态**。

- **处置**：不改实现。这不是缺陷，是已裁判据在没装第二个判据的那一档下的固有覆盖面；
  收窄它的方式是**装 `circuit`**（配置动作，不是代码动作）。本轮 `src/` 一字未动。
- **要补的可见面**：README 与 S5 的 Grafana「上游健康度」那一栏，不能把 `health_ejected_now=0`
  读成"没有坏后端"——它在这一档下读不出业务比率。这条记进 S5 的拆解（不在本轮做，禁令一）。
- **不在本轮做的事**：往 `health` 段里塞一个比率判据。那等于把 `circuit` 的功能搬进 S3 那个段，
  而 9c 的代价我刚刚选择照记而不是改代码——两头不能都要。

### 四、判据形状：本节三条说法各自的"确实发生过"那一半

延续第八节那个成对写法（只看上界挡不住退化实现）：

| 本节说法 | 钉住它的实测格 |
|---|---|
| 装了 `circuit` 后探活不再直接放回全量 | `recoveries(1)` **逐数等于** `half_open_recovered(1)`，而 `ejections=15`——若探活走全量，`recoveries` 会跟着 15 涨 |
| 不装 `circuit` 时第二条出口在跑 | 9e：`ejections=6 == recoveries=6` 且 `admitted=0`（这条口的收据由它自己的计数交出） |
| 9c 那条边界是"节奏"而不是"从不摘除" | 同一配置的突发档 9e 确实摘了 6 次——**否则这条边界读起来就像"熔断永不生效"** |
| 合并的代价读不出来 | 9a 94 ms vs 9c 95 ms 同带；而 9b（纯被动）也 95 ms，说明这一段耗时的主项是"攒满 K 条业务成功"而不是"等到期" |

### 五、S4-07 之后仍然挂着的事

- B-013 那两臂 `least_conn` 仍是**修前读数**（S4-06a 已就地标注，S5 引用前要重跑）。
- 每请求成本（限流 / 分布式 / 熔断 / 重试四件，对 B-008 的 8.7 µs 与 B-016 的 p99 两把尺）
  归 **S4-08**，本轮一条都没量。
