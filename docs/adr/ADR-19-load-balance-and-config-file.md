# ADR-19 · 负载均衡三策略 + 上游节点表与路由表的配置文件格式

- 状态：已采纳（S3-02 落地本 ADR；健康检查与摘除安全阀归 S3-03，MySQL 节点表归 S3-04）
- 日期：2026-10-29
- 相关：ADR-18（链的写回通道、池按目标分桶、干净边界换目标）、ADR-15 及其追加节、ADR-14（**本 ADR 不扩大它的跨线程接触面**）、ADR-16（响应 FIFO 决定"什么时候才允许换后端"）、ADR-11（顺序 = 配置顺序）、契约 1.3（不引第三方网络库；引依赖要先写 ADR）、`docs/ARCHITECTURE.md` 1.21/1.23、`docs/ROADMAP.md` 的 S2 债表

## 这一节在问什么

S3-01 之后一条路由只能对应**一个**目标下标。真实形态是一条路由后面跟着**一组**后端，于是三问：

1. **这组后端从哪来**——命令行已经装不下（`--upstream` 是一个扁平端点列表，没有"组"和"策略"的概念），所以要有一个文件。文件的格式是什么、由谁解析。
2. **组里选哪一个**——轮询 / 最少连接 / 一致性哈希三种，各自的状态放在哪一层（进程共享？worker 私有？连接对象上？）。
3. **选错了怎么知道**——一致性哈希最容易被写成"引用一条性质"（"N→N+1 只迁移 1/(N+1)"是**教科书结论**，不是我量到的数）。

## 我选择什么

**一、配置文件只描述"节点表 + 路由表"，进程形态仍然归命令行。**

`--config <path>` 读一个 JSON 文档，结构定死成三层（字段名就是文档里的那几个，多一个都不认）：

```json
{
  "upstreams": [
    { "name": "api",
      "balance": "round_robin",
      "targets": [ {"address": "127.0.0.1", "port": 18081},
                    {"address": "127.0.0.1", "port": 18082} ] },
    { "name": "shard",
      "balance": "consistent_hash",
      "hash_key": "target",
      "vnodes": 160,
      "targets": [ ... ] }
  ],
  "routes": [
    { "match": "prefix", "pattern": "/api", "upstream": "api" },
    { "match": "regex",  "pattern": "/v[0-9]+/orders", "upstream": "shard" }
  ]
}
```

**监听地址、监听端口、`--workers`、fd 预算、停读线、排水窗口一律不在文件里**，仍是命令行参数。理由不是省事：那些是**进程形态**（这一个实例跑成什么形状），路由与节点表是**策略**（这个实例怎么决定请求去处）。把它们混进同一份文件会立刻造出第二份真相——`--workers` 与文件里的 worker 数谁赢这个问题一旦存在，我就得写一段"合并规则"，而合并规则是迟早被人改错的地方。**代价照记**：S5 做热重载时，"策略能热、形态不能热"这条边界必须显式写进 S5 的验收，别到时候假装一份文件能重载整个进程配置。

**这条切分同时保住了门禁证据**：S1/S2/S3-01 的全部冒烟与压测复现命令都只传 `--listen/--upstream/--workers`（B-007、B-008、B-012 的复现行都是），没有一个传 `--config`。**不传 `--config` 时行为逐字节等于 S3-01**：`--upstream` 的扁平列表变成"一个匿名组、策略 `round_robin`、路由表为空但有一条隐式 catch-all"——

> 等等，这里必须写清**隐式 catch-all** 的确切含义，否则它是第二个真相：不传 `--config` 时**不装** `RouteFilter`，也不装 `LoadBalanceFilter`，链是空的，回源走 `Reactor::Config::default_target`（就是 S2-06a 的 `i mod E`）。**没有"隐式路由"这回事**，"行为等于 S3-01"是靠"一环都不装"实现的，不是靠造一条没人看见的规则。

而 `--route` / `--route-regex` 这一对临时开关**由文件取代、不留兼容层**（S3-01 的 ADR-18 已经预告）。取代的方式是硬的：`main.cc` 里删掉这两个分支，传了就是"无法识别的选项"退出码 2。留兼容层等于让同一件事有两种配法，而 S3-02 的成本对照与 S3-05 的故障注入只会各测一种。

**二、解析器在本仓库里手写，只支持一个 JSON 子集；不引入第三方 JSON 库。**

契约 8.2 禁令三说任何新依赖都要先写 ADR，而**这份 ADR 就是那个位置**——我的结论是不引。三条理由：

1. 我要的不是"能读 JSON"，是**读不出就整体失败**。子集自己写，严格性才有地方表达：未知字段、重复键、类型不对、`balance` 取了三值之外、`targets` 为空、`vnodes` 非正、数组里混进非对象元素——每一条都必须是**拒绝**而不是忽略。这条立场的原型是 `max_header_count` 那次（"配置写了、代码没读"）和 `--upstream` 那条（"配置写错不该退化成少连一个上游"）。
2. 子集边界写死，不承诺兼容任意 JSON：只接受对象/数组/字符串/十进制整数/`true|false`/`null`；字符串里的转义只认 `\"` `\\` `\/` `\b` `\f` `\n` `\r` `\t` 与 `\uXXXX`（且 `\uXXXX` 只允许落在 ASCII 可打印范围里出现在 `pattern`/`name` 之外——写复杂了就是自找）；不接受注释、不接受 NaN/Infinity、不接受顶层标量、不接受尾逗号。
3. 面很小：一个 ~200 行的下降式解析器 + 一张"字段→类型"的校验表，用例比解析器本体长。它的正确性由**用例**兜，不由上游库的声誉兜（这条与"网络层自研"是同一个立场：契约 1.3 禁第三方网络库的理由——核心考察点——在这里同样适用，因为配置校验是网关的**安全责任**之一）。

**放弃的东西也写清楚**：我**不**做 YAML（Envoy 那种），因为那要么再写一个解析器、要么引一个库，而收益只是"少写几个花括号"；**不**做 schema 文件（JSON Schema 是另一套要实现的东西）；**不**做 include/import。

**三、链上是两个 filter，不是一个：`RouteFilter` 决定"哪一组"，`LoadBalanceFilter` 决定"组里哪一个"。**

`RequestInfo` 因此再加**一个**字段，而且它的读者就在下一环：

```cpp
std::uint16_t upstream_group = route::kNoUpstreamGroup;   // 0xfffe = 没人决定过组
```

- 为什么不把两件事写进一个 filter：路由是**纯函数**（ADR-18 第三节），负载均衡**天生有状态**（游标、计数、环）——把有状态的塞进纯函数那一层，1.23 那条"规则语义用例能在不建 socket 的文件里跑完"的性质当场作废，S3-03 的健康检查也没地方插（它要的是"这一组里现在谁可用"，不是"这条请求属于哪条路由"）。
- 为什么不复用 `upstream_target` 那一格让 RouteFilter 直选：**顺序 = 添加顺序**这条链口径的意义就在于每一环只做一件事；直选意味着路由表里要嵌进策略，而策略是**组**的属性、不是**规则**的属性（两条规则指向同一个组时，它们必须共享同一个游标——这正是"一份真相"的位置）。
- 顺序写死：**路由在前、均衡在后**，由配置数组的顺序表达。S4 的限流放前放后是它自己的取舍（ADR-11 那条"不存在无条件正确的顺序"），但路由必须在均衡之前——没有"哪一组"就没有"组里选谁"。
- **环与游标都在装配期建好**：一致性哈希环是 `vector<pair<uint64_t,uint16_t>>` 排序一次、运行期只读；轮询游标与配对计数是**每 worker 一份的普通整数**，只被该 worker 的循环线程碰。**所以本 ADR 没有扩大 ADR-14 的接触面**，而它的可证伪形式仍然是 `tsan` preset 零 data race。

**四、最少连接数的那把尺，我量的是"配对数"，不是"请求数"。**

`per-target 当前被配给下游的上游连接条数`——借出/新建 +1，归还进桶或被淘汰 −1（这两个时机已经在 `take_pooled_upstream` / `recycle_upstream` / `evict_pooled` 里，我不新造第三个记账点）。为什么不数"在飞请求"：ADR-15 定的配对是**下游存活期独占**，一条下游挂着 3 条在飞请求时它对那个后端的占用就是 1 条连接，而 nginx 的 `least_conn` 数的也是 active connections 而不是 requests。数请求会造出第二把尺，而**两把尺迟早量出两个答案**。

**五、一致性哈希的参数在文件里，不是在我的默认值里。**

- **哈希函数：FNV-1a 64 位**，offset basis `0xcbf29ce484222325`、prime `0x100000001b3`，自己实现（30 行，无依赖）。为什么不用 `std::hash`：它的结果**跨实现不保证稳定**，而"同一 key 恒定同一后端"和"N→N+1 的迁移率"这两条判据一旦依赖一个我控制不了取值的函数，报告里的数就变成"在我这台机器的这一版标准库上成立"。**锁死常量的代价**：换哈希函数等于换掉所有 key→后端的映射（迁移率 100%），这条必须写进文档而不是藏在代码里。
- **key 来源**：`hash_key` 取 `target`（原始 origin-form，与 ADR-18 同一个匹配对象）或 `header:<Name>`（大小写不敏感取第一个命中值）。默认 `target`。**为什么必须显式**：key 选什么决定的是"哪一批请求会一起搬家"，这不是实现细节，是产品语义。
- **vnodes 默认 160/后端**，可在组里覆盖。这个数字我给不出推导，只能给实测：**S3-02 的用例要在 N→N+1 时把迁移率量出来**，并把不同 vnodes 取值下的实测散布写进 BENCHMARK，而不是把 160 读成结论。
- **迁移率是量出来的**：用例形状 = 固定一组 key（10,000 个，从确定性的生成序列来，不用随机种子碰运气），N 个后端建一次环、N+1 个后端再建一次，统计"映射变了"的 key 占比，断言 **≤ 1/(N+1)**。**如果这条断言在 160 vnodes 下不成立，我改 vnodes 或者改哈希函数，不改判据**——判据来自本 ADR，不是从实测里挑出来的。

## 为什么

- **为什么不 shared 一份负载均衡状态**：`least_conn` 的"全局最少"要跨 worker 读同一张计数表，那是共享可变状态；ADR-14/15 已经为这件事付过一次学费（S2-02 定 per-worker 的决定性理由就是"shared 池会把跨线程销毁那一整类竞态放进来"）。所以**这里买到的均衡是 per-worker 的**，代价我写进下面的"我放弃什么"，不等 S3-06 才发现。
- **为什么把"组"做成名字而不是下标**：文件里 `routes[].upstream` 是**组名**，装配期解析成下标。用下标写配置的话，`upstreams` 数组一增删排序，所有路由静默改道（这正是 S2-06a 那条"端点数超过 worker 数不增加容量"教的东西——位置不是身份）。**代价**：引用不存在的组名必须整体失败，`main.cc` 里就多一条启动前校验（同 `validate_route_targets` 那一族的形状）。
- **为什么不预先为 S3-03 的健康检查加字段**：摘除会改变"组里谁可用"，那是 S3-03 的读者自己的事。今天给 `RequestInfo` 加一个 `candidates` 之类的容器，就是 S1-03 那次"配置写了、代码没读"的重演。**接口返工的时机与读者同批**——这条纪律在 ADR-18 里已经兑现过一次，不用口头再承诺一遍。

## 我放弃什么

- **全局最优的均衡**。per-worker 的游标与计数意味着：16 个 worker 各自轮询时，某个后端收到的连接数是 **16 个独立计数器的叠加**，瞬时可能不均。**这条不能读成"没问题"**：S3-02 的验收要报的是**按后端维度的实测分布**（M 条请求 ÷ N 后端落在 ⌊M/N⌋…⌈M/N⌉），而这个等式成立的场景是"单 worker 内多条下游"；多 worker 下我会**明写测到的是哪个形状**（同一条 keep-alive 上多条请求 = 一个 worker 内均衡；多条短连接 = 跨 worker 派发 + 每 worker 轮询的叠加），而不是拿一个单 worker 的用例冒充全局。
- **加权**（weight）。已裁边界：加权要先进本 ADR、再进 `TASKS.md`，而且必须**连带写清它与健康检查摘除的相互作用**（摘掉一个加权后端时，权重是重归一还是保留？这个问题一旦没有答案，`max_ejection_percent` 那个安全阀的"容量"分母就是含糊的）。S3-02 不做。
- **主备 / backup 池、慢启动、per-backend 连接上限、按请求的并发配额**。前四者都在"某个后端坏了/慢了"这条线上，那是 S3-03 与 S4 的边界（回源耗尽时的自产响应至今仍是 S4 的空格子，S3-02 不顺手填）。
- **配置热重载与"改文件不重启"**。切换策略不重启进程**不在 S3-02 范围**（已裁在验收句里），它是 S5 双 buffer + 引用计数那一格。今天文件只在 `start_listen` 之前读一次，运行期不改——这与链不许运行期改是同一条时序纪律。
- **给负载均衡单独新增产品侧计数**。"哪个后端收到几条"仍然由**被连的那一侧自报**（`TestUpstream::connections_accepted()`，S3-01 加的那格；真进程侧沿用 B-007 的 `accepted_by_addr=`）。我不给网关加"每目标请求数"这组分位——它的第一个真读者是 S3-03 的误摘率分母，那时按 ADR 引入。

## 后果与约束

- **验收句要的三个形状，各自的可断言形式**（原文在 `TASKS.md:206`）：
  - **轮询**：M ÷ N，**按后端计数**落在 ⌊M/N⌋…⌈M/N⌉。复用 S2-01 `DispatchIsRoundRobinBalanced` 的形状但换维度——那里断的是 worker，这里断的是 `connections_accepted()`/`requests_served()` 的逐后端读数。
  - **最少连接**：人为把某个后端压成高并发后它**确实少分到**。断言方向、不断绝对值（绝对值会被这台机器的时序牵着走）。
  - **一致性哈希**：同一 key 恒定同一后端（重复 100 次喂入，纯函数那一半）；N→N+1 **迁移率实测** ≤ 1/(N+1)。
- **阳性验证（每条都必须真打红，没红过的不算守着什么——这条是 S3-01 用一次"两条用例全绿"换来的）**：
  ① 把 `consistent_hash` 的环查找写成"取环上第一个节点"→ 迁移率用例必须红（它是那条唯一能证伪"我实现了哈希环"的用例）；
  ② 把轮询游标改成常量 0 → 分布用例必须红；
  ③ 把 `least_conn` 的比较换成 `<=`（或反过来）→ 方向用例必须红；
  ④ 解析器：把未知字段/重复键/空 `targets` 三种输入各打一遍，**必须三种都是启动失败**，而不是"少配一条路由照样跑"。
- **与 S3-01 那三格的接口不能含糊**：目标切换仍然只在干净边界上发生（`in_flight==0` + `outbound_pending==0` + `upstream_reusable`）。**负载均衡让这件事变常见了**：同一个组里轮询意味着同一条 keep-alive 的下一条请求大概率换后端，于是那条路径从 S3-01 的"边角"变成主路径。`pump_response` 那次重驱动的负载会上升，所以 **B-012 那条成本对照在 S3-02 结束时必须重跑一次**（空链 vs 路由 vs 路由+均衡，同机交替 ≥2 轮）——这是本 ADR 给自己加的一条，不是验收句写的。
- **`sizeof(Connection)` 仍然不许变大**（S3-01 立的那条 `static_assert`）。组下标存在**路由表**里、不存连接对象上；`Connection` 已经有目标下标那一格，够它认自己的桶了。
- **`--config` 传了但读不到/解析不过**：退出码 2 + 一条指出**哪一个字段**的 stderr 消息。绝不"退回默认配置继续跑"（那条立场在 `--upstream` 与 `--route` 上都表过态：一个能安静退化成"少配一点"的网关，它的观测面看起来只是负载不对，不是配置错了）。
- **deploy/ 里要有一份能直接跑的示例配置**（契约第 7 节矩阵对"配置文件字段变化"的完成判据：示例配置能直接跑通）。`deploy/` 目录今天还是空的，这一格在 S3-02 收尾时补上最小的一份（一个组两个后端 + 两条路由），并用它跑一条冒烟证明"直接跑通"是真的。

## 追加（2026-10-30，S3-02 落地时）：环上的哈希函数换了一道终值

**这条是本 ADR 第五条自己预留的旋钮**（"如果这条断言在 160 vnodes 下不成立，我改 vnodes 或者改哈希函数，不改判据"），不是新决策，但既然动了 `src/`，就得记在同一份 ADR 里，不然读代码的人会以为环上用的还是裸 FNV-1a。

**发生了什么**：点键 `组名#序号#端点` 里，同一个组的成员之间只差末尾那截端口号。FNV-1a 是逐字节 `h = (h ^ c) × prime`，只差末位字节的两个输入，哈希值相差约 `Δ × prime`——相对 2^64 是 6e-8 量级。于是每个成员的 160 个点各自挤成一簇，环不是"均匀撒点"。实测（`S3_02_MigrationRate.AddingOneBackendMovesAtMostOneInNewTotal`，10,000 个确定性 key，把这行实现换回裸 `fnv1a64` 就是这组数）：**N=3→4 迁移率 48.10%、N=7→8 迁移率 40.10%**，而理想界是 25% 与 12.5%。

**为什么不是抬 vnodes**：同一组输入把 vnodes 从 160 抬到 1000、10000，迁移率是 45.77%/48.39% 与 47.22%/52.74%——**一点都不改**。因为簇数由成员数决定、簇宽由"末位差异 × prime"决定，两者都不随 vnodes 变；vnodes 只往每个簇里加点。这条实测否掉了 ADR 给的第一个旋钮，所以我走第二个。

**改成什么**：`ring_hash(text) = mix64(fnv1a64(text))`，`mix64` 是 splitmix64 的三步移位-乘法。**FNV-1a 那两个常数一个字没动**（`S3_02_Fnv1a64.MatchesPublishedTestVectors` 仍按发布向量钉着它们），加的是它后面的一道终值。**key 与点必须走同一个函数**：只混点不混 key，等于拿一把没刻度的尺去量一把被拉直过的尺——URI 之间也常常只差末位（`/orders/1` vs `/orders/2`），裸 FNV 会把它们同样挤成一簇。改完同一条用例的读数是 **24.41% / 11.11%**，两条都在界内。

**代价，按第五条那句原样付**：换哈希函数等于换掉所有 key→后端 的映射（迁移率 100%）。S3-02 落地时线上一条存量流量都没有，所以这笔代价今天没有付在真实请求上；**但它以后每次都要付**——这道终值不是可以"顺手再改得好一点"的东西，换它等于一次运维事件。

## 追加第二条：`≤ 1/(N+1)` 是期望，不是上界（判据要配对才成立）

阳性验证里发现的一件事，必须写进这份 ADR，否则下一个读到判据的人会照着它写出一条**挡不住退化实现**的断言：把环查找改成"取环上第一个点"（`return ring.front().second`），N=3 那档的迁移率是 48.10% → 红；但 **N=7 那档读到 0.00%，反而"满足" ≤ 12.5%**。原因很直白：所有 key 都不再参与选择时，两张环给出的映射*处处相同*，差集是空集。**一条只看上界的断言挡不住"哈希根本没生效"。**

所以本 ADR 把这条判据读成**一对**：上界（`S3_02_MigrationRate`，量的是搬家比例不能失控）**加上散布**（`S3_02_LoadBalance.ConsistentHashPinsTheSameKeyAcrossConnections`，一批 key 不许全落在同一台后端上，量的是选择真的发生了）。散布那一半的样本数是 **24 个而不是 6 个**，理由写在那条用例旁边：压测与单测里的端点串带着端口号，而夹具端口是内核选的，样本太小时"别全钉一台"就成了一枚每轮重掷的硬币。

**同时记一条不好看的余量**：N=3→4 这一档实测 24.41%，界是 25.00%，**余量只有 0.59 个百分点**。因为界的值就是这个分布的期望，所以任何端点串的组合都有约一半概率测出略高于它的数——这不是实现有毛病，是"单次采样 ≤ 期望"本身是个掷硬币命题。今天没有改判据（改判据要重新裁），只把这个性质写在这里，等 S3-03 的误摘率那类需要"多次读数"的判据时一并处理。
