### 一句话门禁判定

**转发链、响应语义、背压动作、策略插入点这四件事在 S1 都成了可断言的命题**，而且每一条都有反证（sanitizer 会报警、`read_disarmed_connections` 会等于 1、TSan 会红、`✗` 计数不是 0 时脚本会失败）。**SLO #1 没有达标**（四份取样 30–38 ms 量级 vs 目标 1.0 ms）；**SLO #2 连测量条件都还没凑齐**（100k 长连接要 S2 的连接模型 + `ulimit`）；**SLO #3 有基线读数、判定暂缓**——nginx 原始态 9,147.69 vs 网关 18,854.32 = 206%，卡住它的不是代码也不是环境，是**测量条件不齐**：容器只能走端口发布（实测 `--network host` 不共享本发行版命名空间、bridge IP 不可路由），分母因此被压到同一上游直连（56,332.52）的 16%，而我自己写的 proxy 配置里那 206% 对**我**乐观。这四句话是 S1 门禁的全部结论，多一句都没有数支撑。

### S1 实测暴露出来的、S2 必须处理的债（每条都指向一个数）

| 债 | 实测证据 | 为什么归 S2 |
|---|---|---|
| 单 Reactor 的排队放大 | 增量 p99 30–38 ms，而 `延迟 ≈ 连接数/QPS` 两组都贴合到 1.4–3.6% 内；50 并发对照下增量只有 1.370 ms（每请求成本 ≈36 µs 不变） | 分摊并发 = 多 Reactor + 连接池，就是 S2 的全部内容 |

| 每连接内存有一笔没归因的差额 | 128 条空闲从 S1-06 的 5.31 涨到 S1-07 的 **5.81 KiB/连接**，而对象只涨 8 B（`sizeof=520`） | SLO #2 的判定要到 100k 才做。**外推值 2026-10-27 重算并纠错**：0.5 KiB × 100k = **≈49 MiB**（原文写"决定 50 GB 还是 51 GB"错了三个数量级，已改），相对 100k 规模应有的 ≈1.9 GiB 是 **2.5%**——**问题不在量级，在于"每连接内存的构成"这张表上有一个空项，而这条 SLO 判的就是它**。**2026-10-28 第一次有大规模实测锚点（S2-06，25,000 连接对）**：稳态增量 436,748 KiB → **17.47 KiB/对**（= 2 个 `Connection` + 两侧缓冲，≈8.73 KiB/对象），散布 0 KiB；外推 100k 对 ≈ **1.71 GiB**，与上面那句"≈1.9 GiB"同量级、**这条外推从此有实测起点了**。注意**别把 17.47/2 与 5.81 当成同一个数**：5.81 那一档是 128 条**只有下游**的空闲连接，17.47 这一档每条配对含一条上游连接与它的缓冲，两个口径的分母不同（构成表要拆开的那一格正是这个）。归掉那 0.5 KiB 空项与出构成表仍归 **S2-07**；而 #2 的 100k 判定**已经交了**——S2-06a（ADR-17 候选 A：端点列表 + per-worker 静态映射，135/135、tsan 零 race）把回源容量从 28,232 抬到 `min(N,E)×28,232=112,928`，**B-007 实测 100,000 连接对 → 17.47 KiB/对 + 空闲 CPU 占单核 0.22% → 两格都达标**（`measurable=1`、`established=100000/100000`、每端点实测 25,000 条）。四倍规模下与 25k 档逐位相同，所以"线性"现在是实测不是外推；外推的 1.71 GiB 与实测 1.67 GiB 差 2.5% |
