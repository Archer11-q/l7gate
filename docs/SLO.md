# SLO —— 三个数字，本项目的全部价值锚点

> 契约第 2 节的铁律：任何 C++ 项目说不出这三个数字就是空壳。本项目做得更深一层——**三个数字全部以 Nginx 同环境实测为基线做对比**，不由公开数字推算。

## 记录格式（未达标照记，格式固定）

```
实测 <值> / 目标 <值> / 达标|未达标 / 归因 <定位到具体机制，不是形容词>
```

达不到就写「未达标」并给归因。**实测不达标而如实记录，价值高于达标但说不清来源。** 归因写不到具体机制（解析、分配、连接管理、写盘、syscall 次数中的哪一项，量级多少）就不算完成。

## 测量条件（写死，改动任何一条都要在 BENCHMARK.md 里显式声明）

三个数字都不许脱离测量条件单独引用。

**取样规程（2026-10-26 裁决采纳，自 S2 起强制；只加纪律，不动任何目标值）**：判断"某次改动有没有改善数字"，必须**同机交替、每个改动至少两轮**，报告里给出**极差**（同一份代码两次读数的最大偏差），并且把"两轮之差"与"改动预期效果"放在同一张表里比。理由不是理论，是 S1 收尾量到的实测散布：同一份 binary 复跑，直连 p99 自己漂了 **11.3%**、四份增量极差 **27%**、#3 比值两轮复现是 206.11% 与 203.74%（差 1.2%；更早那次 158% 是被测方被环境拖慢的作废轮）。在这种带宽下，单轮读数说"变快了 7 ms"没有任何证据价值——**没有这条规程，S2 的多 Reactor 改动会产出一堆无法证伪的"成功"，而基于它们做的后续决策会一路错下去。**

### #1 转发尾延迟

- 同机回环（`lo`），网关与上游同机部署，排除物理网络抖动
- 响应体 **1 KB**，固定不可变
- HTTP/1.1，keep-alive 开启
- **1000 并发连接**
- 稳态采样 **60 s**，预热不计入
- 测的是**增量**：同一负载下「直连上游」与「经网关转发」的 p99/p999 差值。原始 p99 单独记录，但达标判定只看增量
- 工具：wrk（`--latency`）与 hey 交叉验证
  - **这套第三方工具的覆盖范围到 99% 为止**：wrk 4.1.0 的 `--latency` 只打 50/75/90/99 四行，hey 0.1.4 的分位表只到 99%。所以 p999 ≤ 5.0 ms 这半边**在 2026-10-28 之前是无法判定的**——不是没跑，是取不到那个分位。
  - **p999 的取数方案已于 2026-10-26 裁决、并于 2026-10-28（S2-06）落地**：在**自研 C100K 长连接客户端**里做 HDR 分位统计（SLO #2 本来就要自研这个客户端，见契约 1.3 唯一允许自研压测客户端的场景），不引入 wrk2/vegeta 之类第三方依赖。落地形态：`l7gate_c100k --requests-per-conn N`（**闭环请求形态**，每连接一次只在飞一条，量的是**每请求**转发延迟；默认的隧道空闲形态量的是握手，两者不是同一个物理量，别拿后者填这一格）。记录已就位（B-006 结果三），**判定仍要等 S2-07 按取样规程出增量、1000 并发、≥2 轮**那一份。方案记录在 `docs/adr/ADR-17-c100k-hdr-measurement.md`。
- **演示面上那一格 p99/p999 从哪儿来（S5-03，`docs/adr/ADR-25-bench-percentile-exporter.md`）**：网关自己不产分位——`/metrics` 那 101 个键全是整数计数，没有一格是时延（ADR-24 裁「分位由客户端自己算」）。Grafana 第 2 格读的是 `tools/l7gate_bench_exporter` 从 `build/bench/<批>/s1-p99.summary.txt`（wrk，只到 p99）与 `s1-p999.summary.txt`（`l7gate_c100k` 的 HDR 桶，≈128 µs/请求）搬来的**已落盘读数**，每条 series 带 `canonic`/`conns`/`batch`/`observer_cores`。**这一格只是把上面那两条线搬到眼睛前面，不新增测量条件、不产生判定**：#1 的达标判定读的仍是本节写死的五条参数与 BENCHMARK 的落盘记录；`canonic=0` 的批次在图上可区分，不得当判定读。**S5-07 已把标准档的落盘摘要产出来**（`canonic=1` 的
`s1-p99.summary.txt` 在 `build/bench/s5-07-p99-w{1,16}-r*`、`s1-p999.summary.txt` 在
`build/bench/s5-07-p999-c1000long-w16-r{4,5}`，长窗档那两发就是面板第 2 格等的那条曲线），
面板那一格读的仍是这些盘上文件——**它仍是眼睛不是账本**：#1 的判定读 B-021/B-008 的落盘记录，不读图。
- 环境前置：CPU 绑核方案、内存分配器、全部组件版本号（见 ENVIRONMENT.md 第 7 节）
  - B-001 的落实：分配器已记录（glibc，`LD_PRELOAD` 空）、组件版本号已由 `scripts/bench/env-snapshot.sh` 一次性落盘、**绑核未做**（WSL 下 cpufreq 接口不可读，方案按 ENVIRONMENT 第 7 节留到 S4）——这条偏差在 BENCHMARK.md 里显式声明过，不是遗漏

### #1 首次记录（2026-10-26，B-001，`canonic=1`）

```
实测 增量 p99 = 57.540 ms（直连 24.850 / 经网关 82.390，wrk 1000 并发闭环）
目标 增量 p99 ≤ 1.0 ms
未达标
归因 三层，逐条有数：
  (1) 闭环排队主导——wrk 是"发一条等一条"，稳态下 延迟 ≈ 连接数/QPS：
      直连 1000/59,860 = 16.7 ms ≈ 实测 p50 16.35 ms；经网关 1000/18,229 = 54.9 ms ≈ 实测 p50 53.35 ms。
      所以 57.5 ms 这个差值读作"服务速率赤字被 1000 并发放大成排队"。
  (2) 每请求成本 ≈ 38 µs（网关瓶颈线程 54.9 µs/请求 vs 直连上游 16.7 µs/请求）。
      对照实验：并发降到 50（B-002，非标准口径、不作判定）时增量 p99 从 57.54 塌到 1.36 ms、
      p50 差从 37.0 塌到 1.09 ms——尾巴随并发收缩，正是排队主导的形状。
  (3) 成本的可观测来源：单 Reactor（S1 的既定形状，ADR-03）+ 每请求 5.0 次 epoll_ctl
      （epoll_modifications 9,359,517 / requests_parsed 1,872,093 = 5.0，ET 下挂/摘 EPOLLOUT 的固有支出）。
      分摊到多线程是 S2（多 Reactor + 连接池），缓冲水位动作是 S1-07；本任务不改结构追数字。
```

### #1 第四份记录（2026-10-29，B-008，S2-07 的线程模型 A/B —— 第一次真正测到多 Reactor）

```
实测 增量 p99 = 4.160 / 4.330 / 6.290 ms（workers=16，同机交替 3 轮，组内极差 2.130 ms）
     对照 增量 p99 = 32.990 / 33.050 / 35.210 ms（workers=1，同批交替 3 轮，组内极差 2.220 ms）
目标 增量 p99 ≤ 1.0 ms
未达标（超目标 4.2 ~ 6.3 倍）
归因 两条系列**不重叠**（w16 最大 6.290 < w1 最小 32.990，间隔 26.700 ms，而组内极差各 ~2.1 ms）
      → 按规矩四这个改动是**可判**的：多 Reactor 把服务速率赤字从 ≈34 µs/请求 压到 ≈8.7 µs/请求。
      剩下的 4–6 ms 是每请求净加工成本被 1000 并发放大：`p50 ≈ 连接数/QPS` 在 w16 上贴合到 0.3–1.6%
      （1000/39,025.61 = 25.62 ms vs 实测 p50 25.590），直连同一模型 1000/59,312 = 16.86 vs 16.240。
      每请求赤字 8.7 µs × 1000 并发 = 8.7 ms 是这个模型的**上界**，实测 4.16–6.29 ms 更低，
      因为尾巴比稳态排队更紧（p50→p99 跨度 5.07–7.35 ms，vs workers=1 的 12.89–21.80 ms）。
```

**这一条同时纠正 SLO 自己的一处陈述**：#1 此前的"六份取样 30–38 ms"里，**八份落盘 `canonic=1` 档全部跑在
`--workers` 缺省 = 1 的单 Reactor 路径上**（`s1-p99.sh` 从没传过这个参数，逐档核过横幅：单 Reactor 那条
才有 `max_connections=4096`，多 Reactor 那条才有 `workers=`）。所以 B-006 附那句"没有证据说多 Reactor
把 #1 的增量打下来"的真实性质是**这一格没被测过**，不是"测了没差异"——S2-07 用六轮交替把它补上了，

### #2 长连接资源占用

- **100k WebSocket 长连接**，握手完成后进入空闲（不发业务帧）
- 稳态判定：连接数达标后静置 ≥ 60 s，RSS 曲线不再单调上升
- RSS 取 `/proc/self/status` 的 `VmRSS`，不用 `ps` 的 VSS/RSS 混合口径
- **必须记录 malloc 实现**（glibc / jemalloc / tcmalloc）——这个数直接由分配器决定，换分配器等于换指标定义
- 每连接内存 = (`VmRSS` − 空进程基线 RSS) / **连接对数**。**分母口径由项目所有人于 2026-10-26 裁决**：代理拓扑下一个客户端连接配一条回源连接，**1 客户端 + 1 回源 = 1 个计费单位**（原先这一行写的是「/ 连接数」，而"连接数"在代理下有歧义——`TASKS.md` 卡点四记的就是这条歧义；目标值 `≤ 20 KB` 一个字没动，改的是分母的解释）。换算关系：按"连接对象"口径的每个读数 ×2 ≈ 按"连接对"口径的读数，100k 连接对 = 200k 个 `Connection` 对象
- **口径变更前后的可比性**：S1 期间进文档的所有读数都是**连接对象**口径（`sizeof(Connection)=520`、128 条空闲 = 5.81 KiB/**对象**、B-004 负载态 ≈19.7 KiB/**连接对**）——注意负载态那一条本来就是按对算的（`VmRSS` 增量 ÷ 1000 对），所以换口径后**负载态读数不变、空闲态读数要 ×2**。这两条在 `docs/BENCHMARK.md` 各自的原记录里就地标注，不重新写一份历史
- 空进程基线必须先单独测一次，否则算进去的是程序本体内存，100k 时会被摊薄成假达标
- 空闲 CPU < 5%：无业务流量时的事件循环唤醒次数应当接近 0，这条同时是「有没有在空转 timer」的检测器
- 工具：**自研 C100K 客户端**（契约 1.3 唯一允许自研压测客户端的场景，短连接测 C100K 是假的，只有长连接真考验每连接内存）
- **拓扑前提（2026-10-28 随 S2-06a 写死）**：隧道态一条下游配一条上游（ADR-09/15），所以 100k 连接对要
  100k 条「网关→上游」连接，而这一跳的容量 = `min(worker 数 N, 回源端点数 E) × 单元组容量`（本机实测 28,232）。
  **`--workers ≥ 4` 且 `E=4` 才有 112,928 ≥ 100k**；`--workers 1` 时这一档测不出来，容量仍是 28,232。
  报告里端点数、每端点实际条数（夹具自报 `accepted_by_addr=`）与容量逐项落盘，不拿 `对数 ÷ E` 当结论。
- **稳态窗口的取法（同一天定下）**：RSS 与空闲 CPU 都取"**客户端进程还活着的那 30 s**"（`c100k.sh` 的
  `CLIENT_END_TS` + 窗口内 fd 不许下降的门）。客户端一退出就有 FIN 风暴，那段 CPU 是"关门"不是"空闲"——
  实测被它骗过两次（25k 报 1.57%、100k 报 11.47%），修法与证据在 BENCHMARK 口径变更节与 FAULT-INJECTION §7。
- **建连窗口与握手上限**：`RAMP_MS=300000`（333 条/秒）、`HANDSHAKE_TIMEOUT_MS=120000`。这不是 SLO 的条件而是
  观察者的吞吐极限（833 条/秒那一轮 `established=64282/100000`），SLO 写死的"握手后空闲 + 达标后静置 ≥60 s"
  一条没少
- **上游池的两格口径自 S3-01（2026-10-29，ADR-15 追加节）起变了，就地标注、不回填历史数字**：
  ① `pool_idle_count()` 从"本 worker 的空闲热上游数"改成"**按目标分桶后各桶之和**"——单目标配置下
  两者数值相同（只有一个桶在用），所以 B-007/B-011 那两档的读数不受影响；但任何"池有多满"的比较
  必须写清是哪几个桶。② `pool_max_idle`（默认 64）的上界从"**每 worker**"变成"**每 worker 每目标**"，
  于是空闲上游的内存硬上界从 64 条变成 `E × 64` 条/worker。**这一格是 #2 的账**：E 个目标 × 每条
  热连接的入向/出向缓冲（各 8 KiB 容量级）就是最坏情况下的额外持有量，报告里给多端点配置时必须把 E
  与 `pool_max_idle` 一起写出来。隧道那一档不受这条影响（隧道态 1:1 专用、不入池，B-011 的"池摊销 = 0"
  仍然成立）。防复发的断言：`S3_01_Routing.PoolMaxIdleIsPerBucketNotPerWorker`（把上界当每 worker 总量
  算的写法会让第二条归还被判成池满关掉，那条用例就红）。

### #3 吞吐

- 前提：本机 **16 vCPU**（`nproc` 必须等于 16，否则条件不成立，见 ENVIRONMENT.md 第 2 节）
- 1 KB 响应体、HTTP/1.1 keep-alive、回显上游
- **Nginx 用同机、同参数、同绑核方案实测**，取 `nginx:1.25.4` 镜像（基线版本锁定，中途不得更换，否则历史对比数据全部作废）
- 两组之间除被测程序外，其余条件逐项一致：同一上游、同一台机器、同一时间窗口、同一绑核、同一分配器记录
- 判定：`QPS_网关 / QPS_nginx ≥ 60%`

> 附加产出不是第四个数，是 #3 的归因：与 Nginx 的差值必须定位到 HTTP 解析、内存分配、连接管理、日志写盘、系统调用次数中的哪几项，用 perf 火焰图作证。「差多少」谁都能测，「差在哪」才是本项目。**注意 perf 在本机可用性尚未验证**（版本与内核不匹配），这项前置风险记在 ENVIRONMENT.md 第 4 节，S4 期间做冒烟验证。
