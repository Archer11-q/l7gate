# SLO —— 三个数字，本项目的全部价值锚点

> 契约第 2 节的铁律：任何 C++ 项目说不出这三个数字就是空壳。本项目做得更深一层——**三个数字全部以 Nginx 同环境实测为基线做对比**，不由公开数字推算。

## 目标值（禁止为迁就实测而修改）

| # | 指标 | 目标值 | 首次可测阶段 | 当前状态 |
|---|---|---|---|---|
| 1 | 转发尾延迟 | 网关自身引入的增量 **p99 ≤ 1.0 ms，p999 ≤ 5.0 ms** | S1 | 实测 **增量 p99 = 57.540 ms** / 目标 ≤ 1.0 ms / **未达标** / 归因见 `docs/BENCHMARK.md` B-001。**p999 半边：无法判定**（wrk 4.1.0 与 hey 0.1.4 的分位表都只到 99%，见下「工具」条） |
| 2 | 长连接资源占用 | 100k WebSocket 长连接稳态：**每连接 ≤ 20 KB，空闲 CPU < 5%** | S2（连接模型稳定后）/ S3 复测 | 未测 |
| 3 | 吞吐 | **QPS ≥ Nginx 同环境实测值的 60%** | S2 | 未测 |

## 记录格式（未达标照记，格式固定）

```
实测 <值> / 目标 <值> / 达标|未达标 / 归因 <定位到具体机制，不是形容词>
```

达不到就写「未达标」并给归因。**实测不达标而如实记录，价值高于达标但说不清来源。** 归因写不到具体机制（解析、分配、连接管理、写盘、syscall 次数中的哪一项，量级多少）就不算完成。

## 测量条件（写死，改动任何一条都要在 BENCHMARK.md 里显式声明）

三个数字都不许脱离测量条件单独引用。

### #1 转发尾延迟

- 同机回环（`lo`），网关与上游同机部署，排除物理网络抖动
- 响应体 **1 KB**，固定不可变
- HTTP/1.1，keep-alive 开启
- **1000 并发连接**
- 稳态采样 **60 s**，预热不计入
- 测的是**增量**：同一负载下「直连上游」与「经网关转发」的 p99/p999 差值。原始 p99 单独记录，但达标判定只看增量
- 工具：wrk（`--latency`）与 hey 交叉验证
  - **这套工具的覆盖范围到 99% 为止**：wrk 4.1.0 的 `--latency` 只打 50/75/90/99 四行，hey 0.1.4 的分位表只到 99%。所以 p999 ≤ 5.0 ms 这半边**当前无法判定**——不是没跑，是取不到那个分位。要取到得换/加发压工具（wrk2、vegeta 之类），那属新依赖，按契约 8.2 禁令三要先 ADR，且需项目所有人裁决。**目标值不动，缺口照记。**
- 环境前置：CPU 绑核方案、内存分配器、全部组件版本号（见 ENVIRONMENT.md 第 7 节）
  - B-001 的落实：分配器已记录（glibc，`LD_PRELOAD` 空）、组件版本号已由 `scripts/bench/env-snapshot.sh` 一次性落盘、**绑核未做**（WSL 下 cpufreq 接口不可读，方案按 ENVIRONMENT 第 7 节留到 S4）——这条偏差在 BENCHMARK.md 里显式声明过，不是遗漏

### #1 首次记录（2026-10-26，B-001，`canonic=1`）

```
实测 增量 p99 = 57.540 ms（直连 24.850 / 经网关 82.390，wrk 1000 并发闭环）
目标 增量 p99 ≤ 1.0 ms
未达标
归因 三层，逐条有数：
  (1) 闭环排队主导——wrk 是"发一条等一条"，稳态下 延迟 ≈ 连接数/QPS：
      直连 1000/59,860 = 16.7 ms ≈ 实测 p50 16.35 ms；经网关 1000/18,229 = 54.9 ms ≈ 实测 p50 53.35 ms。
      所以 57.5 ms 这个差值读作"服务速率赤字被 1000 并发放大成排队"。
  (2) 每请求成本 ≈ 38 µs（网关瓶颈线程 54.9 µs/请求 vs 直连上游 16.7 µs/请求）。
      对照实验：并发降到 50（B-002，非标准口径、不作判定）时增量 p99 从 57.54 塌到 1.36 ms、
      p50 差从 37.0 塌到 1.09 ms——尾巴随并发收缩，正是排队主导的形状。
  (3) 成本的可观测来源：单 Reactor（S1 的既定形状，ADR-03）+ 每请求 5.0 次 epoll_ctl
      （epoll_modifications 9,359,517 / requests_parsed 1,872,093 = 5.0，ET 下挂/摘 EPOLLOUT 的固有支出）。
      分摊到多线程是 S2（多 Reactor + 连接池），缓冲水位动作是 S1-07；本任务不改结构追数字。
```

未达标（超目标 36 倍；目标值不动，按契约 8.2 禁令二）
两份之间的变化，逐条只有实测、没有推断：

  (b) 50 并发对照（同口径复跑，仍非标准口径、不作判定）增量 p99 1.360 → 1.370 ms、

      "(3) 成本来源 = 5.0 次 epoll_ctl" 不能升级为"少了 1 次所以快了 21 ms"。

      **SLO #1 的测量条件不因此改动**：同机回环就是契约写死的条件，1.15 那条"回环上

### #1 第三份记录（2026-10-26，B-004，`canonic=1`，S1-08 之后 —— S1 收尾按这一组陈述）

```
实测 增量 p99 = 29.720 ms（直连 26.410 / 经网关 56.130，wrk 1000 并发闭环）
目标 增量 p99 ≤ 1.0 ms
未达标。S1 收尾的诚实陈述是：三次标准口径取样 = 36.420 / 37.890 / 29.720 ms，
      即 **30–38 ms 量级、超目标 30–38 倍**（B-001 的 57.540 ms 是 S1-06 时的读数）。
      中间那次 37.890 是同一份 S1-07 binary 的第二次取样（B-003 附），它存在的唯一理由
      就是把"1000 并发下单轮样本有多不稳"这件事测出来。
      p999 半边仍无法判定（wrk 4.1.0 / hey 0.1.4 分位表只到 99%）。
这一份能说的：空 filter 链没有可分辨的成本 —— 每请求 epoll_ctl 4.003
      （三次读数 4.005 / 3.999 / 4.003，极差 0.15%），经网关 QPS 与上一轮同量级，
      负载态内存同量级；S1-07/S1-08 的四个背压计数在这套条件下仍然全为 0。
这一份不能说的：p99 变好了。经网关 p99 56.130 与上一轮 60.530 同量级，而**直连 p99
      从 22.640 涨到 26.410** —— 差值的变化主要由分母（直连组，我控制不了它）移动造成。
      三次取样的极差（27%）大于"一次改动带来的 7 ms 差异"的可信区间，所以 S2 之后要判断
      某次改动有没有把 p99 打下来，必须同机交替、每个改动至少两轮；这条要求写进了
      B-004 的可比性声明，是给下一个改代码的人（包括半年后的我）的约束。
```

> 这条最容易造假的点在于「和谁比」。我必须给出直连基线的那组数字本身，而不是一句「网关只引入 0.4ms」。

### #2 长连接资源占用

- **100k WebSocket 长连接**，握手完成后进入空闲（不发业务帧）
- 稳态判定：连接数达标后静置 ≥ 60 s，RSS 曲线不再单调上升
- RSS 取 `/proc/self/status` 的 `VmRSS`，不用 `ps` 的 VSS/RSS 混合口径
- **必须记录 malloc 实现**（glibc / jemalloc / tcmalloc）——这个数直接由分配器决定，换分配器等于换指标定义
- 每连接内存 = (`VmRSS` − 空进程基线 RSS) / 连接数。**空进程基线必须先单独测一次**，否则算进去的是程序本体内存，100k 时会被摊薄成假达标
- 空闲 CPU < 5%：无业务流量时的事件循环唤醒次数应当接近 0，这条同时是「有没有在空转 timer」的检测器
- 工具：**自研 C100K 客户端**（契约 1.3 唯一允许自研压测客户端的场景，短连接测 C100K 是假的，只有长连接真考验每连接内存）

### #3 吞吐

- 前提：本机 **16 vCPU**（`nproc` 必须等于 16，否则条件不成立，见 ENVIRONMENT.md 第 2 节）
- 1 KB 响应体、HTTP/1.1 keep-alive、回显上游
- **Nginx 用同机、同参数、同绑核方案实测**，取 `nginx:1.25.4` 镜像（基线版本锁定，中途不得更换，否则历史对比数据全部作废）
- 两组之间除被测程序外，其余条件逐项一致：同一上游、同一台机器、同一时间窗口、同一绑核、同一分配器记录
- 判定：`QPS_网关 / QPS_nginx ≥ 60%`

> 附加产出不是第四个数，是 #3 的归因：与 Nginx 的差值必须定位到 HTTP 解析、内存分配、连接管理、日志写盘、系统调用次数中的哪几项，用 perf 火焰图作证。「差多少」谁都能测，「差在哪」才是本项目。**注意 perf 在本机可用性尚未验证**（版本与内核不匹配），这项前置风险记在 ENVIRONMENT.md 第 4 节，S4 期间做冒烟验证。
