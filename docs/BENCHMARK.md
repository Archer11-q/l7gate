# BENCHMARK —— 压测记录

规矩只有四条，都是为了让"半年后这份数字还能不能用"这个问题有答案：

一，**一次压测一条记录**，原始数字（不是截图里的均值）+ 结论 + 环境参数一起写。契约第 7 节对这份文件的完成判据点名了三样：CPU 绑核、分配器、各组件版本号。少任一条，这份记录就只是"我记得当时挺快"。

二，**口径变更必须留一条记录**：改了哪条、为什么改、改前改后是否可比。不许把不可比的两次放在一起画趋势线。

三，**达标判定只认 `canonic=1` 的那一轮**（`scripts/bench/` 里的脚本自己判口径，不由我嘴上说）。非标准口径的跑法允许存在，但它的身份是**归因实验**，标题里就写明。

四，**判断"某次改动有没有改善"必须同机交替、每改动至少两轮，并给出极差**（2026-10-26 裁决采纳，自 S2 起强制）。这条是从 S1 收尾的散布里长出来的：同一份 binary 复跑，直连 p99 自己漂 11.3%、四份增量极差 27%、#3 比值两轮复现 206.11%/203.74%（差 1.2%）。写进这里而不是只写在 SLO，是因为**每份新记录都要在标题下面回答"另一轮呢？"**——答不出来就标"单轮样本，不构成改动有效的证据"。

### 结论：**未达标**，且 p999 半边当前无法判定

SLO #1 的目标是增量 **p99 ≤ 1.0 ms、p999 ≤ 5.0 ms**。实测增量 p99 = **57.540 ms**，超目标 57 倍。按契约 8.2 禁令二，目标值不动，这里照记并归因。

p999 不是"没测到"而是**这套工具链取不到**：wrk 4.1.0 的 `--latency` 只打 50/75/90/99 四行，hey 0.1.4 的分位表只到 99%。要拿到任意分位需要换/加发压工具（wrk2、vegeta、自研皆算新依赖），按契约 8.2 禁令三要先 ADR，按交接段授权 (a)(b) 两项都要停下来请示——所以这一格记"无法判定"，不记 0。

### 归因

**一，这个 57.54 ms 里绝大部分是排队，不是网关的加工成本。** wrk 是闭环模型：1000 条连接，每条"发一条、等一条"，于是稳态下 `延迟 ≈ 连接数 / QPS`（Little 定律）。验算：直连 1000/59,860 = 16.7 ms ≈ 实测 p50 16.35 ms；经网关 1000/18,229 = 54.9 ms ≈ 实测 p50 53.35 ms。两组都贴合到 3% 以内。所以"经网关 p99 = 82 ms"读作"网关把服务速率降到了 1/3.3，于是每条连接在闭环里多排了 38 ms 的队"，而不是"网关每请求多花 38 ms"。

**二，换算成每请求服务时间，网关引入的是 ≈38 µs，不是 38 ms。** 直连时上游单线程 16.7 µs/请求；经网关时瓶颈线程（网关）54.9 µs/请求。差值 ≈38 µs 是网关自己的 CPU 成本。旁证：把并发降到 50（`build/bench/s1-c50/`，非标准口径，仅作归因不作判定），增量 p99 从 57.54 ms 塌到 **1.36 ms**、p50 从 37.0 ms 塌到 **1.09 ms**——尾巴随并发线性收缩，正是排队主导的形状，而残下的 ~1 ms 量级才是每请求成本在闭环里的表现。

**三，每请求成本的可观测来源：单 Reactor + 每请求 5.0 次 `epoll_ctl`。** `epoll_modifications=9,359,517 / requests_parsed=1,872,093 = 5.0`。S1 的形状本来就是一条事件循环线程（ADR-03、S1-04），挂/摘 `EPOLLOUT` 各一次 × 两个方向 + 收尾一次是这套 ET 写法的固有支出。这两条都是**已计划的后续任务**要动的地方：多 Reactor 与连接池在 S2（`TASKS.md` S2 行），背压动作在 S1-07；本任务不改结构去追数字。（**S1-07 之后这个数是 4.005**，见 B-003 的对照表——省下的那一次我没有归因到具体代码行，只有两处独立测量都稳定少 1 次这个事实，见 ARCHITECTURE 1.15；同一份对照表也显示 50 并发下的每请求成本没变，所以"少一次 syscall"没有兑换成尾延迟的等比改善，这条当年写的因果要按那个强度读。）

**四，尾延迟的放大机制说明 S1 的这个数字不能横向比。** 同一份网关代码，1000 并发下增量 57.5 ms、50 并发下 1.36 ms。SLO #1 写死了 1000 并发，所以判定按 57.5 ms 记未达标；但真正要向"≤1.0 ms"逼近的路径是每请求服务时间（38 µs 这一头）与并发分摊（S2 那一头），把这条写在这里是为了下一次改代码时有正确的成功判据，而不是去调口径。

### 另两个数字（门禁四件套第 1 条要求同场记录）

**自测 QPS（经网关，wrk 闭环 1000 并发，60 s 稳态）= 18,229.47**；直连同一上游 = 59,860.19。按卡点三，S1 只交这个数字、不设判定基线（vs Nginx 的基线在 S3/S5，Docker 尚未可用）。

### 与 B-001 对照：什么变了、什么没变、什么我不能归因

| 指标 | B-001（S1-06） | B-003（S1-07） | 变化 |
|---|---|---|---|
| 增量 p99 | 57.540 ms | **36.420 ms** | −21.120 ms（−36.7%），**仍未达标**（超目标 36 倍） |
| 经网关 p99 | 82.390 ms | 61.950 ms | −20.440 ms（−24.8%） |
| 直连 p99 | 24.850 ms | 25.530 ms | +0.680 ms（+2.7%）——基线自己也在动，这条就是"增量的分母是我自己的上游"那句话的意思 |
| 经网关 QPS | 18,229.47 | 19,640.38 | +7.7% |
| 每请求 `epoll_ctl` | 5.00（9,359,517 / 1,872,093） | **4.005**（7,872,390 / 1,965,838） | **−19.9%**，这是本任务确定性的结构收益 |
| 50 并发对照的增量 p99 | 1.360 ms | 1.370 ms | +0.7%（QPS 27,510 → 27,582，+0.3%） |

**没变的那一条决定了这张表怎么读。** 50 并发那轮是"每请求成本"的对照：1.360 → 1.370 ms、QPS 差 0.3%，也就是**每请求 CPU 成本一次都没降**。既然每请求成本没降、QPS 只涨 7.7%，那 1000 并发下 21 ms 的增量收缩就**不能**说成"少打一次 `epoll_ctl` 换来的"——它是高并发尾巴形状的变化（p50→p99 的跨度从 29.04 ms 缩到 12.16 ms），而我只各有**一轮**样本，没有在同一台机器上把两个 binary 交替跑起来的 A/B，所以这条改动的因果我写不出来。诚实的版本是：**每请求 `epoll_ctl` 从 5.00 降到 4.005 是实测的、可复现的；增量 p99 从 57.54 降到 36.42 是实测的；把前者说成后者的原因是我没有证据的**。要拿这条做趋势，得先按 SLO 的"口径变更必须留记录"补一次同机交替复跑。

排队主导的判定继续成立（B-001 归因第一条不作废）：`延迟 ≈ 连接数 / QPS`，经网关 1000/19,640.38 = 50.9 ms ≈ p50 49.790（差 2.2%），直连 1000/59,624.37 = 16.8 ms ≈ 16.180（差 3.6%）。B-001 归因第三条里"每请求 5.0 次 `epoll_ctl`"这个数在 S1-07 之后是 **4.005**，那一节已就地标注。

### 结论：**未达标**（增量 p99 = 36.420 ms，目标 ≤ 1.0 ms）；p999 半边仍无法判定（wrk 4.1.0 / hey 0.1.4 的分位表都只到 99%）

按契约 8.2 禁令二，目标值不动。下一步的数字归属写清楚：S1-07 交的是"停读线在真实负载下不误触发"（四个计数全 0）+ 每请求 `epoll_ctl` 少一次，这两条都到位；把增量 p99 压向 1.0 ms 的路径仍然在 S2（多 Reactor 分摊并发）与每请求服务时间（36 µs 这一头，见 B-002/B-003 的 50 并发对照），不在背压里。

### 可比性声明

与 B-001 逐项对齐：`release`、未绑核、glibc、同一个 `l7gate_bench_upstream`、`CONNECTIONS=1000 / DURATION=60s / WARMUP=10s / WRK_THREADS=8 / BODY_BYTES=1024`、`canonic=1`。唯一变化是被测代码本身。**注意**：单轮样本在 1000 并发下的复现性我没有测过（B-002 那种低并发对照的 ±1% 不能外推到这儿），所以上面的对照表只能读成"两次实测的差"，不能读成"这次改动的效果"。

## 口径变更 · SLO #2 的分母：连接数 → 连接对（2026-10-26，项目所有人裁决）

**改了哪条**：`SLO.md` #2 的「每连接内存 = (VmRSS − 空进程基线 RSS) / 连接数」里，分母由含糊的"连接数"明确为**连接对数**（1 个客户端连接 + 1 条回源连接 = 1 个计费单位）。**目标值 `≤ 20 KB` 未动**（契约 8.2 禁令二管的是目标值，这里改的是分母解释，且由裁决给出，不是我自行放宽）。

**为什么改**：`TASKS.md` 卡点四记的那条歧义——网关侧一条下游 + 一条上游是 2 个 fd、2 个 `Connection` 对象，"每连接 20 KB"在这两种读法下差一倍，而 SLO #2 的判定要到 S2/S3 才做，越晚定越容易被历史读数牵着走。

**改前改后是否可比**：S1 期间的读数分两种情况——
- **负载态**（B-001…B-004 的 `≈19.7 KiB/连接对`）**本来就是把 `VmRSS` 增量除以 1000 对**得到的，所以换口径后**数值不变**，只是当时行文写成了"每连接对"。
- **空闲态**（`S1_04_Reactor.MemoryPerIdleConnectionIsMeasured` 摊出的 **5.81 KiB/连接对象**、`sizeof(Connection)=520`）是**对象**口径，按新分母要 ×2 ≈ **11.6 KiB/连接对**（128 条空闲下游连接场景里回源连接根本没建，`outbound_buffers_created`/`scratches_created` 为 0，所以这个 ×2 是**口径换算而不是实测**——真正的双对象空闲内存要等 S2 的连接模型 + 100k 场景测出来，那一轮才是 SLO #2 的判定读数）。
这条换算我标成"口径推导"而不是"实测"，因为把它写成实测就等于凭空造一个数（128 条空闲下游连接对应的上游连接数 = 0，`upstream_opened` 在读数里可查）。

**为什么这条值得单独一节而不是改一行**：`ENVIRONMENT.md` 第 7 节早就写明 SLO #2 的数字"直接由 malloc 实现决定"，分母再一变动，历史读数就全部要带着口径标签才能引用。这正是契约规矩二（口径变更必须留记录）存在的理由。

### 结果二 · 100,000 连接对名义档（`canonic=1`）：**未达标，卡住的是测量条件，不是内存**

同一脚本、同一台机、同一份 binary，只把 `CONNECTIONS` 抬到 100000。原始档 `build/bench/tier-100k/`。

| 项 | 实测 |
|---|---|
| 建立 / 计划 | **28231 / 100000** → `established` 精确停在**单元组天花板**上（比 ADR-17 探针实测的 28,232 少 1） |
| 网关账 | `downstream_accepted=100000`（**下游一条没丢，全接进来了**）、`upstream_opened=28231`、**`upstream_connect_failed=75708`**、`accept_errors=0`、`rejected_over_capacity=0` |
| 客户端账 | `failed=71769`，全部落在 `handshake-timeout`（30 s 到点）。**没有一条是 connect 失败**——墙不在下游侧，在网关回源那一跳 |
| 生命周期 | `live=0`、`constructed==destructed==128231`、`fd 39→39`、排水 **1.0 s**：100k 规模下 S2-05 的账仍然闭合 |
| 每连接内存 | 算出来 **34.41 KiB/对**，**这个数不引用**（原因见下） |
| 空闲 CPU | 算出来占单核 **43.41%**，同样**不引用** |

**为什么后两格不引用——分母被人动过了**：71,769 条下游连上了、被 accept 了、**但配不到上游**（回源元组耗尽），于是它们的 `Connection` 对象与缓冲全在分子里，而分母按口径只数"连接对"= 28,231。分子与分母不是同一件事，那个商就没有意义：**34.41 相对 17.47 的"翻倍"是这条算术造成的，不是网关在 100k 下退化了一倍**。脚本从本轮起自己堵住这个洞——`downstream_accepted ≠ established` 就置 `measurable=0`，并在两格旁边写明"本轮不引用"。

**归因（就是那一格测量条件）**：网关的 100k 条回源全部落在同一个 `(目的 IP, 目的端口)` 元组上，实测容量 28,232（`ENVIRONMENT.md` 第 7 节 + ADR-17 的探针复现）。客户端侧靠 4 个目标地址已经拿到 112,928 的容量，本轮也确实把 100,000 条连接打了进来——**瓶颈只剩网关回源那一跳的单端点**。这正是 ADR-17 最后那条待裁决项——**已于 2026-10-28 裁完＝候选 A（`--upstream` 端点列表 + per-worker 静态映射），落地任务 `S2-06a`**；裁之前 #2 的 100k 判定只能记成现在这个形状，我不会靠减目标值或换分母把它做绿（禁令二）。

**顺带暴露的一条产品行为（记下来，本任务不修）**：回源 connect 失败时网关**不关下游、也不自产错误响应**，请求留在下游缓冲里，于是客户端只能自己超时（本轮 71,769 条下游全部以 `handshake-timeout` 收场，且 `upstream_connect_failed=75708 > 71769` 说明它在反复重试）。"上游连不上时多久表态、怎么表态"归 S4 的请求超时与自产响应那一格——现在那一格是**空的**。这是空，不是 bug；但在把回源打成耗尽之前，没有任何观测面能让人看见它是空的。

### 三条限定，一条都不能省

1. **这一档只在 `--workers ≥ 4` 上成立。** 回源容量 = `min(N, E) × 28,232`；`--workers 1` 的单 Reactor
   路径只用第 0 个端点，容量仍是 28,232——那是静态指派的选择，不是我漏了（ARCHITECTURE 1.21 边界①）。
2. **ramp 从 120 s 放宽到 300 s、握手上限从 30 s 到 120 s，是被观察者的吞吐逼出来的，不是我挑的。**
   同一份 binary、同样 100k 条，`--ramp-ms 120000`（833 条/秒）那一轮 `established=64282/100000`、
   `failed=35718` 全 `handshake-timeout`，而上游 `accepted/requests/upgrades` 全是 100,000 一条没漏
   （`build/bench/tier-100k-e4/` 与 `probe-upstream-100000/`，机制与判别实验在 FAULT-INJECTION §7）。
   SLO #2 写死的两条条件——"握手后进入空闲"与"达标后静置 ≥60 s"——**一条没少**，动的是工具参数。
3. **p99=36.7 秒那一格读的是客户端自己。** 终局自报 `elapsed_ms=372,742 self_cpu_ticks=14,659`
   ≈ 单核 39%、`self_rss_kib=22896` 持 `self_open_fds=100006`：100k 条握手在 300 s 窗口里排队，
   尾部落在观察者自己的 CPU 预算上。**这一格不进 #1 的判定**（#1 要的是 1 KiB/1000 并发下
   "直连 vs 经网关"的**转发**增量，S2-07 按取样规程做），我把它放在这里是为了不让一个 36 秒的数字
   以"网关的尾延迟"的身份出现在报告里。

`die`，空闲 CPU 那格直接作废；② 100k 档的建连窗口与握手上限改成 `RAMP_MS=300000 /

换 E 就是换这一跳的容量，所以它是口径的一部分。**目标值 `≤ 20 KB`、`< 5%` 与分母「连接对」一个字没动。**

**为什么改**：全部来自实测，不是预防性设计。①的代价被量到过两次：25k 档 E=4 报 **1.57%**（窗口最后一格
+42 tick、E=1 同档 0.21%），100k 档 E=4 报 **11.47%**（最后一格 +361 tick 且 fd 从 200,039 掉到 97,166）——
都是客户端退出那一刻的 FIN 风暴被算进了"空闲"。②的原因是 833 条/秒下观察者自己只能完成 64,282 条握手。
逐样本数字与判别实验在 `docs/FAULT-INJECTION.md` 第 7 节 S2-06a 那三条。

**改前改后是否可比**：内存那一格**完全可比**——窗口右界只影响"最后 15 个样本"的取法，而 RSS 在污染轮与
干净轮里逐 KiB 相同（B-006 的 441,204 与本档的 1,751,020 都落在同一商数 17.47 上）。空闲 CPU 那一格：
B-006 的 0.17% 是**在旧窗口定义下**取的，事后看它没有踩到风暴（同档 E=1 复跑得 0.21%，与新定义下的
0.22% 同带），所以历史读数**继续可用**，但它当时没有门保护——这一条按原样记，不假装旧定义也给过同样的保证。

**为什么这条值得单独一节**：`空闲 CPU` 是 SLO #2 的两个判据之一，而它的读数取决于"哪 30 秒算空闲"。
没有那条 fd 门的话，下一轮 11.47% 会被读成"网关在 100k 下变忙了"——**那是网关的性质还是我取数的形状，
必须由文件里的一行来回答，不能由我记得住哪一轮干净来回答。**

标定那轮报的是 `2,000,000 vs 4,000,000`，看着像"上游在重复计数"，其实是 direct 2M + proxy 2M。

## B-010 · 100k 条隧道在**负载下**的排水耗时（2026-10-29，S2-07 第五项，`c100k.sh DRAIN_UNDER_LOAD=1`）

**这一格为什么必须由 S2 交、不许推给 S4**：ARCHITECTURE 1.20 边界④ 把"排水耗时与 100k 规模下的下线时间"
归给 S2-06/S2-07；而 S2-06 那一轮我写过「排水 0.5 s 收干净 25,000 条隧道」，那句在 S2-06a 被撤回——
三档 25k 的 `drain_tunnels_hard_closed` 全是 **0**，隧道是客户端退出那一刻的 FIN 级联关掉的，
0.5 s 只是网关从 SIGTERM 到自己退出的时间。**根因是脚本的顺序**：`c100k.sh` 天然先退客户端、再停网关，
所以排水全程没活干。要测它，必须在**客户端仍持有连接时**发信号。这一档就是那一格的实测。

它同时决定一件事：默认 `--drain-timeout-ms 5000` 在 100k 规模下还站不站得住。而 1.20 写的
「S4 的请求超时必须 ≤ drain」这条对齐**要用到这个数**才有依据。

| 项 | 值 |
|---|---|
| 日期 | 2026-10-29 09:13–09:23（本地） |
| 被测 | 与 B-007/B-008 同一份 binary（`release`，`l7gate` sha256 前缀 `13aa69c86a0449094ef006b0`） |
| 手段 | `scripts/bench/c100k.sh` 新增 `DRAIN_UNDER_LOAD=1` 档：`established==planned` 且静置窗口已开始后，脚本给网关发 SIGTERM（客户端仍持有全部连接），0.05 s 一轮计时到网关自己退出 |
| 静置窗口内取数 | 参数 | `DRAIN_TIMEOUT_MS=5000`（**产品默认值本身**，不是为这一档放宽的值）、`DRAIN_SETTLE_IN_WINDOW=10`（100k 档 `HOLD_SECONDS=60`，所以信号落在窗口开始后的第 ~10–20 s） |
| 100k 档参数 | `CONNECTIONS=100000 TARGETS=4 UPSTREAM_ENDPOINTS=4 WORKERS=16 RAMP_MS=300000 HANDSHAKE_TIMEOUT_MS=120000 HOLD_SECONDS=60` → `canonic=1` |

### 结果

| 档 | 连接对 | 信号前网关持有 | **SIGTERM→退出** | `drain_tunnels_hard_closed` | `drain_forced_timeout` | `live` | `constructed==destructed` | fd |
|---|---|---|---|---|---|---|---|---|
| 2,000（`workers=4`，冒烟） | 2,000 | fd 4,016 / RSS 39,304 KiB | **0.117 s** | 2,000 = established | 0 | 0 | 4,000 = 4,000 | 17→17 |
| 25,000（E=4，`workers=16`） | 25,000 | fd 50,040 / RSS 441,204 KiB | **0.305 s** | 25,000 = established | 0 | 0 | 50,000 = 50,000 | 41→41 |
| **100,000（正式档，`canonic=1`）** | 100,000 | fd **200,040** / RSS **1,751,032 KiB** | **0.947 s** | **100,000 = established** | **0** | 0 | **200,000 = 200,000** | **41→41** |

正式档另外几栏：`drain_requested=16`（每条 worker 各计一次，accept 循环不持有连接所以不计数）、
`drain_closed_idle=0`、`drain_closed_buffered=0`、`drain_in_flight_at_entry=0`、
`drain_rejected_new_connections=0`、`downstream_accepted=upstream_opened=upgrades_101=100000`、
夹具自报 `accepted_by_addr=127.0.0.1:25000, .2:25000, .3:25000, .4:25000`（逐端点实测，不是 `100k÷4`）、
`upstream accepted=100000`。信号前那一刻的 fd 与 RSS 就是"负载下"这三个字的证据。

### 判定

```
实测 100k 条隧道在客户端仍持有连接时的排水（SIGTERM→进程退出）= 0.947 s
     / 断言 drain_tunnels_hard_closed == established = 100000 ✓ / drain_forced_timeout = 0 ✓
     / live_connections = 0 ✓ / constructed == destructed = 200000 ✓ / fd 41→41 ✓
结论 默认 --drain-timeout-ms 5000 在 100k 连接对下**站得住**，余量 5000/947 ≈ 5.3 倍
归因 排水扫描是每条 worker 在自己注册表上线性走一遍（16 条 worker 各 ~6,250 对），
     0.947 s ÷ 200,000 个连接对象 ≈ 4.7 µs/对象；规模从 25k 到 100k（4 倍）耗时 0.305→0.947（3.10 倍），
     所以它是**亚线性到线性**之间，没有出现超线性形态。
```

**这条对 S4 的直接影响，写在取数这一轮而不是留给以后**：`drain` 在 100k 下实测 0.947 s 就能收干净，
所以"S4 的请求超时 ≤ drain（默认 5000 ms）"这条对齐**不需要为了排水规模去抬高默认值**；
S4 定义请求超时时可以按 5000 这个上界来做，只要它自身不超过 drain。
仍然归 S4、这一档一个字没动的是另一半：**回源耗尽时网关多久表态、自产什么响应**（今天"不伪造状态码"的口径不变，
本轮没有把它顺手改成 502）。

### 阳性验证（能红才叫绿）

## B-011 · 每连接内存的**构成表**（2026-10-29，S2-07 第三项；那 0.50 KiB 空项在这里结掉）

验收句要的是"构成表每一项都有数"，并且不许有我算出来的格子。取数点是 `tests/connection_test.cc` 里新增的
两条 `S2_07_MemoryComposition` 用例：**在进程内复刻生产的那一对**（`unordered_map<int, shared_ptr<Connection>>`
注册表 + `make_shared`，与 `reactor.h:350` 同一个形状），字节量取 B-007 那一档的真实负载
（163 B 升级请求 + 129 B 的 101 头 + **零条业务帧**），容量问 `Buffer::capacity()`，
堆总量问 `mallinfo2().uordblks`（含取整），scratch 有没有留问 `has_scratch()`。

### 每连接对（1 客户端 + 1 回源 = 1 个计费单位，卡点四裁决）

| 构成项 | 字节/对 | 这个数怎么来的 |
|---|---|---|
| 入向 `Buffer` 存储 × 2 | **8,192** | `capacity()` 逐条读，停在 `initial_capacity=4096`；两侧入向各只装过 163 / 129 字节，没有扩容理由 |
| 出向 `Buffer` 存储 × 2 | **8,192** | 同上；与 B-007 的 `outbound_buffers_created=200,000`（= 2×对数）对齐 |
| `Connection` 对象 × 2 | **1,056** | `sizeof(Connection)=528`（ADR-16 之后的值，含入向 `Buffer` **对象本体**） |
| 出向 `Buffer` 对象 × 2 | **176** | `sizeof(Buffer)=88`；入向那一个已经在 528 里，**不能再数一遍** |
| **可点名小计** | **17,616** | 上面四项相加 |
| `shared_ptr` 控制块 × 2 + 注册表节点 × 2 + glibc 取整 | **245** | `mallinfo2().uordblks` 的每对总量减去可点名部分 |
| **每对堆在用量（实测）** | **17,861** | 256 对前后差分 ÷ 256，debug preset、glibc-malloc |
| `ParseScratch` | **0**（若隧道化后不释放 = **2,095**） | `has_scratch()` 实测 0；2,095 是阳性验证量出来的（2,048 体 + 取整） |
| 池摊销 | **0** | B-007 的 `pool_borrows=pool_returns=0`——隧道态不入池（ADR-15），所以这一格不是"池省了钱"，是"池根本不参与" |
| 业务帧的缓冲增量 | **0** | SLO #2 的口径就是握手后空闲（`bytes_tunnel_down=0`） |

### 与生产那一条实测线的对照

```
实测 每对堆在用量 = 17,861 B（本档，256 对，进程内）
实测 每对 (VmRSS − 空进程基线) = 17,889 B（B-007，100,000 对，生产进程）
差 = 28 B/对 = 0.16%
     第三条独立视角：本档同一进程的 VmRSS 增量 = 18,112 B/对（17.69 KiB），
     与上面两个数同带——两张表是不同时间、不同规模、不同进程各自量出来的。
```

**这就是构成表的验收判据**：它不是"我逐项加起来恰好等于商"，而是**进程内 256 对**与**生产 100k 对**
两个独立测量落在同一个数上（0.16%）。阳性验证：把 `release_scratch()` 摘掉 → 每对变成 **19,956 B**
（= B-007 的 111.6%）、未点名一角从 245 B 变成 2,340 B → 三条断言**同时红**。能红才叫绿。

### S1-07 那 0.50 KiB/连接的未归因差额，这一格结掉了

ARCHITECTURE 1.11 留的账是：128 条空闲下游连接的 RSS/连接从 S1-06 的 **5.31** 涨到 S1-07 的 **5.81 KiB**，
而 `sizeof(Connection)` 只涨 8 B（512→520）——0.50 KiB/连接 × 128 条 = 总共 **64 KiB** 没有归属。
现在有两个实测：

```
每连接堆在用量 N=128 = 4,602 B / N=1024 = 4,663 B（差 61 B，与 N 无关）
同两段的 VmRSS：N=128 那一段 +0 KiB（堆里要了 575 KiB）/ N=1024 那一段 +224 KiB（224 B/连接）
```

归因：**在 N=128 这个尺度上，VmRSS 不是每连接内存的可用仪器**——同一进程里加了 128 条连接、
堆在用量涨 575 KiB，而 VmRSS 一位没动（页在更早的分配里已经驻留）。所以 5.31 与 5.81 之差
（64 KiB，正好是这种"驻留时机"的量级）落在仪器粒度里，**不构成"每连接内存变了 0.50 KiB"的证据**。
每连接内存的可引用数字从此以**堆实测（本档）与生产 RSS 商（B-007）**为准，两者互为对照。
ROADMAP 债表里那一行"每连接内存有一笔没归因的差额"因此可以划掉。

### 一条必须留着别让人踩的口径混用

**17.47 KiB/对 ≠ 2 × 5.81 KiB/连接**。5.81 那一档是 **128 条只有下游**的空闲连接（没有出向 buffer、
没有 scratch、没有配对上游，且分母是"连接对象"），17.47 这一档每条是**两个对象 + 四块缓冲**。
上面那张表的第二行到第五行就是这个差别的全部内容。拿 ×2 去互推会得到一个既不等于 11.6 也不等于 17.47 的数。

### 可比性声明

- 本档不改任何 SLO 目标值与分母口径（禁令二）；`≤ 20 KiB/对` 与"连接对"分母一个字没动。
- 与 B-007 的对照只在**同一份负载**（163 B 请求 / 129 B 头 / 零业务帧）下成立；带上业务帧之后
  缓冲容量会不会涨，取决于帧大小与背压，那是 S1-07 的 `S1_07_Backpressure` 四条用例管的事。
- 用例跑在 `debug` preset（`-O0`）。`sizeof` 与容量与构建类型无关，堆字节因此可比；
  sanitizer 构建下这两条只打印不判（同 1.10 那条 `k_rss_is_instrumented` 纪律）。

## B-012 · S3-01 的成本那一格:空链 vs 路由链,同机交替 2 轮(2026-10-29,workers=1 / 100 并发闭环)

**这一格在问什么**:路由进了主路径,每请求加了多少钱。验收句给的形式是"空链 vs 路由链,
同负载 100 并发闭环,每请求 p50/p99/p999 与每请求 `epoll_ctl` 逐项对照,≥2 轮报极差,
判据是增量不超过本档的散布带"。

**两臂只差一个因子。** 我在 `scripts/bench/s1-p999.sh` 上加了 `GATEWAY_EXTRA`(默认空 →
argv 与 S2 时代逐字相同,所以 B-008/B-009 的可比性不作废),它**只作用在经网关那一臂**:

- A 臂:`--upstream` 一个端点、**不装 filter**(链是空的)。
- B 臂:同一个端点、加 `--route /=0`(一条 catch-all 前缀,命中所有请求、送到唯一的 0 号目标)。

所以目的地、端点数、worker 数、负载全同,差别只有"链上多跑一环 + 多一次桶选择"。
B 臂的网关横幅自报 `route_rules=1 no_match_status=404 default_target=0`,A 臂 grep 这一行是
**0 次**——因子确实只落在了一臂上,不是我口头说的。

**为什么是 workers=1 而不是 16**:B-009 实测 100 并发这一档,经网关 w1 的观察者占单核
**0.39**(仪器不饱和),w16 那一臂是 **0.99**(饱和)。要"能读的"对照只能在 w1 上做。
**因此本档不能和 B-008 那个每请求 ≈8.7 µs 互推**——那个数是 `workers=16 / 1000 并发 / wrk`
那条线上的每请求净赤字,臂不同、档不同、仪器也不同。S3-06 终判要的是同一档的对照,
这一格先把它该答的那一半答掉:**路由这一环有没有可分辨的成本**。

### 结果(每臂 4 轮,同机交替顺序 A1 → B1 → A2 → B2;经网关一侧)

| 轮 | 臂 | p50 µs | p99 µs | p999 µs | p9999 µs | QPS | 每请求 `epoll_ctl` | 样本 | 观察者占单核 |
|---|---|---|---|---|---|---|---|---|---|
| A1 | 空链 | 3,264 | 4,480 | 5,760 | 7,808 | 30,875.1 | **4.0005** | 3,704,855 | 0.39 |
| B1 | 路由链 | 3,136 | 4,480 | 5,760 | 6,784 | 31,633.2 | **4.0002** | 3,795,862 | 0.39 |
| A2 | 空链 | 3,264 | 4,480 | **6,016** | 7,296 | 31,185.6 | **4.0000** | 3,742,118 | 0.39 |
| B2 | 路由链 | 3,136 | 4,480 | 5,760 | 7,552 | 31,304.1 | **4.0000** | 3,756,337 | 0.39 |

直连臂(同一台机、同一个上游、100 并发闭环)本轮只作参照:p50 548–552 µs、p99 988–1,020 µs、
QPS 169,518–171,621、观察者 0.99 核(直连臂本来就是这个形状,B-009 记过)。
**每请求 `epoll_ctl` = `epoll_modifications ÷ requests_parsed`**(B-001 起就是这个口径),
四份落在 **4.0000–4.0005**,极差 0.0005,两臂各自都在带内。

### 判定

```
实测 每请求成本增量 = 无可分辨增量
     p50：A 两 3,264 / B 两 3,136（组内极差各 0；跨臂差 128 µs = 该量级一个 HDR 桶宽 ≈141 µs）
     p99：四份全等 4,480 µs（极差 0）
     p999：A 5,760 / 6,016（组内极差 256 µs）、B 5,760 / 5,760（极差 0）→ A 自己的散布 ≥ 跨臂差
     QPS：A 30,875.1–31,185.6（极差 311，1.01%）、B 31,304.1–31,633.2（极差 329，1.05%）
     每请求 epoll_ctl：4.0000–4.0005（极差 0.0005）
目标 S3-01 验收句：增量不超过本档散布带
判定 **通过（无可分辨成本）**——不是"变快了"，是"这台仪器分辨不出路由这一环花了多少钱"
归因 链上一次纯函数调用（前缀是 string_view 比较，本档只有一条规则）+ 一次下标比较，
     没有新增 syscall：四份的每请求 epoll_ctl 与空链臂同值就是这句话的证据
```

**那个不好看的一面要写清楚**:QPS 两臂的名义区间**不重叠**(A 上界 31,185.6 < B 下界 31,304.1,
差 118,0.38%),照规矩四这看起来"可判"。但方向是**加了一环反而快 0.4%**,而 0.4% 远小于
每臂自己的组内极差(1.0%),且 B 臂在每一对里都是**第二个**跑的——机器热状态与后台负载的
顺序效应完全能吃掉这个量。所以我判"无可分辨成本",**不判"路由让网关变快了"**。
把 0.4% 读成收益就是 B-004 那年我写过的那类错(差值的变化主要由分母移动造成)。

**可比性声明**

- 四份都是 `canonic=0`(100 并发不是 SLO #1 写死的 1000 并发那一档)。**本档不判 #1 达标与否**,

  `proxy.client.log`、`direct.client.log`、`s1-p999.summary.txt`),驱动流水在同级 `*.driver.log`。

## 口径变更 · `s1-p99.sh` 从此带 `WORKERS` 因子（2026-10-29，S2-07 第①项）

**改了哪条**：`scripts/bench/s1-p99.sh` 新增环境变量 `WORKERS`（缺省 **1**），传给网关的 `--workers`；
summary 里多一行 `被测系统 workers=N（网关自报 …）`；`NEED_FD` 计入 worker 常驻 fd；
起跑时按**横幅签名**判路径（多 Reactor 必须匹配 `^\[serve\] 监听 .*（workers=N `，单 Reactor 必须匹配
`max_connections=`），对不上 `fatal`；退出后再与网关自报的 `workers=` 对一次账。
**`canonic` 的判据没有加这一项**——SLO #1 写死的五条测量条件里没有线程数，`--workers` 属于**被测系统本身**，
所以它是合法的 A/B 因子而不是口径项。

**为什么改**：核了八份落盘 `canonic=1` 档的 `gateway.log`，**全部是单 Reactor 横幅、没有一份传过 `--workers`**。
也就是说 S2-01 之后那两份（B-006 附的 31.150 ms、B-007 可比性段的 36.930 ms）量的是 S1 的形状，
而文档把它们写成"多 Reactor 之后的对照"。S2-07 的验收句要求"多 Reactor 后按取样规程重测"，
这一格在那之前**根本没有被测量过**。

**改前改后是否可比**：
- **workers=1 那一臂完全可比**——`--workers 1` 就是 `main.cc` 的缺省路径（`workers >= 2` 才起 `ReactorGroup`），
  本轮 workers=1 的三轮（32.990 / 33.050 / 35.210 ms）落在历史八份的同一条带里（29.720–37.890，
  另有两份未引用的 32.320 / 35.140），所以 **B-001…B-007 一条不作废、也不回填**。
- **workers=16 是一个新的臂**，不是历史某一份的复跑。它与 workers=1 之间唯一的差别是 `--workers`，
  其余条件（同一上游夹具、E=1、body、并发、预热/稳态时长、wrk 线程、同一台机、glibc、未绑核）逐项相同，
  所以两者的差可以读作"线程模型的效果"（B-008 那三条理由与不重叠的极差就是它的证据形式）。
- 历史各份**没有一栏记 workers**（当时恒为缺省值 1），所以从今天起报告里必须显式写 `workers=`；
  这一条本身就是这次发现教训的一半——**一个不写出来的常量会在几次改动之后变成没人记得的口径**。

## B-013 · S3-02 的成本那一格：链上加两环值多少钱、"每请求换后端"值多少钱（2026-10-30，workers=1 / 100 并发闭环 / 每臂 2 轮）

**这一格在问什么**：验收句给的形式是"路由链 vs 路由+均衡链，同机交替 ≥2 轮报极差"。ADR-19 还给自己
加了一句更尖的：**均衡让"换目标"从边角变成主路径**，所以 `pump_response` 那次重驱动、以及
"按自己那条目标归还进桶 + 从另一个桶借出"这条路径的负载会上升。这一格答的就是这两件事。

**臂的定义**（`workers=1` / `CONNECTIONS=100` / 1 KiB 体 / 闭环每请求 /
直连 100,000 条每连接、经网关 18,000 条每连接 / 稳态门 ≥50 s / 四臂都起**两台**上游进程）：

| 臂 | 网关配置 | 想量什么 |
|---|---|---|
| **A0 空链** | `--upstream ep1`，一个 filter 都不装 | 基线 |
| **A1 路由 + 一成员组** | `--config`：两条路由各指一个**只含一个成员**的组 | 链上多两环 + 均衡环被走一遍，但永远只有一个人可选、**不会换后端** |
| **A2 路由 + 两成员轮询** | `--config`：一条 catch-all 指一个**两成员**组，`round_robin` | 加进"每请求换后端"这件事 |
| **A2b 路由 + 两成员最少连接** | 同上，`least_conn` | 原想做对照："两台上游同等忙、几乎不换后端" |

### 判读

**一、链上加两环、只要不换后端 → 无可分辨成本。** A1 对 A0 的计数器**逐字相同**
（`epoll_modifications=7,199,900`、`upstream_opened=100`、`pool_borrows=0`），延迟读数
p50 差 192 µs、QPS 差 −4.6%，**略微超出 A0 自己的组内极差（128 µs / 3.9%）**——所以这一格
老实记成"**在本档分辨率的边缘，判不出是否非零**"，不写"零成本"。硬的是那条计数器：
多出来的两环没有多打一次 `epoll_ctl`、没有多开一条上游、没有产生一次借还。

**二、每请求换后端 → 可分辨成本，量级是一倍半。** A2 对 A0：p50 **+1,664 µs（1.57 倍）**、
p99 +2,144、p999 增量从 4.000 ms 变成 6.176–8.672 ms、QPS **−36%**，两轮同方向、
且远超出各自极差的若干倍。ADR-19 后果段自己加的那格**是真的**：换目标一旦发生，
成本不在"算该给谁"上，在**换的动作**上（归还进桶 + 从另一个桶借出，A2 里 292,546 次 = 16.3% 的请求）。
A2 自身 p999 两轮差 2,432 µs（A0 是 0）也是这条的一部分：**换的频率由 100 条并发连接的交错顺序决定**，
所以这一臂的成本要报区间、不能报单点。

**三、这条对照没做成，而失败本身就是本节的第二个发现。** A2b 的本意是"两台上游同等忙、几乎不换后端"，
用来排除"负载从一台摊到两台"这个因子。实际落盘是 **ep1 1,768,877 / ep2 31,123（98.3% / 1.7%）**——
`least_conn` 把连接几乎全吸在第一台上了。机制解释得通、也和三个计数器一致：
`least_conn` 的平手规则是"等长取成员顺序第一条"（`lb_filter.cc` 里写死的破平），而**均衡是每请求重做的**：
一旦两台的配对数看起来相等，任何一条当前配在第二台上的下游都会被重新判给"第一条"，于是它换目标、
把第二台那一格腾出来、让总数继续往第一台偏——`upstream_opened=830`（对照 A0 的 100）与
4,318 次借还就是这次迁移的账。它两轮计数器**完全相同**，说明这不是运气而是结构的吸引子。

**所以**：
- 上面第二条的"排除两台上游抢 CPU"这句话**我原来写重了**，现在降级为：A2b 只证明"两台上游都被连过、
  都开过连接"时成本没有复现，**没证明**"两台同等负载"时也没有。要真排除上游侧的因子，得先修平手规则
  或另加一臂。
- **`least_conn` 今天这个形状是有毛病的**：它不是"往最闲的送"，而是"往成员 0 聚"。
  这在两条单测里没暴露，因为它们的并发形状刚好把配对数拉开了（`...SendsNewWorkToTheIdleBackend` 里
  0 号和 1 号被 stall 占住、2 号是唯一的 0）。**用例的形状决定了它抓不抓得住这条**——
  这是 §8/§9 那条"没红过的断言不算断言"的又一次应用，只是这次红的是**真实负载**而不是我改坏代码。
  nginx 的做法是平手时在平手集合里轮询；要不要采纳是**一条行为变更**，得进 ADR-19 再进本表，
  我不在收尾里顺手改。已列为待裁事项（TASKS 交接段）。

**四、这格还没归因完的部分，写明不藏。** A2 每请求 p50 +1.6 ms，而切换只发生在 16.3% 的请求上——
摊到每条切换请求上是 ~10 ms 的量级，**大到不像"一次归还 + 一次借出"应有的成本**。剩下的可能
（切换后那条上游的连接状态/EPOLLOUT 重挂、被压住的那次重驱动、桶间 shared_ptr 搬运）我都**没有**
直接证据；`perf` 火焰图是该用的工具，而 perf 与本机 6.18.40.1-WSL2 内核的匹配性仍是
`docs/ENVIRONMENT.md` 第 4 节的未验证项，且契约 3.2 把火焰图列为延迟决策的证据门槛。
**本格结论止于**："换目标有可分辨成本（p50 约 1.6 倍、QPS −36%），成本不在选择计算上、
也不在 `epoll_ctl` 数量上；进一步的归因需要火焰图或一条临时切换探针。"
**对 S3-03 的直接后果**：如果健康检查的摘除/恢复会改变可用成员数，那它的代价不只等于容量损失，
**还等于一次全组重排**——这条要写进 S3-03 的实测设计里。

### 一条必须同时说的更正：B-012 那四轮是被工具自己判红的

`build/bench/s3-01-cost-a1.driver.log` 里有 7 条 ✗，包括 `requests_done=20594212 ≠ planned=650000000`
和脚本自己那句"本轮有 ✗，上面的数字不要用"。**根因不是网关也不是脚本坏**：
`REQUESTS_DIRECT` / `REQUESTS_PROXY` 是**每条连接**的配额，总配额 = ×并发；
6,500,000 × 100 = 650M 条超过 `l7gate_c100k` 自己约 120 s 的总预算，客户端在吃完配额之前按预算收工，
于是 `requests_done == requests_planned` 这道门**在那组参数下永远合不上**。B-012 的读数来自一个
119,998 ms 的真稳态窗口，但那一轮的形式资格不成立。
**本格的定标就是被它逼出来的**：直连 100,000、经网关 18,000 条每连接，八轮全部 `rc=0`、✗ 计数 0、
`requests_done == parsed == completed` 逐轮闭合。**B-012 已记的"无可分辨成本"我不回头改数**，
是否按本次定标复测由项目所有人裁决；这里只把形式资格写清楚，免得下一个人把 4.0000 读成"已完整验收"。

## B-014 · S3-03 的两个门禁数：摘除耗时、误摘率（带分母），外加安全阀那一格（2026-10-30，真进程 / release / 两轮取样）

**这一格在问什么**：契约第 4 节给 S3 的原话是"摘除耗时实测；误摘率实测"。这两个数不是功能清单——
一个回答"坏后端拖着流量多久"（S2-06 实测的 71,769 条客户端超时就是没有它的形状），
一个回答"判据失准时我会不会把健康的也摘掉"。第三格是 ADR-12 第一次真正落地：全部后端同时死时，
被摘除的容量必须停在上限、且"挡掉了"这件事有账。

**环境**：`release` 构建、`workers=1`、上游是 `l7gate_test_upstream`（仓库内、与单测同一个类）、
`curl` 打业务请求、脚本 `scripts/bench/s3-03-health.sh`、落盘 `build/bench/s3-03/`。跑了两轮取样。

### 阶段 1 · 摘除耗时（门禁第 1 个数）

配置：3 台 `round_robin` + catch-all、探活 `100ms`、`max_fails=2`、`fail_timeout=60s`、
阀 50%。`kill -9` 二号后端（T0 = 脚本墙钟），摘除时刻取网关自报的
`health_t1_127.0.0.1_18182_last_ejection_epoch_ms`（T1，**同一根墙钟轴**，这是它存在的理由）。

| 轮 | 摘除耗时（kill → 网关自报摘除） | 摘除后 10 条业务请求 | 死后端 ejections | 健康两台 ejections |
|---|---|---|---|---|
| r1 | **202 ms** | 全部 200、无一落到 128 B | 1 | 0 / 0 |
| r2 | **202 ms** | 同上 | 1 | 0 / 0 |

**202 ms 的构成对得上账**：至多一个探活间隔（0–100 ms，取决于杀进程落在哪一拍之间）
+ 2 次失败判定（2 个间隔）+ 摘除动作本身。两轮完全一致说明这段是确定性的调度，
不是压在时序上的运气。"该后端不再收到任何请求"由被连的那一侧之外的证据钉：
摘除后 10 条请求无一落到 128 B（128 B 是死后端的体长）。

### 阶段 2 · 误摘率（门禁第 2 个数，带分母）

配置：三台全健康、探活 `20ms` 跑 25 s（每台 ≈1,160 轮）+ 轻业务负载（每 250 ms 一条）。
分母 = 探活轮数 × 健康后端数，分子 = 健康后端被摘次数。

| 轮 | 每台探活轮数 | 分母 | 分子 | 误摘率 |
|---|---|---|---|---|
| r1 | 1160 / 1160 / 1160 | 3480 | **0** | **0 / 3480 = 0.00%** |
| r2 | 1157 / 1157 / 1157 | 3471 | **0** | **0 / 3471 = 0.00%** |

判据成对（ADR-12 落地追加节）：上界（0 ≤ X）在本阶段天然满足——但**"从不摘除"的退化实现
同样满足它**，所以"摘除确实发生过"的下界由阶段 1（死后端 ejections=1）与阶段 3（摘除总数=1）
承担，三者合起来才是这一格的完整证据。

### 阶段 3 · 安全阀（ADR-12 第一次真正落地）

配置：10 台后端**全部杀掉**、`max_ejection_percent=10`、探活 `50ms`。floor(10 × 10%) = 1 台可摘。

| 轮 | ejected_now | 摘除总数 | 被阀挡下 |
|---|---|---|---|
| r1 | 1 | 1 | 540 |
| r2 | 1 | 1 | 540 |

"最坏只损失 10% 容量"由 `ejected_now=1` 直接钉住；"阀不是靠从不摘除过关"由摘除总数=1 钉；
"挡掉的每一次有账"由 blocked_by_valve=540 钉（3 s ÷ 50ms ≈ 60 轮 × 9 台待摘 ≈ 540，逐拍对得上）。

### 过程中逼出来的一处实现修正（照记）

第一轮取数时阶段 2 只跑了 **189 轮**（25 s ÷ 132 ms，不是预期的 ≈1,250 轮）。根因不在探活机：
`epoll_wait` 的默认上限 `wait_timeout_ms=200` 决定了健康 tick 最多每 200 ms 醒一次，探活的
"每 20 ms 一拍"被循环的睡眠上限拉长了一整个量级。修法：**探活启用时**把等待上限夹到
探活间隔（`Reactor::run()`，探活不装配的路径一分钟都不多醒——SLO #2 的空闲场景不受影响）。
修后 1160 轮。取数工具侧另踩一格：本机 `date +%3N` 把 `%N` 按纳秒打出（19 位时间戳），
毫秒改用 bash 的 `EPOCHREALTIME`。

### 不在本格

每请求成本对照（S3 门禁第 3 条）按 TASKS 的拆解归 **S3-06** 的终值等式（对着 B-008 的
≈8.7 µs 报）；B-012/B-013 的对照臂届时按 B-013 的定标复跑与否、连同待裁⑤一起处理。

## B-015 · S3-04 的两个验收数：首次连通取证 + reload 生效耗时（2026-10-30，真容器 / release）

**这一格在问什么**：契约 9.1 把"8.4 客户端 ↔ 8.0.36 服务端兼容性"挂了四天的"未取证不算既成事实"；
S3-04 验收句要的 reload 生效耗时（增删一个后端到路由表反映出来的秒数）和降级路径
（MySQL 不可用时按已加载的配置继续服务）。这三件事合起来是节点表这条线的全部证据。

**环境**：`release` 构建、Docker Desktop WSL Integration（server 29.4.3）、镜像 `mysql:8.0.36`
（digest `sha256:a53272402242…`，锁定 tag 未动）、端口发布 `127.0.0.1:13306 → 3306`、
上游 `l7gate_test_upstream` 三台、`curl` 打业务请求、脚本 `scripts/smoke-s3-04.sh`（真容器全链路）、
探针 `l7gate_mysql_probe`（连通取证可复跑）。

### 首次连通取证（契约 9.1 那句话的翻案）

`l7gate_mysql_probe` 五步全通：**connect → CREATE TABLE → INSERT → SELECT 读回 → DELETE**，
`client=8.4.11 ↔ server=8.0.36`。8.4 客户端连 8.0 服务端从"Oracle 矩阵说允许"转正为
"本机实测成立"（ENVIRONMENT 第 3 节已就地更正）。取证工具是仓库内的可复跑目标，
不链 `l7gate_core`——验的是客户端库本身，链上产品代码反而分不清"是库的问题还是我的问题"。

### reload 生效耗时（验收：增删一个后端到路由表反映出来的秒数）

两端钉法：T0 = 脚本 `INSERT`（脚本墙钟）；T1 = 网关第一次把请求发到新成员（首次观测到
它的响应体长）。网关自报的 `nodes_last_publish_epoch_ms` 落在 [T0, T1] 内（同一根墙钟轴）。

| 轮 | reload 生效耗时 | reload 间隔配置 | 构成 |
|---|---|---|---|
| r1 | **406 ms** | 500 ms | ≤ 一个 reload 周期 + 查询 + 发布 + worker 对账 |
| r2 | **536 ms** | 500 ms | 同上（跨了一个周期边界） |

读数的**粒度就是 reload 间隔**：生效时刻落在"变更后的第一次成功 fetch"，而 fetch 每 500ms
一拍。要更快的生效就把间隔调小——代价是 MySQL 的查询频率，这是配置取舍不是实现上界。
DELETE 对称验证（删掉的成员在宽限一个周期后不再接到任何请求）两轮全过。

### 降级路径（验收：不是拒绝、不是 500）

| 格 | 实测 |
|---|---|
| `docker stop` mysqld 期间 20 条业务请求 | **全部 200**，按已加载成员继续服务 |
| 停机期间网关自报 | `nodes_reloads_failed=10`（每拍失败有账，不安静） |
| `docker start` + INSERT 恢复 | reload 自动接上，被删成员**重新到岗**（本轮 +1 次 `reloads_ok`） |
| 业务计数 | `requests_parsed == responses_completed == 96`——节点表查询不进业务计数（结构上：它不走 Connection 配对机） |

### 工具侧发现（第一轮两格红的归因，照记）

第一轮冒烟两格红，**根因都在脚本不在实现**：① DELETE 判定没给 reload 生效宽限——
DELETE 后第一拍 curl 就撞上旧快照的尾巴，把"还没生效"读成了"没生效"；给一个完整
reload 周期的宽限后同一条路径全绿。② 收尾的信号循环写成 `${PIDS[@]:1}`，把 1 号上游
漏在信号名单外，`wait` 等一个永不退出的进程。两条都与 ⑧（脚本没在跑的时候编辑）同族：
**判定窗口必须覆盖被测机制的生效粒度**。

## B-016 · S3-06 的每请求成本终值：空链 vs 全 S3 链（路由 + 均衡 + 被动 + 探活）（2026-10-30，workers=1 / 100 并发闭环 / 同机交替各 2 轮）

**这一格在问什么**：S3 门禁第 3 条的终值——"S3 的三件新功能每请求加了多少"，对着 **B-008 的
≈8.7 µs 净赤字**报。S3-02 的 B-013 已经量过"路由 + 均衡"两环（不换后端时判"在本档分辨率的
边缘，判不出是否非零"），B-016 补的是**健康检查整段上线**之后的全链形状。

**参数与 B-013 逐字同形**：workers=1 / `CONNECTIONS=100` / 1 KiB 体 / 闭环每请求 /
直连 100,000 条每连接、经网关 18,000 条每连接 / 稳态门 ≥50 s / 单上游。两臂只差一个因子：
**A0 = 空链 `--upstream`；BS3 = 全 S3 链**（catch-all 路由 + 一成员组 + health 段
`probe_interval=100ms`——探活一拍比缺省密十倍，量的是成本上界）。同机交替 A0-r1 → BS3-r1 →
A0-r2 → BS3-r2。落盘 `build/bench/b016-*/`；仪器 `s1-p999.sh` 加了缺省关闭的 `HEALTH_PROBES`
旋钮（探活会往上游打进请求，等式放宽成**有界账**：差值必须落在
[probe_ok, probe_ok+probe_fail] 内）。

### 结果（经网关一侧；直连臂只作分母）

| 轮 | 臂 | p50 µs | p99 µs | p999 µs | QPS | 窗口 ms | 每请求 epoll_ctl |
|---|---|---|---|---|---|---|---|
| r1 | A0 空链 | 3,136 | 4,992 | 6,528 | 34,206 | 52,622 | **4.0000**（7,199,900/1.8M） |
| r1 | BS3 全链 | 3,136 | 5,504 | 7,296 | 33,335 | 53,998 | **4.0003**（7,200,590/1.8M） |
| r2 | A0 空链 | 3,264 | 5,248 | 6,784 | 32,495 | 55,393 | **4.0000** |
| r2 | BS3 全链 | 3,392 | 6,016 | 7,808 | 30,616 | 58,792 | **4.0004**（7,200,638/1.8M） |

### 逐项判定

- **p50 与 QPS：无可分辨**。p50 跨臂差 0 / 128 µs，都在 A0 组内极差（128 µs）内；QPS 跨臂差
  −2.5% / −5.8%，在组内极差（A0 5.1%、BS3 8.5%）内。**每请求净成本对着 B-008 的 8.7 µs
  没有可分辨的抬升**——三环 + 被动记账不收费，与 B-013 的 A1 读数（p50 3,136、p99 4,992、
  QPS 32,329）互为印证。
- **p99 抬出带外，归因 = 主动探活，照记**：BS3 的 p99 比同轮 A0 高 **512 / 768 µs**，超出
  组内极差。对照 B-013 A1（路由 + 一成员组、无健康检查）同档读数 p99 4,992 / 5,248——
  **三环没有这个抬升，探活有**：每 100ms 一条 `Connection: close` 的探活连接（两轮
  probe_ok = 690 / 738）在业务尾部制造调度交互。这是探活间隔取 100ms（比缺省密十倍）的
  **成本上界读数**；缺省 1000ms 时按比例缩。p999 方向相同（7,296 / 7,808 vs 6,528 / 6,784）。
- **每请求 `epoll_ctl` 的探活贡献逐数闭合**：BS3 臂多出的 modifications（690 / 738）
  **恰好等于 probe_ok**——每次探活恰好多打一次掩码修改，一分不多。每请求 4.0000 →
  4.0003–4.0004 的增量 = 探活数 ÷ 业务请求数，不是噪声。
- **探活有界账**：两轮差值 690 / 738 都落在 [probe_ok, probe_ok+probe_fail] 内
  （probe_fail = 0，全部探活成功），等式门的新口径第一次实战通过。

### 待裁⑤的裁决：B-012 不重跑

B-012 那"无可分辨成本"的落盘自带 7 条 ✗（每连接配额被当总配额用），形式资格不成立——
但它的**结论**（空链 vs 路由链无可分辨）已被两份定标合格的测量背书：B-013（同参数四臂）
与本 B-016 的 A0 两轮。**裁：B-012 不复跑，原文照记、结论由 B-013/B-016 维持**；待裁⑤就此结掉。
