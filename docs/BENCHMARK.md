# BENCHMARK —— 压测记录

规矩只有四条，都是为了让"半年后这份数字还能不能用"这个问题有答案：

一，**一次压测一条记录**，原始数字（不是截图里的均值）+ 结论 + 环境参数一起写。契约第 7 节对这份文件的完成判据点名了三样：CPU 绑核、分配器、各组件版本号。少任一条，这份记录就只是"我记得当时挺快"。

二，**口径变更必须留一条记录**：改了哪条、为什么改、改前改后是否可比。不许把不可比的两次放在一起画趋势线。

三，**达标判定只认 `canonic=1` 的那一轮**（`scripts/bench/` 里的脚本自己判口径，不由我嘴上说）。非标准口径的跑法允许存在，但它的身份是**归因实验**，标题里就写明。

四，**判断"某次改动有没有改善"必须同机交替、每改动至少两轮，并给出极差**（2026-10-26 裁决采纳，自 S2 起强制）。这条是从 S1 收尾的散布里长出来的：同一份 binary 复跑，直连 p99 自己漂 11.3%、四份增量极差 27%、#3 比值两轮复现 206.11%/203.74%（差 1.2%）。写进这里而不是只写在 SLO，是因为**每份新记录都要在标题下面回答"另一轮呢？"**——答不出来就标"单轮样本，不构成改动有效的证据"。

### 结论：**未达标**，且 p999 半边当前无法判定

SLO #1 的目标是增量 **p99 ≤ 1.0 ms、p999 ≤ 5.0 ms**。实测增量 p99 = **57.540 ms**，超目标 57 倍。按契约 8.2 禁令二，目标值不动，这里照记并归因。

p999 不是"没测到"而是**这套工具链取不到**：wrk 4.1.0 的 `--latency` 只打 50/75/90/99 四行，hey 0.1.4 的分位表只到 99%。要拿到任意分位需要换/加发压工具（wrk2、vegeta、自研皆算新依赖），按契约 8.2 禁令三要先 ADR，按交接段授权 (a)(b) 两项都要停下来请示——所以这一格记"无法判定"，不记 0。

### 归因

**一，这个 57.54 ms 里绝大部分是排队，不是网关的加工成本。** wrk 是闭环模型：1000 条连接，每条"发一条、等一条"，于是稳态下 `延迟 ≈ 连接数 / QPS`（Little 定律）。验算：直连 1000/59,860 = 16.7 ms ≈ 实测 p50 16.35 ms；经网关 1000/18,229 = 54.9 ms ≈ 实测 p50 53.35 ms。两组都贴合到 3% 以内。所以"经网关 p99 = 82 ms"读作"网关把服务速率降到了 1/3.3，于是每条连接在闭环里多排了 38 ms 的队"，而不是"网关每请求多花 38 ms"。

**二，换算成每请求服务时间，网关引入的是 ≈38 µs，不是 38 ms。** 直连时上游单线程 16.7 µs/请求；经网关时瓶颈线程（网关）54.9 µs/请求。差值 ≈38 µs 是网关自己的 CPU 成本。旁证：把并发降到 50（`build/bench/s1-c50/`，非标准口径，仅作归因不作判定），增量 p99 从 57.54 ms 塌到 **1.36 ms**、p50 从 37.0 ms 塌到 **1.09 ms**——尾巴随并发线性收缩，正是排队主导的形状，而残下的 ~1 ms 量级才是每请求成本在闭环里的表现。

**三，每请求成本的可观测来源：单 Reactor + 每请求 5.0 次 `epoll_ctl`。** `epoll_modifications=9,359,517 / requests_parsed=1,872,093 = 5.0`。S1 的形状本来就是一条事件循环线程（ADR-03、S1-04），挂/摘 `EPOLLOUT` 各一次 × 两个方向 + 收尾一次是这套 ET 写法的固有支出。这两条都是**已计划的后续任务**要动的地方：多 Reactor 与连接池在 S2（`TASKS.md` S2 行），背压动作在 S1-07；本任务不改结构去追数字。（**S1-07 之后这个数是 4.005**，见 B-003 的对照表——省下的那一次我没有归因到具体代码行，只有两处独立测量都稳定少 1 次这个事实，见 ARCHITECTURE 1.15；同一份对照表也显示 50 并发下的每请求成本没变，所以"少一次 syscall"没有兑换成尾延迟的等比改善，这条当年写的因果要按那个强度读。）

**四，尾延迟的放大机制说明 S1 的这个数字不能横向比。** 同一份网关代码，1000 并发下增量 57.5 ms、50 并发下 1.36 ms。SLO #1 写死了 1000 并发，所以判定按 57.5 ms 记未达标；但真正要向"≤1.0 ms"逼近的路径是每请求服务时间（38 µs 这一头）与并发分摊（S2 那一头），把这条写在这里是为了下一次改代码时有正确的成功判据，而不是去调口径。

### 另两个数字（门禁四件套第 1 条要求同场记录）

**自测 QPS（经网关，wrk 闭环 1000 并发，60 s 稳态）= 18,229.47**；直连同一上游 = 59,860.19。按卡点三，S1 只交这个数字、不设判定基线（vs Nginx 的基线在 S3/S5，Docker 尚未可用）。

### 与 B-001 对照：什么变了、什么没变、什么我不能归因

| 指标 | B-001（S1-06） | B-003（S1-07） | 变化 |
|---|---|---|---|
| 增量 p99 | 57.540 ms | **36.420 ms** | −21.120 ms（−36.7%），**仍未达标**（超目标 36 倍） |
| 经网关 p99 | 82.390 ms | 61.950 ms | −20.440 ms（−24.8%） |
| 直连 p99 | 24.850 ms | 25.530 ms | +0.680 ms（+2.7%）——基线自己也在动，这条就是"增量的分母是我自己的上游"那句话的意思 |
| 经网关 QPS | 18,229.47 | 19,640.38 | +7.7% |
| 每请求 `epoll_ctl` | 5.00（9,359,517 / 1,872,093） | **4.005**（7,872,390 / 1,965,838） | **−19.9%**，这是本任务确定性的结构收益 |
| 50 并发对照的增量 p99 | 1.360 ms | 1.370 ms | +0.7%（QPS 27,510 → 27,582，+0.3%） |

**没变的那一条决定了这张表怎么读。** 50 并发那轮是"每请求成本"的对照：1.360 → 1.370 ms、QPS 差 0.3%，也就是**每请求 CPU 成本一次都没降**。既然每请求成本没降、QPS 只涨 7.7%，那 1000 并发下 21 ms 的增量收缩就**不能**说成"少打一次 `epoll_ctl` 换来的"——它是高并发尾巴形状的变化（p50→p99 的跨度从 29.04 ms 缩到 12.16 ms），而我只各有**一轮**样本，没有在同一台机器上把两个 binary 交替跑起来的 A/B，所以这条改动的因果我写不出来。诚实的版本是：**每请求 `epoll_ctl` 从 5.00 降到 4.005 是实测的、可复现的；增量 p99 从 57.54 降到 36.42 是实测的；把前者说成后者的原因是我没有证据的**。要拿这条做趋势，得先按 SLO 的"口径变更必须留记录"补一次同机交替复跑。

排队主导的判定继续成立（B-001 归因第一条不作废）：`延迟 ≈ 连接数 / QPS`，经网关 1000/19,640.38 = 50.9 ms ≈ p50 49.790（差 2.2%），直连 1000/59,624.37 = 16.8 ms ≈ 16.180（差 3.6%）。B-001 归因第三条里"每请求 5.0 次 `epoll_ctl`"这个数在 S1-07 之后是 **4.005**，那一节已就地标注。

### 结论：**未达标**（增量 p99 = 36.420 ms，目标 ≤ 1.0 ms）；p999 半边仍无法判定（wrk 4.1.0 / hey 0.1.4 的分位表都只到 99%）

按契约 8.2 禁令二，目标值不动。下一步的数字归属写清楚：S1-07 交的是"停读线在真实负载下不误触发"（四个计数全 0）+ 每请求 `epoll_ctl` 少一次，这两条都到位；把增量 p99 压向 1.0 ms 的路径仍然在 S2（多 Reactor 分摊并发）与每请求服务时间（36 µs 这一头，见 B-002/B-003 的 50 并发对照），不在背压里。

### 可比性声明

与 B-001 逐项对齐：`release`、未绑核、glibc、同一个 `l7gate_bench_upstream`、`CONNECTIONS=1000 / DURATION=60s / WARMUP=10s / WRK_THREADS=8 / BODY_BYTES=1024`、`canonic=1`。唯一变化是被测代码本身。**注意**：单轮样本在 1000 并发下的复现性我没有测过（B-002 那种低并发对照的 ±1% 不能外推到这儿），所以上面的对照表只能读成"两次实测的差"，不能读成"这次改动的效果"。

## 口径变更 · SLO #2 的分母：连接数 → 连接对（2026-10-26，项目所有人裁决）

**改了哪条**：`SLO.md` #2 的「每连接内存 = (VmRSS − 空进程基线 RSS) / 连接数」里，分母由含糊的"连接数"明确为**连接对数**（1 个客户端连接 + 1 条回源连接 = 1 个计费单位）。**目标值 `≤ 20 KB` 未动**（契约 8.2 禁令二管的是目标值，这里改的是分母解释，且由裁决给出，不是我自行放宽）。

**为什么改**：`TASKS.md` 卡点四记的那条歧义——网关侧一条下游 + 一条上游是 2 个 fd、2 个 `Connection` 对象，"每连接 20 KB"在这两种读法下差一倍，而 SLO #2 的判定要到 S2/S3 才做，越晚定越容易被历史读数牵着走。

**改前改后是否可比**：S1 期间的读数分两种情况——
- **负载态**（B-001…B-004 的 `≈19.7 KiB/连接对`）**本来就是把 `VmRSS` 增量除以 1000 对**得到的，所以换口径后**数值不变**，只是当时行文写成了"每连接对"。
- **空闲态**（`S1_04_Reactor.MemoryPerIdleConnectionIsMeasured` 摊出的 **5.81 KiB/连接对象**、`sizeof(Connection)=520`）是**对象**口径，按新分母要 ×2 ≈ **11.6 KiB/连接对**（128 条空闲下游连接场景里回源连接根本没建，`outbound_buffers_created`/`scratches_created` 为 0，所以这个 ×2 是**口径换算而不是实测**——真正的双对象空闲内存要等 S2 的连接模型 + 100k 场景测出来，那一轮才是 SLO #2 的判定读数）。
这条换算我标成"口径推导"而不是"实测"，因为把它写成实测就等于凭空造一个数（128 条空闲下游连接对应的上游连接数 = 0，`upstream_opened` 在读数里可查）。

**为什么这条值得单独一节而不是改一行**：`ENVIRONMENT.md` 第 7 节早就写明 SLO #2 的数字"直接由 malloc 实现决定"，分母再一变动，历史读数就全部要带着口径标签才能引用。这正是契约规矩二（口径变更必须留记录）存在的理由。

### 为什么这个 206% 不能当结论

一、**分母被测量条件压在天花板之下**。同一个上游直连能跑 56,332.52 QPS，而 nginx 只有它的 **16.2%**。这里面有我消不掉的东西：nginx 在容器里，客户端 leg 走端口发布（DNAT/userland proxy），上游 leg 要从容器出到 WSL 的 eth0（实测 `--network host` **不**共享本发行版的网络命名空间、bridge IP `172.17.0.2` 从 WSL 不可路由，唯一可达入口是 `-p` 发布端口），而网关两侧都是原生回环。这个方向是**拖累 nginx**，所以比值对我偏乐观。
二、**并行度维度没对齐，而对照数据显示瓶颈不在这里**。镜像默认 `worker_processes auto` = 16 worker，我的网关按 ADR-03 就是单 Reactor（多线程属 S2）。档 3 就是为这一维准备的：单 worker 8,053.12 vs 16 worker 关日志 10,627.06 = **76%**——说明这套容器路径里 nginx 根本不是"CPU 并行度不够"，而是被路径本身限制住了。这反过来加重第 一条的分量：容器网络是主因。
三、**比值本身的取样散布大到不能用来宣判**。nginx 原始态三遍是 8,616.83 / 8,834.96 / 9,147.69（极差 6.2%），而网关两遍是 13,654.61（run1）与 18,854.32（run3），**差 38%**，直连两遍 45,336.98 / 56,332.52 差 24%。于是比值两次是 **158.46%**（run1，20:37–20:44）与 **206.11%**（run3）。60% 这条线远在两次读数之下，但拿 30% 松的量去宣布"达标"就是把噪声当结论。**（这一条的归因已由下面的 B-005 附修正：第二轮复现出 203.74%，与 206.11% 只差 1.2%——所以这 30% 不是比值的固有带宽，而是 run1 那一轮「被测方」被环境拖慢造成的。原判定「暂缓」不变，但理由的权重变了：分母被压和并行度不对齐才是留下来的理由，取样散布这一条被实测削弱了。）**
